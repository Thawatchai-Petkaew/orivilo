## How the list was built (fact, with one open point)

- **The Anthropic page lists 42 slugs** (`https://openrouter.ai/anthropic`; own count of the 42 numbered items returned): 38 model slugs and 4 aliases whose slug starts with `~`. The page shows no price or context length.
- **Each of the 38 model slugs was looked up** at `https://openrouter.ai/api/v1/models/anthropic/<slug>/endpoints` (each URL in `source:`). 16 return one or more endpoints; 22 return an empty `endpoints` array (own count over those 38 responses, pattern: endpoint count above 0). This entry calls the 16 "live". No response read carries an `expiration_date` or `deprecated` field.
- **The 4 aliases** (`claude-fable-latest`, `claude-haiku-latest`, `claude-opus-latest`, `claude-sonnet-latest`, each with the `~anthropic/` prefix) are left out of the table: the Sonnet alias page says it "is a latest alias: it always points at the newest model in its family." and that each request is billed "at that model's current price"; it does not name the model it points to. The Haiku alias's endpoints call returns `input_modalities` `["image","text"]` and 0 endpoints. The Fable and Opus alias pages were not read.
- **Open point: the public models list.** The models guide says the root of `GET /api/v1/models` holds `data`, `total_count` and `links`, and "when both are omitted, the full list is returned". Three fetches of `https://openrouter.ai/api/v1/models` (plain, with `supported_parameters=response_format`, with `use_rss=true`) each returned a different shape instead: `data`, `has_more`, `first_id`, `last_id`, with 10 entries of `id`, `type`, `display_name`, `created_at`, `max_input_tokens`, `max_tokens`, `capabilities`, ids such as `anthropic/claude-sonnet-5.5[1m]` and `anthropic/openai/gpt-6.2-astra`, and `has_more` false. The guide "doesn't mention any Anthropic-compatible format or header that changes the response". Why the fetch got this shape is not known; no figure in the table below comes from it.

## Structured output (fact)

- The structured outputs guide shows `"response_format": { "type": "json_schema", "json_schema": { "name": "weather", "strict": true, ...` and says "Structured outputs are supported by select models." and "Support is determined per endpoint, not just per model." For a given model, "check the `structured_outputs` parameter in the Providers section of the model's page."; to route only to supporting endpoints, "Set `require_parameters: true` in your provider preferences."; on a model without support, "The request will fail with an error indicating lack of support."
- The chat completions reference describes `ChatFormatJsonSchemaConfig` as "JSON Schema response format for structured outputs" and `strict` as "Enable strict schema adherence".
- The provider selection guide: `require_parameters` means "Only use providers that support all parameters in your request." (default `false`).
- **Pattern in the table** (own reading of the 16 rows): on every live Anthropic model with a 5.x number, every endpoint lists `response_format`, and every endpoint without `structured_outputs` has an `amazon-bedrock` or `claude-on-aws` tag (Bedrock on every 5.x model, `claude-on-aws` on haiku-5.5 and sonnet-5.5), apart from fable-5.2 `google-vertex/global`. On haiku-4.5, sonnet-4.5 and opus-4.5 the `google-vertex` endpoints list `structured_outputs` but not `response_format`.
- **Not stated.** No page read says whether `require_parameters: true` matches a request carrying `response_format` of type `json_schema` against an endpoint's `response_format` entry, its `structured_outputs` entry, or both.

## Data policy parameters (fact, with what is not stated)

- **`provider.zdr`.** The provider selection guide: "When `zdr` is set to `true`, the request will only be routed to ZDR endpoints." The ZDR guide: "Zero Data Retention (ZDR) means no routine storage of prompts or responses after processing." and the list "is also available programmatically via" `https://openrouter.ai/api/v1/endpoints/zdr`, which also includes Safety Retention endpoints, used only if allowed.
- **The ZDR list, Anthropic models.** Read in thirteen parts at offsets 0 to 1,200,000. Every entry found with a `model_id` starting `anthropic/` has provider `Amazon Bedrock` or `Google` and `safety_retention: false`; none has the tag `anthropic`, `anthropic/fast`, `claude-on-aws` or an `azure` tag, and no `claude-fable` entry was found. The ZDR column above counts these entries per model (own count over the thirteen parts). One entry was split across two parts: the part ending at 1,000,000 cut off at "Amazon Bedrock | anthropic/claude-4.7-opus-20260416", and the next part returned its name "Claude Opus 4.7" with tag `amazon-bedrock/global`; it is counted under opus-4.7. A reading model may miss an entry in a 100,000-character part, so each ZDR count is a lower bound we did not recount.
- **The ZDR guide agrees for Anthropic.** Under "Per-Model-Group ZDR Enforcement", the Anthropic row reads "Removes first-party Anthropic endpoints (Bedrock and Vertex remain available)". That table describes an account setting per model group, not the request field. The guide does not mention Claude Platform on AWS. On Google, the guide says Google requires Safety Retention "for Google models served through Vertex"; it does not say this of Anthropic models on Vertex.
- **`provider.data_collection: "deny"`.** The provider selection guide: "use only providers which do not collect user data" (default `allow`). The chat completions reference: "If no available model provider meets the requirement, your request will return an error." **Not stated:** no page read says which of the endpoints in the table meet `deny`. The endpoints responses carry no data policy field; the providers API gives only `privacy_policy_url`, `terms_of_service_url`, `status_page_url`, `headquarters` and `datacenters` (Anthropic and Claude Platform on AWS both link to `https://www.anthropic.com/legal/privacy`); the provider logging page says the retention policies "are shown below", but the table was not in the text returned for either form of its URL. That page does say "If you opt out of training in your account settings, OpenRouter will not route to providers that train." No page read says whether an endpoint in the ZDR list also meets `deny`.
- **Image input on chat completions.** The chat completions reference's `ChatContentImage` has type `image_url`, `image_url.url` "URL of the image (data: URLs supported)", and `detail` values `auto`, `low`, `high`, `original`. The image understanding guide covers the Responses API ("Each image is an `input_image` content part ...") and lists `image/png`, `image/jpeg`, `image/webp` and `image/gif`; it says "The number of images you can send in a single request varies per provider and per model."

## Our reading, not a stated fact

No page read states this; it is a point for the architect to check with one real answer.

## Why it matters for ORIVILO

`AI_MODELS` in `packages/intent-engine/src/openrouter.ts` pins one model per job; `chat` and `interpret` read `anthropic/claude-sonnet-5.5` and `logo-vector` reads `anthropic/claude-opus-5.5`, and `instant` and `see` use other makers' models. This entry gives the ids, prices, context, image input, and which endpoints can serve a strict `json_schema` call under `zdr: true`, so the architect can pick a model per job and check the data policy routing; which model fits which job is the architect's decision.
