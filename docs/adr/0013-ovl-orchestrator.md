## Context

From ORV-72 to ORV-78 the main session designed, built and checked its own work, with reviewer subagents it briefed in prose. G3 passed every story. The owner then found four defects in screenshots (ORV-80):

1. A Checkbox not centred on its line. The cause was an invalid `calc()` that had been there since E2-4, so every check since then had missed it.
2. A cramped `sm` gap.
3. Story menus that overlap.
4. A squash that reverted ORV-75, because it was built from a stale base.

Each was reported as verified. The checks that would have caught them (a screenshot someone looked at, a computed style, the PR file list compared with `develop`) were never required, so they were never run. The owner does not trust solo work, and the record supports that.

Two systems the team studied solve the same problem.

**Camp Vibes** sends each task as a JSON envelope `{ticket, spec, files, deltas, done_when}`, where `done_when` lists commands that prove the outcome. A role returns JSON `{status, artifacts, checks, summary, needs_decision, blocked_on, next}`; a prose return is sent back. QA writes oracle-first tests from the AC, and a fresh-context adversarial reviewer follows. `complete()` refuses Done without a QA or Security role in the history. Two rejections send the story back to Discovery. A stall watchdog fires after 15 minutes with no commits. A dispatch claim needs an `agentId`, so a phantom dispatch cannot count.

**Allkons Atlas** is a skill in the main loop that never edits deliverables. Its envelope carries `task_id`, `objective`, `role`, `report_contract`, `context_pointers`, `boundaries`, `write_set`, `done_when`, `facts[{claim, checked_by}]` and `model_selection`, with three report contracts (implementer, reviewer, explorer). Acceptance is deterministic checks first, then one fresh-context reviewer. Proof must match the claim: for anything visual, a computed style or a screenshot that was looked at. A finding with no re-executable evidence is dropped. Model-judged review rounds stop at 2, then a human decides. Hooks exit 2: one requires `checked_by` on Agent calls, one guards writes. A heartbeat proves the hooks fire, because a quoting bug once silenced every hook for a month. Their own measure: prose caught 0 of 83 gaps, and running gates caught 7 of 7.

Both agree on the point that matters here: a claim counts only when a check that ran backs it, and the checks are enforced by code, not by instructions.

## Decision

1. **`/ovl` is a skill in the main session.** The main session plans, writes envelopes, keeps records, posts gate packets and talks to the owner. It never edits a deliverable, a guard file or a record: a hook blocks its writes under `packages/` and `apps/`, to the hooks, settings and `scripts/ovl/`, and to `.orivilo/` and `.quality-gate/`. A subagent cannot dispatch subagents, so the orchestrator cannot be an agent; the `lead` agent is retired.
2. **Envelope in, JSON report out.** Every dispatch is one `envelope.v1` JSON object, sent to the agent its `role` names. Every facts entry has a `checked_by` that is a command, a file reference, a URL or a Jira comment. Every `done_when` entry is a command or a file reference, never a wish. Every role has required skills. Only the read-only `Explore` agent runs without an envelope, and it never counts as evidence (the owner's choice, spec open question 10). At most one envelope per role is open at a time in a checkout's records folder (`.orivilo/runs/`, all issues together), and each is bound to the one subagent that runs it by `agent_id`. The Agent call may not run in the background, set `isolation` or `model`, or use a `cwd` other than the envelope's worktree, which must be the session's own checkout. Every subagent ends with one JSON object in its contract: `implementer.v1`, `reviewer.v1` or `qa.v1`. A prose return is sent back. The schemas are written out in the ORV-81 spec.
3. **Roles.** product, ds-architect, designer, builder (Sonnet, TDD), a new `qa` agent (Opus), reviewer (Opus, fresh context) and release. `qa` runs the quality gate, takes light and dark screenshots of each changed story and walks every AC row with evidence. The reviewer keeps code review only. The models stay in the agent files.
4. **Acceptance.** Deterministic checks first (`scripts/quality-gate.mjs`, ORV-13). Then a fresh `qa` and a fresh `reviewer`, neither seeing the other. Proof must match the claim: a visual row needs a screenshot with a note of what was seen, or a computed style. A finding with no re-executable evidence is dropped. The implementer's own `verified` list never counts for a gate.
5. **Enforced by exit 2.** Hooks read the tool call as JSON on stdin, write a heartbeat line, and exit 2 to block. A hook never fails open: any error, a missing file or a missing interpreter also exits 2, and `pre-commit-gate` follows the same rule.
   - `envelope-guard` on Agent calls: schema, `checked_by` and `done_when` forms, `subagent_type` equal to the role, required skills per role, `write_set` shape, the Agent call fields (`run_in_background`, `isolation`, `model`, `cwd`), one open envelope per role, the rework limit.
   - `result-recorder` on SubagentStart, SubagentStop and after Agent calls: it binds the subagent to its envelope by `agent_id`; the report is valid JSON in its contract and comes from the agent type that contract belongs to, findings without evidence are dropped, the qa rules hold at record time (including a gate report from a real run, `stepsSource: "gate"`), and the `agent_id` is recorded. On SubagentStop, exit 2 sends the subagent itself back to fix its report, once; after the Agent call it can only refuse to record, and it closes the envelope. It records a quality-gate run only from the main session.
   - `owner-grant` on the owner's own messages: while an issue is escalated, a grant phrase together with the issue key, in a prompt whose `source` is `user` or in the owner's answer to a question form, is recorded with the exact quote and its time. Prompts from any other source grant nothing.
   - `write-guard`: the main session cannot write under `packages/` or `apps/`; no session can write the guard files (hooks, settings, `scripts/ovl/`, `.github/workflows/`) except a builder whose bound envelope lists the exact path; no session can write records, except PNG screenshots from `qa` or `designer` into their own task folder, by a tool or a Bash write.
   - `merge-guard` on every Bash command that could move `develop` or `main`: direct pushes (with `HEAD` resolved to the current branch), `gh api` merges, GraphQL merge or ref mutations, and commands that move `refs/remotes/origin/*` or change the `origin` remote are always blocked; `gh pr merge` into `develop` needs a `qa.v1` approve and a `reviewer.v1` approve on the PR head, green `gh pr checks`, a quality-gate report from a real run on that head with `ok: true` and no uncommitted changes, light and dark screenshots for each changed story, no changed file outside the issue's `write_set` union, and, when a guard file changes, the owner's approval record for that head (the owner's choice, spec open question 8). Only the release PR from `develop` merges into `main`. The checks run from a develop export taken at the SHA that `git ls-remote origin refs/heads/develop` reports, never from the branch under review or the local `origin/develop` ref.
   - `g3-check` on the Jira transition to G3 PR review, through any Atlassian MCP server: the same checks through `scripts/ovl/g3-check.mjs` from the same export, plus the merge into `develop`.
   - `ovl-doctor` at the start of each run probes every registered guard with a call built to be blocked, and stops the run if one wrote no heartbeat.
6. **Records.** `.orivilo/runs/<ISSUE>/<task_id>/` holds `envelope.json`, `agent.json`, `result.json` or `closed.json`, and for the qa step `qa.json` and its screenshots; `.orivilo/runs/<ISSUE>/gates/` holds the main session's quality-gate runs; `.orivilo/owner-approvals/` holds the owner's approvals of guard-file PRs, written from the owner's own terminal. Except those approvals and the owner's `close-envelope.mjs --owner` close, only hook processes and the `close-envelope.mjs` and `doctor.mjs` scripts write records, each with an exclusive create, so a record is written once and never edited. The folder is not committed; the G3 packet quotes it.
7. **Rework.** At most two rounds after the first verdict, counted per issue, not per task. A failed deterministic check from the main session counts as a round, and so does every builder envelope bound to a subagent after the first verdict, however it ended (a result, no valid report, or abandoned); only an envelope never bound (denied at the prompt, or left from before slice A3) does not. After round 2, the work stops and goes to the owner with both reports. The owner grants each further round by answering in chat, and the `owner-grant` hook writes a record quoting the owner's words (the owner's choice, spec open question 9). That record is weaker than one written from a terminal, and the spec's Honest limits say so.
8. **Lessons become rules** in the `release` agent and the `ovl` skill: squash from `git merge-base origin/develop HEAD`; compare the PR file list with `develop` before push; add a new Jira issue to the active sprint; confirm the remote branch is gone after a merge.
9. **In-session first.** Headless runs (`agent-stage.yml`, `agent-review.yml`) and Jira Automation come later, under their own ADR or an amendment to this one.

What we leave out from the two systems, for now: the stall watchdog (in-session, the owner sees a stall), `model_selection` in the envelope (the agent file sets the model), and an explorer contract (no story needs one yet).

## Consequences

- G3 can no longer pass on the main session's word. A merge needs a `qa.v1` approve, a `reviewer.v1` approve, a quality-gate report and green CI, all on the PR head, and the G3 move needs the merge into `develop` too.
- The hooks are the only merge barrier. GitHub branch protection and rulesets are not available on this repo's plan, so a merge through the GitHub web UI or another client is not guarded, and neither is a session started without these hooks. The G3 packet says so.
- Hooks run from the worktree's own copy. The merge checks run from `origin/develop`, but the `merge-guard` launcher and the other guards do not, so a builder allowed to edit a guard file can weaken them in its worktree. The owner's approval record and the G3 packet's list of changed guard files are the answer, not a technical barrier. The owner accepted this residual risk on 2026-10-23 (spec open question 13).
- The develop export runs with the checkout's own `node_modules`, and trusts the `origin` remote in `.git/config`; tampering with either is a stated limit, not a guarded path.
- A PR that adds the merge checks has no develop copy to be judged by, so the owner merges slice C1 by hand in the GitHub web UI after reading its G3 packet (the owner's choice, spec open question 11). The launcher has no fallback to the branch's copy.
- The hooks run in every Claude Code session in this repo, not only inside `/ovl`. A hook is registered only in the slice that ships the skill or agent that satisfies it.
- Each story costs more dispatches and more time. Two fresh reviews per round is the price of the four defects above not reaching staging.
- The guards depend on the hook input shape of the installed Claude Code version, in particular the `agent_id` field that tells a subagent from the main session. Each hook test uses recorded stdin, so an upgrade that changes the shape turns a test red. If the field is missing, the write guard fails closed.
- The write guard is a guard, not a sandbox. A subagent with Bash can still write outside its `write_set`. The merge guard catches that at the PR, which is later than we would like.
- A hook that silently stops firing would undo all of this. The heartbeat and `ovl-doctor` make that visible at the start of every run.
- The validator adds one dev dependency, `ajv`, chosen by the owner at G2 of ORV-81.
- ORV-13 has to merge before the merge guard can work, and its report has to carry the full `git.sha`, `git.dirty` and `stepsSource`.
- The owner's gates do not change: G1, G2 and G5 stay the owner's, and the POC delegation of G1 and G2 in ADR 0012 still holds.

## What this changes in earlier docs

- **AGENTS.md iron rule 3** ("Verify before handoff") gains: "A check counts for a gate only when a record proves it: the quality-gate report, a `qa.v1` approve, a `reviewer.v1` approve and green CI, all on the PR head. The implementer's own run is not evidence for G3." The command list stays.
- **ADR 0012, decision 2, G3 row.** "Two reviewer passes" now means one `qa.v1` approve and one `reviewer.v1` approve on the same head SHA. ADR 0012 is not rewritten; this ADR records the meaning.
- **`gate-packet` skill.** The G3 row must include the `qa.v1` and `reviewer.v1` reports, the quality-gate report, and the screenshot list. The G3 move goes through `g3-check`. The G4 walk on staging is done by `qa`.
- **`lead` agent.** Superseded by the `ovl` skill and removed. CLAUDE.md drops "The `lead` agent plans and dispatches" and lists `ovl` among the skills.
- **`reviewer` agent.** The AC walk, the quality-gate run and the staging check move to `qa`. The reviewer returns `reviewer.v1`.
- **`release` agent.** Gains the four lessons in decision 8.
- **`product`, `ds-architect`, `designer` and `builder` agents.** Each ends with one JSON report in its contract. The builder reports a blocker in `blocked_on` instead of to `lead`.
- **`docs/context/ai-team-skills.md`.** The model policy drops `lead` and adds `qa`.
- **`pre-commit-gate` hook.** Malformed input and errors exit 2 instead of 0.
- **`docs/context/master-plan.md`.** Phase 3 item 3 (a task schema and a verify step) is delivered by ORV-81.
