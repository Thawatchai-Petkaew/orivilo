## Context

ORV-126 makes a CI guidebook the phase 1 product. Two of its nodes need pictures:

- **`logo-mark`.** A round of four raster drafts of the mark, drawn inside a frame the harness has already decided: the logo type from `logo-type`'s rules, the given name, the core idea, and colour and typography when decided (ORV-126 node 14 and D8). The person picks one. A chosen draft is a direction, never the delivered logo file (ADR 0009 point 6: raster is concept only; the vector logo is a later story).
- **`touchpoints`.** Mockups that show the chosen direction on the applications a business of that kind uses, with the touchpoints picked by the TSIC business type (ORV-126 comment 10202; TSIC 2009 is the taxonomy of ORV-127). The node is outside the ORV-126 POC set today, so this ADR fixes only the provider and the call shape it will use.

ADR 0009 already pins a `logo-image` job to `google/gemini-nano-banana-2.1` and calls it "the only model on OpenRouter that returns images". No story has called it, recorded an eval set or checked its terms, and K-0045 and K-0046 both record that whether OpenRouter covers image models was not checked. ADR 0009 also says every call goes through the chat completions endpoint with `zdr: true` and `data_collection: "deny"` on each request. This ADR checks those statements against OpenRouter's current documentation and settles the provider before the logo image story starts.

## Decision

1. **Option A: image jobs call OpenRouter's Image API.**
   - The server calls `POST https://openrouter.ai/api/v1/images` (K-0072) with `fetch` and `OPENROUTER_API_KEY`, from the same server-only module as the text jobs (`packages/intent-engine/src/openrouter.ts` or a sibling file in that package, with `fetch` injected so the engine stays framework free). No SDK.
   - Not the chat completions endpoint and not the `openrouter:image_generation` server tool. A server tool that lets a chat model write the image prompt breaks the frame in decision 3.
   - This amends ADR 0009 decision 1 for image jobs only.
2. **Two image jobs, one pinned model each, both `google/gemini-nano-banana-2.1` to start.**

   | Job                                                              | Model                           | Price (K-0074, as of 2026-10-26, subject to change)                                                          |
   | ---------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------ |
   | `logo-image`: four logo drafts in the decided frame (ADR 0009)   | `google/gemini-nano-banana-2.1` | 0.00003 US dollars per output image token, that is 30 per million                                            |
   | `mockup-image` (new): touchpoint mockups of the chosen direction | `google/gemini-nano-banana-2.1` | Same output price; the OpenRouter record lists no input price line, Google's input price is 1.50 per million |
   - **Why this model, now that it is not the only one.** It has a single endpoint, so pinning the provider leaves no hidden routing; it takes up to 14 reference images and fixed resolution tiers, which the mockup job needs; its per-token price is the same on OpenRouter and at Google; Google's terms on output are read (K-0074, K-0075). It draws **one image per request** (`n` 1 to 1, K-0074), so a round of four drafts costs four requests. Output is billed per output image token (K-0074), so four one-image requests cost the same output as one call for four images would. Input is not: each request sends its own prompt (and, for mockups, its reference image), so input is paid once per request, at an OpenRouter input rate that the endpoint record does not list and that is therefore unknown (K-0074). The extra cost is that unknown input charge, plus call count and time. ADR 0009's reason ("the only model on OpenRouter that returns images") is replaced by this one.
   - **Exit test, as for `instant` in ADR 0009.** The logo image story records an eval set before the job ships: Latin names and Thai names in the four logo types, scored by a person for legible, correctly spelled text, for staying inside the frame (logo type, colours), and for whether four requests in one round give four distinct drafts. If the model fails the Thai part, `logo-image` either moves to the next candidate on the same API (`openai/gpt-image-2`, listed in K-0074; its endpoint record, `n` range and price are read and recorded as a knowledge entry first) after the same eval, or asks only for marks without lettering and leaves the name to the vector stage. The result is recorded as an addition to this ADR; no model is changed on a guess.

3. **The frame: only deterministic code writes the prompt.**
   - The prompt is a fixed template in code with a version (`promptVersion`), filled only from node records: `logo-type` (decided by its rules), `name` (given), `core-idea` (given, confirmed or skipped), `color` and `typography` when decided, and an optional concept note the person writes. Without a decided colour the template asks for one colour, black on white (ORV-126 node 14).
   - Because each request draws one image, the four requests of a logo round each add one line from a fixed list of four variation lines in the template (for example a different composition emphasis), so the round is varied by code, not by a model. The list is part of `promptVersion`.
   - Values go in as quoted data inside the template; the template says they are data. The concept note is capped in length and refused when it holds a brand name or an artist name (ADR 0009 point 6).
   - No model writes, rewrites or "enhances" the prompt, and the model never chooses the logo type, the name, the colours or the touchpoints.
   - No call is made while `logo-type` or `name` is missing (ORV-126 row 27). When a frame input is provisional, the drafts are provisional on it.
   - For `mockup-image`, the touchpoint list for a TSIC code comes from a deterministic map that the `touchpoints` story owns (a product contract, not decided here). The chosen logo draft goes in as one `input_reference` (the endpoint allows 0 to 14, K-0074), within ADR 0009 point 5's image bounds. One request per touchpoint.
   - **A touchpoint set larger than four runs as several rounds of up to four.** Code splits the map's list in its own order into consecutive rounds of at most four (a set of _t_ touchpoints is ceil(_t_ / 4) rounds), and each round is one unit against the `mockup-image` limit in decision 7, whatever its size. The round cap of four stays, so no per-round limit or cost row changes. Which touchpoints come first is the map's order, owned by the `touchpoints` story. A round the limiter refuses is not run; the rounds already run keep their images, and the person is told how many touchpoints are left and when the limit allows the next round. Worked example, the five agriculture touchpoints in ORV-126 comment 10202 (labels, sacks, farm signage, market stall, transport): ceil(5 / 4) = 2 rounds, the first of 4 requests and the second of 1, so 5 requests and 2 units. With 2 units an hour and 3 a day, the person can run the whole set within one hour, and that day has 3 - 2 = 1 unit left, enough for one more round of up to four. The set costs 5 x 3.36 = 16.80 US cents plus input (estimate basis in Consequences).
4. **The request and the answer.**
   - Request: `model` pinned, `prompt` from decision 3, `n: 1` on every request (the endpoint accepts no other value, K-0074), `resolution: "1K"`, `aspect_ratio` from the template (`1:1` for logos), `provider: { only: ["google-ai-studio"], allow_fallbacks: false }`. No `user`, no `session_id`, no `seed` and no `output_format` (unsupported), no `stream`.
   - A round is several requests: four for `logo-image`, one per touchpoint (at most four) for `mockup-image`. They run in parallel under one abort deadline. A request that fails is not retried; the round shows the images that came back, and says generation failed when none did.
   - **Cost estimate before each round.** Before the rate limit is consumed and before any request, the server computes the round's estimate with a pure function in `packages/intent-engine`: requests in the round x output tokens per image x the pinned output price. The price and the tokens per image are constants kept beside the pinned model id in `AI_MODELS`, each with its K entry and date: 0.00003 US dollars per output image token (K-0074, fact) and 1,120 tokens per 1K image (K-0074, inference from Google's figure, labelled as such in code). A logo round is 4 x 1,120 x 0.00003 = 0.1344 US dollars; a mockup round of _k_ touchpoints is _k_ x 0.0336. Input is not in the estimate, because its OpenRouter rate is unknown (K-0074), and the estimate says so. The estimate is shown to the person beside the action that runs the round, labelled as an estimate that excludes input; for a set split into several rounds (decision 3) the whole set is shown as rounds, images and estimate before the first round runs. It is stored on the round's record next to the `usage.cost` that comes back, so the gap between the two is visible. When ORV-121's per-workspace spend cap exists, the estimate is checked against the remaining cap and a round that would pass it is refused before any request. If the pinned model has no price constant, the round is refused (fail closed), so a model change without a price entry cannot run. The `designer` writes the estimate copy in Thai and English at the story's G2.
   - Data policy: the Image API has no per-request `zdr` or `data_collection` field (K-0073), so ADR 0009 point 4's per-request setting cannot be sent here. This ADR relies on the OpenRouter account settings: training off for every model, safety retention allowed for Google (ADR 0009 addition of 2026-10-23), and prompt logging off (K-0076 section 6.2). **That the account settings apply to image calls is an inference, not verified** (K-0073). The logo image story checks it on a live call with a developer key and records the result here before the job ships; until then it is owner question 1.
   - Each answer is parsed with zod before use: `data` holds exactly one item with `b64_json`; `media_type` and `usage` are optional (K-0072); `usage.cost`, when present, is a number. A missing `usage.cost` is stored as unknown, never as zero.
   - Each image is decoded on the server and allowed by its magic bytes as PNG, JPEG or WebP only, at most 8 MB. SVG and anything else is refused. The bytes are stored as returned; no re-encoding, so no new image library.
   - The answer does not name the model (K-0072). The pinned id, the single allowed provider and `allow_fallbacks: false` are what tie the image to the model, and the stored record says so.
   - Failure, timeout, a refused answer or no key: the request fails, with no retry under other settings and no other model (ADR 0009 point 3). The story sets the route's `maxDuration` and the abort below it from measured call times of four parallel requests.
5. **Every image is labelled a draft, with its trace.**
   - Each stored image carries: method `ai-draft`, job, model id, adapter version, `promptVersion`, the variation line index for logo drafts, the frame values it was drawn from, `usage.cost` or unknown, and the time. The record says the model was pinned by request, not named in the answer.
   - A logo draft shows `logo-mark.draftLabel` (ORV-126 D8) on every draft and on the chosen one.
   - A mockup shows a new key, `touchpoints.mockupLabel`, meaning: an AI mockup for previewing a direction; not a final design; the mark in it may differ from the chosen draft; not checked for trademarks or similarity; uniqueness and ownership not guaranteed. The `designer` writes the Thai and English copy in the locale catalog at the story's G2.
   - Nothing in the product says an image is trademark cleared, screened, unique, original, registrable or owned. Google states it may produce the same or similar content for others (K-0075); OpenRouter assigns no ownership itself and disclaims output quality (K-0076 sections 6.1 and 16.2). A trademark search is the person's step (ADR 0009 point 6).
6. **Storage.** Images go to a private Supabase Storage bucket under a random key in the workspace's path, never public, served through signed URLs that expire within 5 minutes after the authorization helper allows the read (ADR 0001, ADR 0002, ADR 0015 decision 11). How the server reaches Storage is decided in the logo image story's `tech.md`; this ADR adds no storage credential.
7. **Rate limits through the ORV-112 helper** (`createRateLimiter` and `LIMITS` in `packages/auth/src/rate-limit.ts`). The helper's `consume` takes one unit per call, so the unit is a round, and a round is a known number of image requests. Proposed numbers, decided at the logo image story's G1:

   | Limit          | Per    | Windows                                                                   | A unit is                                                                                                  | Image requests at most              |
   | -------------- | ------ | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------- |
   | `logo-image`   | person | 5 per day (from 00:00 Asia/Bangkok, `BANGKOK_OFFSET_SECONDS`), 2 per hour | one round: four requests of one image each                                                                 | 5 x 4 = 20 a day, 2 x 4 = 8 an hour |
   | `mockup-image` | person | 3 per day (same day), 2 per hour                                          | one round: one request of one image per touchpoint, at most 4; a larger set is several rounds (decision 3) | 3 x 4 = 12 a day, 2 x 4 = 8 an hour |
   - One `consume` per round, before any of its requests. Not one per image: a refusal partway would cut a round in half, and the helper has no weighted consume. A round the limiter refuses is not counted (the helper rolls it back). A round whose requests fail at the model is counted, because they may still be billed.
   - The store failing is `unavailable` and the round is refused (fail closed). Over the limit: 429, `Retry-After`, code `RATE_LIMITED` (ADR 0015 decision 4).
   - A round of fewer than four requests still takes one whole unit, so the request ceilings above are the most a person can send, not what a split set uses: the five-touchpoint set in decision 3 takes 2 units for 5 requests.
   - Both windows nest (the day's offset is a whole number of hours), so `assertNested` passes.
   - The per-key credit limit (ADR 0009 point 7) still applies. The per-workspace spend cap is ORV-121's: every image request writes one ORV-121 usage record (`ai_usage`, with the job, the pinned model id and `usage.cost` in millionths of a US dollar, or no amount when none was reported), and the cap sums those records, not the image records of decision 5. The `usage.cost` stored on each image in decision 5 stays, for the trace (`docs/specs/ORV-121/tech.md` §2).

## Consequences

- **Cost.** An estimate, not grounds for a decision. Basis: Google's figure of 0.0336 US dollars (3.36 US cents) per 1K image (K-0074, fact), applied to OpenRouter on the strength of the equal per-token price (K-0074, fact) and the inference that the model emits the same tokens per image there (K-0074, below 0.7). Before OpenRouter's fee on credits, which was not read. Prices as of 2026-10-26; they change.

  | Unit                                                    | Requests (one image each) | Arithmetic, US cents  | Cost, US cents |
  | ------------------------------------------------------- | ------------------------- | --------------------- | -------------- |
  | One logo draft                                          | 1                         | 1 x 3.36              | 3.36           |
  | One logo round                                          | 4                         | 4 x 3.36              | 13.44          |
  | One mockup round (four touchpoints, one reference each) | 4                         | 4 x 3.36, plus input  | 13.44 + input  |
  | Five touchpoints (decision 3): two mockup rounds        | 4 + 1 = 5                 | 5 x 3.36, plus input  | 16.80 + input  |
  | One run: a logo round and a mockup round                | 8                         | 8 x 3.36, plus input  | 26.88 + input  |
  | Most one person can spend in a day under decision 7     | 20 + 12 = 32              | 32 x 3.36, plus input | 107.52 + input |

  Input: the OpenRouter endpoint record has no input price line (K-0074), so its input charge is unknown. At Google's 1.50 US dollars per million input tokens, input would need about 6,667 tokens (0.01 / 0.0000015) to add one cent to a request. ORV-126 D8 estimated 3.9 cents an image from an assumed 1,300 tokens (1,300 x 0.00003 dollars); Google's equivalence implies about 1,120 (0.0336 / 0.00003). The stored `usage.cost` replaces every estimate once calls run; the pre-run estimate in decision 4 uses the same 1,120 tokens and is corrected in code, with its K entry, when recorded costs show a different count. At 2K an image is 5.04 cents on Google's figure.

- **Four requests per round.** Four times the calls, four times the chances of one failing, and a round's time is that of its slowest request. Parallel requests under one deadline keep the wait near one call; a partial round is shown as such.
- **Data policy is set on the account, not the request, and is not yet proven for images.** If someone turns training or prompt logging back on in the OpenRouter account, image calls may follow it silently. The account settings are part of the release checklist for each environment, and the live check in decision 4 is recorded.
- **Processors for PDPA** stay as ADR 0009 named them (OpenRouter and Google). The privacy notice already has to say Google may keep images and logo prompts briefly for safety monitoring and never trains on them; it now names mockups too. That sentence rests on Google's Paid Services rule, which is not yet confirmed to apply through OpenRouter (K-0075; owner question 3).
- **Thai lettering is unproven.** Until the exit test in decision 2 passes, the story may only claim what the eval shows.
- **A second request shape** in the OpenRouter module, with its own recorded fixtures. Tests never call a model (ADR 0009 point 8).
- **Low lock-in.** Another image model on OpenRouter is a pinned-id change with an impact note, a knowledge entry for its endpoint record, and the same eval, not a new adapter. A model that accepts `n` above 1 would still be called the same way unless a later addition here changes it.

## For the owner to confirm

Each point below is an inference in the knowledge entries (confidence below 0.7) or a setting only the owner can make. **Answered:** the owner accepted all five on 2026-10-26 (ORV-126 comment 10205), so condition 1 of the Status line is met. The acceptances carry their own conditions: no image job ships before the live data check in decision 4 is recorded (question 1), prompt logging stays off in every environment's release checklist (question 2), and the privacy notice and draft labels state the gap on Google's terms through OpenRouter (question 3).

1. **Data policy on image calls (K-0073).** The Image API takes no `zdr` or `data_collection`. Do you accept relying on the OpenRouter account settings (training off, Google safety retention allowed, prompt logging off) until the live check in decision 4 confirms they apply to image calls, with no image job shipping before that check is recorded?
2. **Prompt logging off (K-0076 section 6.2).** Turning prompt logging on grants OpenRouter a perpetual licence to the logged prompts and images. Do you confirm it stays off in every environment, as part of the release checklist?
3. **Google's terms through OpenRouter (K-0075).** Whether Google's Gemini API terms, and its Paid Services rule (no training, limited logging), govern calls made through OpenRouter is not confirmed. Do you accept the privacy notice and the draft labels resting on them as the expected terms, with the gap stated, or do you want this settled with OpenRouter first?
4. **Four requests per round (K-0074).** Do you accept that a logo round is four one-image requests, with the rate limit counted per round as in decision 7? (A touchpoint set larger than four is split into rounds, decision 3.)
5. **Cost (decision 7, Consequences).** Do you accept the proposed limits knowing the per-person daily ceiling is about 1.08 US dollars before OpenRouter's fee and input, on an estimate that the first recorded `usage.cost` replaces?

## Not chosen

- **B. Google's Gemini API directly.** Without OpenRouter's fee and with Google's terms applying without a middle party, but it adds a second account and key, and ties the job to one vendor's API shape. The owner chose one account for every model (ADR 0009).
- **C. A media aggregator such as fal or Replicate.** A third account and key beside OpenRouter, and terms not read. It would make sense only for a model OpenRouter does not serve; none is needed now.
- **The chat completions endpoint with image output.** ADR 0009's original path. The dedicated Image API is the documented one for image generation, takes resolution tiers and reference images, and reports cost per call (K-0072).
- **The `openrouter:image_generation` server tool.** A chat model writes the prompt, so the frame would not be enforced by code.
- **A model step that rewrites or enhances the prompt** (as Wireflow's Enhance Prompt node or Higgsfield's prompt layer do, K-0045, K-0046). It would let a model change the frame the harness decided.
- **One `consume` per image.** The helper has no weighted consume, and a refusal after two of four drafts would leave a half round.
- **Compositing the vector logo onto blank mockup scenes by code.** It would keep the mark exact, but there is no vector logo yet and it needs an image library. It is the expected follow-up once the vector logo story ships.
