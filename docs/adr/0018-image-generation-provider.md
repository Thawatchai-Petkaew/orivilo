# ADR 0018: Logo drafts and touchpoint mockups through OpenRouter's Image API

- Status: proposed. It becomes accepted when (1) a `research` knowledge entry records the external facts this ADR rests on (the OpenRouter Image API shape and its missing data-policy fields, the endpoint prices, Google's and OpenRouter's terms on generated output; see "Facts and how they were checked"), and (2) the logo image story (ORV-126 decision D8) passes its G1 with these decisions. On acceptance, ADR 0009's Status line gains a pointer here; the rest of ADR 0009 is not edited.
- Date: 2026-10-26
- Decided by: the owner chose AI image drafts of the logo inside the harness's decided frame, with an architect ADR on the provider as a dependency (ORV-126 comment 10198, decision D8), and asked for application mockups whose touchpoints follow the TSIC business type (ORV-126 comment 10202). The `architect` role wrote this ADR (task `ORV-126-arch-image-provider-1`).
- Builds on: ADR 0001 (Supabase Storage, private buckets, signed URLs), ADR 0002 (server-only data access), ADR 0009 (AI through OpenRouter, one pinned model per job), ADR 0015 (AI controls, rate limits, uploads). None is superseded.
- Amends: ADR 0009 decision 1 for image jobs only (they call OpenRouter's Image API, not chat completions) and the reason given for the `logo-image` row (decision 2 below). Every other part of ADR 0009 stands and applies to the image jobs.

## Context

ORV-126 makes a CI guidebook the phase 1 product. Two of its nodes need pictures:

- **`logo-mark`.** A round of four raster drafts of the mark, drawn inside a frame the harness has already decided: the logo type from `logo-type`'s rules, the given name, the core idea, and colour and typography when decided (ORV-126 node 14 and D8). The person picks one. A chosen draft is a direction, never the delivered logo file (ADR 0009 point 6: raster is concept only; the vector logo is a later story).
- **`touchpoints`.** Mockups that show the chosen direction on the applications a business of that kind uses, with the touchpoints picked by the TSIC business type (ORV-126 comment 10202; TSIC 2009 is the taxonomy of ORV-127). The node is outside the ORV-126 POC set today, so this ADR fixes only the provider and the call shape it will use.

ADR 0009 already pins a `logo-image` job to `google/gemini-nano-banana-2.1` and calls it "the only model on OpenRouter that returns images". No story has called it, recorded an eval set or checked its terms, and K-0045 and K-0046 both record that whether OpenRouter covers image models was not checked. ADR 0009 also says every call goes through the chat completions endpoint with `zdr: true` and `data_collection: "deny"` on each request. This ADR checks those statements against OpenRouter's current documentation and settles the provider before the logo image story starts.

## Decision

1. **Option A: image jobs call OpenRouter's Image API.**
   - The server calls `POST https://openrouter.ai/api/v1/images` with `fetch` and `OPENROUTER_API_KEY`, from the same server-only module as the text jobs (`packages/intent-engine/src/openrouter.ts` or a sibling file in that package, with `fetch` injected so the engine stays framework free). No SDK.
   - Not the chat completions endpoint and not the `openrouter:image_generation` server tool. The server tool lets a chat model write the image prompt, which breaks the frame in decision 3.
   - This amends ADR 0009 decision 1 for image jobs only.
2. **Two image jobs, one pinned model each, both `google/gemini-nano-banana-2.1` to start.**

   | Job                                                              | Model                           | Price (OpenRouter endpoint record, 2026-10-26)         |
   | ---------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------ |
   | `logo-image`: four logo drafts in the decided frame (ADR 0009)   | `google/gemini-nano-banana-2.1` | 30 US dollars per million output image tokens          |
   | `mockup-image` (new): touchpoint mockups of the chosen direction | `google/gemini-nano-banana-2.1` | Same; the reference image is input at 1.50 per million |
   - **Why this model, now that it is not the only one.** It has a single endpoint, so pinning the provider leaves no hidden routing; it takes `n`, `input_references` and fixed resolution tiers, which both jobs need; its price is published by OpenRouter and by Google with the same figure; Google's terms on output are read. ADR 0009's reason ("the only model on OpenRouter that returns images") is replaced by this one.
   - **Exit test, as for `instant` in ADR 0009.** The logo image story records an eval set before the job ships: Latin names and Thai names in the four logo types, scored by a person for legible, correctly spelled text and for staying inside the frame (logo type, colours). If the model fails the Thai part, `logo-image` either moves to the next candidate on the same API (`openai/gpt-image-2`, same per-token output price) after the same eval, or asks only for marks without lettering and leaves the name to the vector stage. The result is recorded as an addition to this ADR; no model is changed on a guess.

3. **The frame: only deterministic code writes the prompt.**
   - The prompt is a fixed template in code with a version (`promptVersion`), filled only from node records: `logo-type` (decided by its rules), `name` (given), `core-idea` (given, confirmed or skipped), `color` and `typography` when decided, and an optional concept note the person writes. Without a decided colour the template asks for one colour, black on white (ORV-126 node 14).
   - Values go in as quoted data inside the template; the template says they are data. The concept note is capped in length and refused when it holds a brand name or an artist name (ADR 0009 point 6).
   - No model writes, rewrites or "enhances" the prompt, and the model never chooses the logo type, the name, the colours or the touchpoints.
   - No call is made while `logo-type` or `name` is missing (ORV-126 row 27). When a frame input is provisional, the drafts are provisional on it.
   - For `mockup-image`, the touchpoint list for a TSIC code comes from a deterministic map that the `touchpoints` story owns (a product contract, not decided here). The chosen logo draft goes in as one `input_reference`, within ADR 0009 point 5's image bounds. One request per touchpoint.
4. **The request and the answer.**
   - Request: `model` pinned, `prompt` from decision 3, `n: 4` for `logo-image` (1 per touchpoint for `mockup-image`), `resolution: "1K"`, `aspect_ratio` from the template (`1:1` for logos), `provider: { only: ["google-ai-studio"], allow_fallbacks: false }`. No `user`, no `session_id`, no `seed` (unsupported), no `stream`.
   - Data policy: the Image API has no per-request `zdr` or `data_collection` field (Facts), so ADR 0009 point 4's per-request setting cannot be sent here. The account settings carry it: training off for every model, and safety retention allowed for Google (ADR 0009 addition of 2026-10-23). The logo image story checks on a live call, with a developer key, that the account setting applies to the Image API, and records the result here before the job ships.
   - The answer is parsed with zod before use: `data` holds 1 to `n` items, each with `b64_json`; `usage.cost` is a number. Fewer images than asked is accepted and recorded.
   - Each image is decoded on the server and allowed by its magic bytes as PNG, JPEG or WebP only, at most 8 MB. SVG and anything else is refused. The bytes are stored as returned; no re-encoding, so no new image library.
   - The answer does not name the model (Facts). The pinned id, the single allowed provider and `allow_fallbacks: false` are what tie the image to the model, and the stored record says so.
   - Failure, timeout, a refused answer or no key: the job says generation failed, with no retry under other settings and no other model (ADR 0009 point 3). The story sets the route's `maxDuration` and an abort below it from measured call times.
5. **Every image is labelled a draft, with its trace.**
   - Each stored image carries: method `ai-draft`, job, model id, adapter version, `promptVersion`, the frame values it was drawn from, `usage.cost`, and the time. The record says the model was pinned by request, not named in the answer.
   - A logo draft shows `logo-mark.draftLabel` (ORV-126 D8) on every draft and on the chosen one.
   - A mockup shows a new key, `touchpoints.mockupLabel`, meaning: an AI mockup for previewing a direction; not a final design; the mark in it may differ from the chosen draft; not checked for trademarks or similarity; uniqueness and ownership not guaranteed. The `designer` writes the Thai and English copy in the locale catalog at the story's G2.
   - Nothing in the product says an image is trademark cleared, screened, unique, original, registrable or owned. Google states it may produce the same or similar content for others (Facts). A trademark search is the person's step (ADR 0009 point 6).
6. **Storage.** Images go to a private Supabase Storage bucket under a random key in the workspace's path, never public, served through signed URLs that expire within 5 minutes after the authorization helper allows the read (ADR 0001, ADR 0002, ADR 0015 decision 11). How the server reaches Storage is decided in the logo image story's `tech.md`; this ADR adds no storage credential.
7. **Rate limits through the ORV-112 helper** (`createRateLimiter` and `LIMITS` in `packages/auth/src/rate-limit.ts`). Proposed numbers, decided at the logo image story's G1:

   | Limit          | Per    | Windows                                                                   | A unit is                           |
   | -------------- | ------ | ------------------------------------------------------------------------- | ----------------------------------- |
   | `logo-image`   | person | 5 per day (from 00:00 Asia/Bangkok, `BANGKOK_OFFSET_SECONDS`), 2 per hour | one round of four drafts            |
   | `mockup-image` | person | 3 per day (same day), 2 per hour                                          | one round of up to four touchpoints |
   - One `consume` per round, before any model call. A round the limiter refuses is not counted (the helper rolls it back). A round that fails at the model is counted, because it may still be billed.
   - The store failing is `unavailable` and the round is refused (fail closed). Over the limit: 429, `Retry-After`, code `RATE_LIMITED` (ADR 0015 decision 4).
   - Both windows nest (the day's offset is a whole number of hours), so `assertNested` passes.
   - The per-key credit limit (ADR 0009 point 7) still applies, and the per-workspace spend cap is ORV-121, which reads the `usage.cost` stored in decision 5.

## Consequences

- **Cost** (1K images, the Google figure of 3.36 US cents, before OpenRouter's fee on credits, which is not checked here):

  | Unit                                                    | Images | Cost, US cents |
  | ------------------------------------------------------- | ------ | -------------- |
  | One logo image                                          | 1      | about 3.4      |
  | One logo round                                          | 4      | about 13.4     |
  | One mockup round (four touchpoints, one reference each) | 4      | about 13.6     |
  | One run: a logo round and a mockup round                | 8      | about 27       |
  | Most one person can spend in a day under decision 7     | 32     | about 108      |

  Prompt text and the reference image add well under 0.1 cent a call at 1.50 per million input tokens. ORV-126 D8 estimated 4 cents an image from an assumed 1,300 tokens; Google's own equivalence gives about 1,120. The stored `usage.cost` replaces both estimates once calls run. At 2K a mockup costs about 5 cents.

- **Data policy is set on the account, not the request.** If someone turns training back on in the OpenRouter account, image calls follow it silently. The account settings are part of the release checklist for each environment, and the live check in decision 4 is recorded.
- **Processors for PDPA** stay as ADR 0009 named them (OpenRouter and Google). The privacy notice already has to say Google may keep images and logo prompts briefly for safety monitoring and never trains on them; it now names mockups too.
- **Thai lettering is unproven.** Until the exit test in decision 2 passes, the story may only claim what the eval shows.
- **A second request shape** in the OpenRouter module, with its own recorded fixtures. Tests never call a model (ADR 0009 point 8).
- **Low lock-in.** Another image model on OpenRouter is a pinned-id change with an impact note and the same eval, not a new adapter.

## Impact list

- `packages/intent-engine`: an image call beside `openRouterComplete` with its own URL constant; `AI_MODELS` gains `mockup-image`; the two frame prompt builders with `promptVersion`; the zod answer schema and the magic-byte check; recorded fixtures.
- `packages/auth`: `LIMITS` gains `logo-image` and `mockup-image`; `limits.test.ts` pins them.
- `packages/db`: a table for image draft records (workspace id, job, model id, adapter version, prompt version, frame, storage key, media type, cost, time), each column tagged by classification (`.claude/rules/security.md` rule 11); a migration.
- `apps/web`: the server actions that run a round (session, authorization helper, rate limit, model call, storage, record); the signed-URL read; locale keys `logo-mark.draftLabel` and `touchpoints.mockupLabel` in Thai and English; the route's `maxDuration`.
- `.claude/rules/security.md` rule 6: the two new limits, once decided.
- ADR 0009: a pointer on its Status line when this ADR is accepted. ADR 0015 decision 3: the AI control rows now cover two more jobs, each with its tests.
- Environment variables: `OPENROUTER_API_KEY` only, unchanged. No new AI key. Any storage credential is the logo image story's decision. OpenRouter account privacy settings per environment (training off, Google safety retention allowed) are configuration, not variables.
- Spec ORV-126 D8: its cost estimate is refined by this ADR's figures; its rate limit proposal is carried into decision 7.

## Not chosen

- **B. Google's Gemini API directly.** About OpenRouter's fee cheaper and Google's terms apply without a middle party, but it adds a second account and key, and ties the job to one vendor's API shape. The owner chose one account for every model (ADR 0009).
- **C. A media aggregator such as fal or Replicate.** A third account and key beside OpenRouter, a higher listed price for the same model family, and terms not read. It would make sense only for a model OpenRouter does not serve; none is needed now.
- **The chat completions endpoint with image output.** ADR 0009's original path. The dedicated Image API is the documented one for image generation, takes `n`, resolution tiers and reference images, and reports cost per call.
- **The `openrouter:image_generation` server tool.** A chat model writes the prompt, so the frame would not be enforced by code.
- **A model step that rewrites or enhances the prompt** (as Wireflow's Enhance Prompt node or Higgsfield's prompt layer do, K-0045, K-0046). It would let a model change the frame the harness decided.
- **Compositing the vector logo onto blank mockup scenes by code.** It would keep the mark exact, but there is no vector logo yet and it needs an image library. It is the expected follow-up once the vector logo story ships.

Confirmation: not confirmed yet; follow-up: the logo image story under ORV-126 decision D8 (lane L, key created after ORV-126 G1). It adds recorded-response tests in `packages/intent-engine` that fail `pnpm test` when the request is not pinned to `google/gemini-nano-banana-2.1` with `only: ["google-ai-studio"]` and `allow_fallbacks: false`, when the body carries a `user` or `session_id`, when the prompt holds anything outside the frame records or is built while `logo-type` or `name` is missing, when a non-PNG, JPEG or WebP answer or one over 8 MB is accepted, and when a stored draft lacks its label key, model id or `promptVersion`; `limits.test.ts` pinning the `logo-image` and `mockup-image` windows; the Thai eval set result recorded as an addition here; and the live check that the account's data settings apply to the Image API. The `security` role reviews that story (ADR 0015 decision 2: a new model call and prompt). Until then, no screen may say ORIVILO draws logos or mockups.
