## Why

The catalog is what an agent reads before composing UI (handoff §15, ADR 0003 item 4). Every stable entry carries a contract and rules, but `examples` is empty on all of them, so an agent that follows the workflow "read the contract and one example, then compose" has nothing to read and falls back to guessing from the component's features. ADR 0003 item 5 organises the catalog in three tiers, each with page examples, and DESIGN.md §12 promised the bento example page with this story. This story lands one page example per tier, built only from the public components, points every stable entry at the example that uses it, and makes `check-catalog` verify that those paths and the coverage rows are real.

## Story

As an agent or a person composing a Studio screen or a generated page, I want one full page example per catalog tier in Storybook, composed only from the public components with Thai and Latin fixture content, so that I can read how the components fit together in a real layout before composing, and so that `coverage.md` states which tiers have an example and which do not.

## Rules and bounds

- **Examples are reference material, not public API.** `src/examples/` is not exported from the package index; the catalog points at the files so an agent reads them. Nothing in an example is imported by a component.
- **Composition only.** An example uses the public components through `../components/index` (the package's `@orivilo/design-system` entry from outside) and Tailwind layout classes. It adds no component, no token and no recipe. A page-level pattern that would deserve a component (page header, empty state, metric) stays inline here and is still `none` in `coverage.md`.
- **Fixture content.** Thai and Latin, the long Thai name without spaces, and a missing value from `src/components/fixtures.ts`. Metrics are computed from the rows on the page, never typed in. The story description says the data is fixture data.
- **Honesty.** The landing page shows no testimonial, logo cloud, rating, user count, discount or pricing, because none has data. The step that interprets a brief is labelled rule-based (AGENTS.md rule 4).
- **One primary per view.** A page has one `primary` Button; a dialog is its own view and has its own.
- **Copy.** Thai, sentence case, no middot, no em dash; actions named after the outcome.
- **Titles.** `Examples/<Tier>: <Name>` so the ids read `examples-<tier>-<name>` and `check-catalog` can tell examples from component stories.
- **Recipes for pages.** A page example proves its recipes with one page per story (`Under`), not the six-cell Matrix: a page carries landmarks (navigation, regions, a banner), and six copies in one document make them non-unique, which axe reports as a violation. The Matrix stays the tool for components, which carry none.
- **Marketing status.** The landing example is `draft` in `coverage.md`, because the tier's own sections do not exist and the page is composed from Base and Application components. It becomes `stable` when a marketing section lands with its own entry.

## Out of scope

The reference screen (E2-8), marketing section components (Hero, Features, Pricing and the rest stay `none`), Page header, Empty state and Metric as components, Storybook docs pages, visual regression baselines, the canvas example page (E4-8), the agent composition exercise (E2-14).
