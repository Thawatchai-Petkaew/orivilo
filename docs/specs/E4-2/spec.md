## Why

ADR 0004 takes React Flow for the canvas behaviour and keeps every visual value in our tokens; E4-1 landed those tokens, the port shapes, the edge dashes and the status words. Nothing on the board exists as a component yet, and E4-3 (groups, toolbar, menus) and E4-4 (library, inspector, missing inputs) build on the four pieces every board has: the board, a node, a port and an edge. This story lands those four with every catalog state as a story, the keyboard paths the catalog promises, and the command registry as the only source of keys.

## Story

As the Studio implementer and as E4-3's and E4-4's base, I want `CanvasBoard`, `CanvasNode`, `NodePort` and `CanvasEdge` in the design-system package on React Flow, styled only through the `board`, `node`, `port` and `edge` component tokens, with typed ports that accept only their own kind, edges that say what they mean, keyboard connect, nudge and delete, and the registry's E4-2 commands wired, so that the board composes from the contract like every other component and nothing on it is a React Flow default.

## Rules and bounds

- **Behaviour borrowed, visuals ours (ADR 0004).** Viewport, drag, selection, connection, focus order, Enter and Space to select, Escape to deselect, Delete to remove come from React Flow. Every colour, width, radius, dash and font is a `--cmp-*` or `--ds-*` property in `recipes.css`; the base stylesheet is loaded for layout and every `--xy-*` it reads is set from a token on `.ds-board`. No React Flow component other than `ReactFlow`, `Handle`, `Background`, `EdgeLabelRenderer` and the provider is used.
- **Controlled graph.** The board takes `graph` and calls `onChange(next)` with the whole next graph for every change (position, selection, connection, deletion, meaning), so the shell owns the document and history. Node `data` stays plain data (title, kind, summary, status, error, missing, collapsed, ports); rich body content comes through `renderBody` so a board can be saved as JSON.
- **The registry is the only key source.** `scripts/build-commands.ts` writes `src/commands/generated.ts` from the YAML; the board matches events against the generated shortcuts for the scopes that apply (node, edge, selection, board, app). A command the board cannot complete itself is handed to `onCommand`. Nothing in the components spells a key.
- **Meaning never moves (DESIGN.md §8).** Selection is violet (`canvas.selection`), focus is the ink ring (never removed, also on edges), missing inputs are lime because the node asks the engine, error is danger, the three statuses are their own words and colours. Kind is shape first; meaning is dash first.
- **Honest UI.** Nothing on the board generates anything. The status line shows what the board did (connected, moved, removed) or the `status` the shell passes. A missing-inputs row lists words; asking for them is E4-4.
- **Studio chrome.** The board is wrapped by the consumer in the neutral boundary (the app does this at the root); the Matrix story proves nothing in the canvas groups changes under a customer profile.
- **Not in this story.** The node resizer and its focusable handles (custom width comes from `node.width` today), groups, toolbar, minimap, controls, context menu, command menu (E4-3), library, inspector, missing-input prompts (E4-4), undo history and node creation UI (shell, reached through `onCommand`), present-mode commands (E4-7). The catalog's a11y line about resize handles stays as the contract for the resizer story.
