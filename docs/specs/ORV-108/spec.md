# ORV-108: Team update before product work

## Why

The owner wants one last team-tooling round before product work starts, so that product stories get an architect, a security reviewer and a researcher, named standards to be checked against, and a gate that catches leaked secrets and unsafe code. One gap from the ORV-81 loop is closed at the same time: a stuck envelope today needs the owner at a terminal (ORV-108 comment 10157 records the scope and the form addition).

Version 2 adds three sources the owner recorded on ORV-108, and nothing else:

- the allkons survey and the decisions on open questions 1 to 9 (comment 10158);
- the owner's visual-quality decision (comment 10159), which takes up L-0017, L-0018 and L-0019 from ORV-107, where the owner found three visual defects by eye after the plays and an approve passed them;
- the Camp Vibe survey (the ORV-108 comment after 10158).

Seven deliverables, nothing more:

1. Three new roles: `architect`, `security`, `research` (slice A).
2. Visual quality in the loop: a look change in rework goes through the designer with a screenshot; the designer signs off the changed stories before qa; shared play helpers measure what is rendered; the owner sees the screenshots before review (slice A).
3. `.claude/settings.json` denies reading `.env*` files by the forms agents use (slice A).
4. One ADR that names the standards (OWASP ASVS Level 2, OWASP Top 10 for LLM Applications, WCAG 2.2 AA) and the required controls (AI, performance budgets, observability, the API error envelope, PDPA masking), and says what is not done yet. Every new ADR carries a `Confirmation:` line (slice B).
5. Gate additions: a secret scan and a code scan that start in report mode, the audit failing on high or critical, commitlint in the gate with a commit-msg hook, and a Thai jargon list in the copy check, in `pnpm quality-gate` and in CI, with no new paid service. Security rules for 404-not-403, uploads, field classification tags and money (slice B).
6. The owner closes a stuck envelope by clicking an option in a question form, recorded by a hook, as the rework grant works in ADR 0014. The terminal `--owner` path stays as the fallback (slice C).
7. Web security headers and a Report-Only nonce Content Security Policy for `apps/web`, pinned by tests (slice D).

**Frame (L-0012).** Every check here is a **guard rail for agents that follow the rules, not a boundary.**

- `owner-close` (new hook) judges an `AskUserQuestion` call. The main session writes the question and the options, so the owner's click is the only proof, as ADR 0014 says for the grant. A session that sets out to defeat it can still write `closed.json` by a Bash call that hides `.orivilo` (ORV-96).
- The secret scan and the code scan are pattern rules over files. Nothing outside the session enforces them: GitHub rulesets return HTTP 403 on this plan (ORV-97 comment 10110), so a red CI check does not stop a merge made in the GitHub web UI. `merge-guard` stops an agent merge only through the gate record and `gh pr checks`. In report mode they block nothing at all.
- The `.env*` deny rules are permission rules that Claude Code matches against a tool call's text. A Bash command in a form the rules do not name (`node -e`, `awk`, `cp`) reads the file. Nothing outside the session holds the secret back; the boundary for secrets is that they live in Vercel and in the owner's local files, never in the repo.
- The commit-msg hook runs on the local machine only, and `git commit --no-verify` skips it. The gate step and CI read the same commits again.
- The order "designer sign-off before qa" lives in the `ovl` skill text. No hook checks it, and `merge-check` does not read the sign-off.

The forms a rule-following agent uses, which the guards must catch:

- `node scripts/ovl/close-envelope.mjs <task_id>`, from the main session (`ovl` skill, section 4).
- The close form, from the main session (new, this spec).
- `node scripts/ovl/close-envelope.mjs <task_id> --owner`, from the owner's terminal (unchanged).
- `pnpm quality-gate` and the CI `run:` lines, the only ways the scans and the commit check run.
- `git commit -m "<message>"`, from a builder (agent file, step 6) and from the main session (`ovl` skill, section 4).
- A `Read` of a `.env*` path, and `cat`, `head`, `tail`, `less`, `more`, `grep` or `source` naming one. No skill, agent file or `AGENTS.md` reads a `.env*` file; these are the forms an agent reaches for when it looks for a value.

## Story

As the owner, I want the team to have an architect, a security reviewer and a researcher, checked against named standards and required controls, behind a gate that catches leaked secrets, unsafe code and malformed commits. I want a designer to look at every rendered change before qa and to show me the screenshots, so I stop finding visual defects by eye after an approve. I also want to close a stuck envelope with one click, and the app to send standard security headers. Then product work starts on a team I trust, and I do not need a terminal for a routine unblock.

## Visual quality (slice A)

From the owner's decision (comment 10159) and lessons L-0017, L-0018 and L-0019. It applies to a PR that changes a rendered component: a changed `*.stories.tsx`, or a changed file under `packages/design-system/src/components/` or `packages/design-system/src/recipes/`.

**Designer visual sign-off.** A `designer` envelope with `report_contract` `reviewer.v1` and an empty `write_set` judges the look of one head. For each story under each changed `*.stories.tsx` title it takes eight screenshots: the narrowest and the widest container the story allows, Thai and English, light and dark. It saves them under the main checkout's `.orivilo/runs/<ISSUE>/<task_id>/screenshots/`, opens each with Read, and reports `approve` or `request_changes`. `checks_run` lists every PNG path (the contact sheet); each rejected look is a finding with `screenshot` evidence. It edits no file.

**Order in step 6.** Round 0: the sign-off goes first. When it returns, the main session posts the contact sheet on the Jira issue (the absolute PNG paths), and then dispatches `reviewer` (and `security` when its cases hold) on the same head. `qa` is dispatched only on a head that has both a sign-off approve and a reviewer approve. Round 1 or more: the reviewer re-check first (L-0014), then a new sign-off on the head the re-check approved, then `qa`. A sign-off's `request_changes` is a verdict: the fix goes to `builder` with `rework_of` (the recorder already counts a designer `reviewer.v1` result).

**A look change in rework.** A finding or an owner comment whose fix changes how something looks goes to `designer` first. The designer records the change in `docs/specs/<KEY>/design.md` and screenshots it rendered, with the proposed CSS injected into the story, light and dark, before any builder envelope. The builder envelope then carries that design.md section in `context_pointers` and one fact per screenshot (`checked_by` `test -f <absolute path>`). A grant form for that round (`ovl` section 3) names the screenshot paths in its question.

**The owner sees the screenshots.** The contact sheet is on the Jira issue before the reviewer is dispatched, and the G3 packet lists the latest sign-off's PNG paths for the merged head. The loop does not wait for the owner to look (open question 10).

**Shared play helpers.** `packages/design-system/src/testing/visual-asserts.ts`:

- `expectEdgeInk(el, side, px)` reads the rendered pixels across one edge of `el` (a pixel column or row through the edge, counted in device pixels and divided by `devicePixelRatio`) and asserts the ink width. It reads pixels, not computed style, so a border plus an outline drawn as one edge counts as two.
- `expectSameHeight(el, ...siblings)` asserts that chips, tags or controls in one row have the same rendered height within 0.5 px.
- `expectNoGlyphClip(el)` asserts that, for each text node under an ancestor whose overflow is not `visible`, every `Range` client rect lies inside that ancestor's padding box and inside its rounded corners (a point-in-rounded-rectangle test on the computed radii). Stories that use it carry a Thai sample with stacked marks, `ปิ่นโต้` and `โลโก้`, from `src/components/fixtures.ts`.

`CanvasChat.stories.tsx` adopts them in place of its local height and scroll asserts in `expectGoneChip`. `.claude/rules/testing.md` gains the L-0018 rule line, and `builder.md` step 4 gains the pixel-column sentence.

**Report mode.** A new scanner lands in report mode: with `--report` it prints each finding (file and rule) and the line `report mode: <n> findings, not blocking`, and exits 0. Without `--report`, any finding exits 1. The mode lives in the command lines of `scripts/quality-gate.mjs` and `.github/workflows/ci.yml`, both guard files, so the switch to blocking is one guard-file PR that removes `--report` from both, with the owner approval record (open question 14). The commit check and the jargon list are format rules inside existing checks, not new scanners, so they block from the start.

**The commit check.** `commitlint.config.mjs` extends `@commitlint/config-conventional` and adds one rule: the header names an issue key `ORV-<n>` (in the scope or the subject), as builder step 6 asks. It also turns `subject-case` off and raises `header-max-length` to 160, because this repo's subjects carry file and identifier names and long issue titles (every recent commit passes; four old pre-ORV commits do not). `pnpm lint:commits` runs `scripts/check-commits.mjs`, which lints each commit of `git log --no-merges origin/develop..HEAD`. A release PR (`GITHUB_BASE_REF` is `main`) is skipped with the line `release PR: each commit was checked on its own PR`, since its commits are the squash commits on `develop`. The commit-msg hook is `.githooks/commit-msg` (`pnpm exec commitlint --edit "$1"`), switched on by the root `package.json` `prepare` script (`git config core.hooksPath .githooks`), with no hook manager dependency.

**The Thai jargon list.** The copy check refuses developer words in the Thai message values of `packages/design-system/src/i18n/messages/th.ts` and `apps/web/i18n/messages.ts`, as DESIGN.md asks ("No jargon in user copy"): `เอพีไอ`, `เอนด์พอยต์`, `แบ็กเอนด์`, `ฟรอนต์เอนด์`, `ดีพลอย`, `รีเควสต์`, `เพย์โหลด`, `สคีมา`, `ดีบัก`, `คิวรี`, and the Latin words `API`, `endpoint`, `payload`, `JSON`, `null`, `undefined`. The product words the Studio teaches (`token`, `component`, `profile`) are not on the list; `th.ts` uses `token` today (open question 13).

**Trade-off, stated.** The defaults install with `pnpm install` and run the same way on the owner's Mac, in a builder worktree and in CI, with no account, token or paid plan. What they give up:

- secretlint checks the files at the head only, not git history. A secret added and removed inside one branch is not seen. gitleaks scans history but is a Go binary each machine must install, and its GitHub Action needs a paid licence for an organization account (decision 1).
- `eslint-plugin-security` matches AST patterns within one file: no data flow and no taint tracking, and some rules are noisy (`detect-object-injection`). Semgrep CE goes deeper but needs Python or Docker on every machine. CodeQL is free only for public repos; this repo is private, so it would need GitHub Advanced Security, which is paid (decision 2).
- The audit already fails on high and critical (`--audit-level high` reports high and above). It checks production dependencies only; dev and build tools are not audited (decision 3).
- In report mode a leaked secret or an unsafe pattern shows in the gate report and blocks nothing until the switch.

## Required controls (ADR 0015, slice B)

ADR 0015 is renamed `docs/adr/0015-standards-and-required-controls.md`, since it now holds more than security and accessibility. Beside the three standards it names these controls. For each it says which role and which check covers it today, or `not covered yet`, and it claims none as met without that check. Each decision carries a `Confirmation:` line.

- **AI.** Model calls run on the server only, through OpenRouter, one pinned model per job (ADR 0009). Briefs, Jira text and uploads are untrusted input, kept apart from the instructions in the prompt. Model output is validated with zod before use and never executed. Each AI job has a rate limit per user and a spend cap per workspace. No personal data goes into a prompt unless the job needs it. A person confirms before model output changes saved data. AI output is labelled as AI in the UI.
- **Performance budgets.** Core Web Vitals at the 75th percentile: LCP 2.5 s or less, INP 200 ms or less, CLS 0.1 or less (the "good" thresholds, with the source URL). Nothing measures them yet, so no report or UI claims them.
- **Observability.** Each server action and route handler response carries a request id (header `x-request-id`). Each log line is one JSON object with `level`, `requestId`, `route`, `durationMs` and `outcome`. No secret and no personal data in a log line (masked as below). An error is logged once, at the boundary.
- **API errors.** Every error response body is `{"error": {"code": "<UPPER_SNAKE>", "message": "<safe text>", "requestId": "<id>", "retryable": <boolean>}}`. The message never carries a stack, a query or personal data. Only a GET, or a write that carries an idempotency key, is retried, by this matrix:

| Status                            | Retryable | Client does                                                  |
| --------------------------------- | --------- | ------------------------------------------------------------ |
| 400, 401, 403, 404, 409, 413, 422 | no        | Show the message; the user fixes the input or signs in again |
| 408, 429                          | yes       | Wait for `Retry-After`, or 1 s without it; at most 3 tries   |
| 500                               | no        | Show the message and the requestId; no automatic retry       |
| 502, 503, 504                     | yes       | Back off 0.5 s, 1 s, 2 s with jitter; at most 3 tries        |
| network error, no response        | yes       | Same as 502, 503, 504                                        |

- **Personal data (PDPA).** Thailand's Personal Data Protection Act B.E. 2562 is named with its source URL. Masking is the default: a field classified `personal` is masked in UI lists, logs, exports and prompts unless the viewer holds a permission that unmasks it, and each unmask is logged. Masked forms: an email keeps its first character and its domain (`t***@gmail.com`), a phone number and a Thai national id keep their last 4 digits. The ADR says these are engineering defaults, not legal advice, and claims no PDPA compliance.

**Security rules.** `.claude/rules/security.md` gains four rules, each pointing at ADR 0015, and its `paths` gain `apps/web/next.config.ts` and `apps/web/proxy.ts`:

- **404, not 403.** A read or write of a resource outside the caller's workspace answers 404 with the same body as a resource that does not exist, so the answer does not show that it exists. 403 is only for a resource the caller can see but may not change.
- **Uploads.** The type is allowed by the file's content (its magic bytes), never by its name or the client's content type. Each kind has a size cap. Objects go to a private bucket under a random key, never the user's file name, and are served through short-lived signed URLs after the authorization check. A user's SVG or HTML is never rendered inline; anything that is not an allowed image is served with `Content-Disposition: attachment`.
- **Field classification tags.** Every column in the `packages/db` schema carries one tag: `public`, `internal`, `personal` or `secret`. `personal` is masked by default (PDPA above). `secret` never leaves the server and is never logged. ADR 0015 names the tag format.
- **Money.** Amounts are integers in minor units (satang for THB) in a `bigint` column, with the ISO 4217 currency code beside them. No float. One rounding helper (half to even). Display through `Intl.NumberFormat` with the locale from the catalog.

## Web security headers (slice D)

`apps/web/next.config.ts` sets `poweredByHeader: false` and a `headers()` entry for every path (`/(.*)`), with the values in `apps/web/security-headers.ts`:

- `Strict-Transport-Security: max-age=63072000; includeSubDomains` (no preload)
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `X-Frame-Options: SAMEORIGIN` (the Studio may frame its own previews)
- `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()`
- `Cross-Origin-Opener-Policy: same-origin`

`apps/web/proxy.ts` (Next.js 16 calls request middleware a proxy; slice D checks the file name and the nonce handling against the installed `next` package's docs before building) makes a fresh nonce per request, at least 128 random bits in base64, and sets `Content-Security-Policy-Report-Only` on the response, and on the forwarded request headers so Next.js puts the nonce on its scripts. The policy, in production:

`default-src 'self'; script-src 'self' 'nonce-<n>' 'strict-dynamic'; style-src 'self' 'unsafe-inline'; img-src 'self' blob: data:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self' https://accounts.google.com; frame-ancestors 'self'`

`form-action` also names `https://accounts.google.com` because Google sign-in is a form post whose server action redirects there, and Chromium checks the redirect target against `form-action` (security review SEC-6). The nonce is 16 bytes from `crypto.getRandomValues`, base64 encoded.

In development only, `script-src` adds `'unsafe-eval'` (React's dev tooling needs it). The proxy matcher skips `_next/static`, `_next/image`, `favicon.ico` and prefetch requests. No enforcing `Content-Security-Policy` header is set in this story, and there is no `report-uri` or `report-to` endpoint (no service), so a violation shows only in the browser console. Moving to enforcing is a later story, once the console shows no violation on the Studio pages.

`apps/web` gets a `test` script that runs Vitest at the version `packages/design-system` pins, so `pnpm test` (turbo) runs `apps/web/security-headers.test.ts`.

## Stuck envelope: the close form (slice C)

**Stuck** means an envelope that is open, is bound (it has `agent.json`), and has no final `SubagentStop` in `heartbeat.jsonl`. Today `close-envelope.mjs <task_id>` refuses it, and only the owner's terminal `--owner` closes it. A foreground Agent call blocks the main session, so while the main session asks a form, none of its own subagents is running. A live one can only belong to another session.

The flow:

1. `envelope-guard` blocks a dispatch because `<role> envelope <task_id> is still open`, or `close-envelope.mjs` refuses with no final `SubagentStop`.
2. The main session asks one `AskUserQuestion` form. The question names the task id, its role, its `agent_id` and its `started_at`, and warns that a builder envelope closed this way still counts as a rework round. The options are:
   - close: the whole label is exactly `ปิดงาน <task_id>` or `Close envelope <task_id>`, with nothing before or after it;
   - decline: `ยังไม่ปิด` or `Keep open`, without the close phrase.
3. The new `owner-close` hook (PostToolUse, matcher `AskUserQuestion`) writes `closed.json` only when all of these hold:
   - the input has no `agent_id`, so the main session asked the form;
   - the answer is one of the option labels offered, so text typed under Other closes nothing;
   - the label matches `^(?:ปิดงาน|close envelope) (ORV-\d+-[a-z0-9-]+)$` (case-insensitive on the English phrase);
   - the task exists and is open, is bound, and has no final `SubagentStop`;
   - if the input carries `background_tasks`, it does not list the task's `agent_id` with status `running`;
   - every field it reads is present: question, option labels, answer, `tool_use_id`, `session_id`, `transcript_path`.
4. The record: `closed.json` `{reason: "abandoned", by: "owner", source: "question_form", question, options, answer, answered_at, tool_use_id, session_id, transcript_path}`, written once with an exclusive create through `writeClosed`.
5. Any other case writes nothing and exits 2 with the reason. Malformed input, a missing field or an error fails closed (ADR 0013 decision 5). A plain decline exits 0 and is silent.

`--owner` from the terminal keeps working unchanged. `close-envelope.mjs`'s refusal message names both ways: the close form in the main session, or `--owner` from the owner's terminal. Slice C first records one real PostToolUse(`AskUserQuestion`) stdin sample and notes whether `background_tasks` is in it (decision 4).

## Rules and bounds

- The close labels and the decline labels are owner-facing text in a Claude Code form, not app UI, so they are not in the locale catalog. Each form carries Thai and English. No middot and no em dash in any label.
- One form closes one envelope per close option. The hook never guesses a task id: the whole label carries it.
- `owner-close` writes through `writeClosed` and never edits a record. A late `SubagentStop` for an envelope closed this way finds it closed, and `result-recorder` writes no `result.json` (existing behavior).
- The new roles change no existing role's required skills, contract or model. The designer keeps its skills and gains one allowed shape: `reviewer.v1` with an empty `write_set`.
- The scans run over tracked files only (`git ls-files`), never over `node_modules`, `.orivilo/` or `.quality-gate/`.
- A new scanner starts in report mode and becomes blocking only by a guard-file PR that removes `--report` from the gate and CI together.
- The jargon list applies to Thai message values only; English copy keeps DESIGN.md's rule, read by the reviewer.
- The helpers assert the rendered result. A play that sets one CSS property and asserts that property does not count as the visual check (L-0018).
- No app UI text is added in this story, so no locale catalog change, apart from rewording a Thai message the jargon list refuses.
- Each slice is one Jira issue and one PR of about 400 changed lines (decision 7), built one deliverable per builder task. Build order A, B, C, D; D needs only B's security rule paths, so it may run beside C.

## Honest limits

- The close form is weaker than the terminal. The main session writes the question and the options; the click is the only proof (ADR 0014, Consequences).
- No live PostToolUse(`AskUserQuestion`) stdin sample was recorded (the harness has no owner click to capture), so the `background_tasks` check rests on the shape seen in a `SubagentStop` sample and on the transcript-derived fixture. A live input may differ; then the hook fails closed or never sees a running agent, and the owner's click decides. Capture one live sample in `docs/specs/ORV-85/stdin-samples.md` on the owner's next form and rerun the owner-close tests on it.
- `owner-close` and `owner-grant` refuse an answer when `tool_response.afkTimeoutMs` is present: the dialog resolved itself after an idle timeout, which is not the owner's click (security review SEC-1). The `.env*` deny entries match a dotenv path argument (alone, after a space, or after a slash) including piped forms; they are permission patterns, not a boundary, and a command that builds the path another way is not seen.
- A subagent in another session that is still running when the owner closes its envelope keeps running. Its report is not recorded, and its edits stay in its worktree.
- The scans are pattern rules. They miss secrets in shapes the preset does not know, secrets in git history (secretlint default), and unsafe code that needs data flow to see. A clean scan is not a security claim. In report mode they stop nothing.
- CI is not a boundary. With no ruleset (ORV-97), a red check stops only an agent merge through `merge-guard`.
- ADR 0015 names standards and controls to check against. It certifies nothing, and no UI or report may say the product conforms to ASVS, the LLM Top 10, WCAG or the PDPA, or meets the performance budgets. Field classification tags, masking, the error envelope and request ids have no code and no check yet.
- The commit-msg hook is skipped by `--no-verify` and by a clone where `pnpm install` did not run. The squash commit on `develop` takes the PR title (`ORV-123: ...`, AGENTS.md), which is not a Conventional Commit and is not checked.
- The jargon list is a word list. It misses other spellings and phrasing; reading the Thai copy aloud (DESIGN.md) stays the check for tone.
- The `.env*` deny rules see the forms they name only (Frame).
- The sign-off order is skill text; `merge-check` still requires only the qa, reviewer and gate records. A designer sign-off approve is a judgement of the screenshots, not a measurement.
- `expectEdgeInk` counts ink against a threshold, so antialiasing and the device pixel ratio can move it by a device pixel. A Thai mark drawn above its font's own ascent is outside every `Range` rect, so `expectNoGlyphClip` cannot see it; the designer's screenshots are the catch for that.
- The Report-Only policy blocks nothing and reports only to the browser console. `style-src 'unsafe-inline'` stays until the styles carry the nonce. A nonce policy makes every page render per request, with no static page.

## Out of scope

- Splitting `product` into BA, SA and PO (excluded by the issue).
- A security or research skill, a new report contract, a headless security run in CI.
- Requiring a `security` approve or a designer sign-off in `merge-check` (decision 5).
- Secret scanning of git history, CodeQL, GitHub Advanced Security, Dependabot, SBOM.
- An ASVS audit, a penetration test, an axe scan, a screen reader pass, a Core Web Vitals measurement, a PDPA legal review.
- Code for request ids, the error envelope, masking or classification tags (the ADR names them; each lands with the story that needs it).
- An enforcing CSP, a CSP report endpoint, HSTS preload.
- Switching the scanners to blocking (open question 14).
- GitHub rulesets (ORV-97) and closing the `.orivilo` forge gap (ORV-96).
- Any change to the grant form, the rework count, or `--owner`.
