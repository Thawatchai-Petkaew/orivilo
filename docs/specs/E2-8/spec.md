## Why

The handoff's MVP (§19, phase 4) asks for one product surface, the team workspace with project creation, built from the shared components, where long data, a small viewport, an error and an overlay work under both hand-made profiles. E2-4 to E2-7 proved the components one at a time and in example pages; nothing yet is a real screen in the app, and E2-11 needs a screen to show under two directions. This story lands that reference screen: one component in the design-system package, rendered as a route of the app and as stories in Storybook, with the flows that a workspace has (create a project, archive the selected ones) running on fixture data that the screen says is fixture data.

## Story

As the owner judging the vertical slice, and as E2-11's preview, I want the team workspace screen composed only from `@orivilo/design-system` components, with a project table, project creation in a dialog and an archive confirmation, proven with long Thai and Latin data, at 360 px, with a load error, and with the overlays carrying the Professional and Friendly profiles, so that the components are shown to compose into a working screen before the resolver and the interpreter build on them.

## Rules and bounds

- **Where it lives.** `packages/design-system/src/examples/workspace.tsx`, exported with the other examples through the package's `./examples` entry, so the app route and later E2-11's preview render the same component. The package index still exports components only.
- **Composition only.** Button, Badge, Field, Input, Select, Textarea, Checkbox, Dialog and Table from the package; Tailwind for layout; no new token, recipe or component. The selection bar, the page header and the confirm dialog are inline in the screen and stay `none` in `coverage.md`.
- **Honest UI.** The screen labels its data as fixture data and says nothing is saved. Counts are computed from the rows on the screen. The creation and archive flows change the screen's own state with a short simulated delay so pending shows; nothing claims persistence.
- **One primary per view.** "สร้างโปรเจกต์" on the page; "สร้าง" inside its dialog; the archive confirm uses the destructive variant.
- **Copy.** Thai, sentence case, no middot, no em dash; errors say what went wrong and how to fix it; actions are named after the outcome.
- **No app test runner.** The app has no Vitest or Playwright set-up and this story does not add one (that is delivery-loop work, E0); the route is verified by `next build` and by a screenshot of the running app, and every behaviour is proven in the Storybook project of `pnpm test`.

## Out of scope

Persistence, auth and workspace data access (E2-15), the Studio shell with navigation (E4), the ConfirmDialog pattern as a component, Members management, project detail pages, the preview under two directions (E2-11), a Playwright suite for the app.
