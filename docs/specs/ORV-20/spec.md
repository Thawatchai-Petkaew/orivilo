# ORV-20: color node knowledge, category audit and role rules

## Why

The brief makes knowledge the moat: a canvas node is expert in its topic, and it decides from rules with sources instead of improvising. The brand CI method (`docs/context/brand/brand-ci-method.md` §3 and §5) already says how color is chosen: audit the category's hues and take the gap, define roles before values, keep feedback, selection and focus apart from the brand, and compute contrast instead of judging it by eye. Today none of this runs. The starter rules (`directions.ts`) cite a knowledge id that has no entry, and no rule knows anything about hue, a lineup or a role.

During the POC the owner wants the system to work per the concept before the screen flow (ORV-20 comment). For color, the concept is: a category lineup and a personality vector go in; a role palette comes out in which every value names the rules and knowledge entries that produced it; every text and UI pair passes the contrast contract that already guards the design system (E0-5); and the same input always gives the same output. The ORIVILO brand spec v1.1 (`docs/context/brand/orivilo-brand-spec-v1.1.md` §5) is the worked example: the ORIVILO lineup and vector must reproduce its palette, or the slice B spec ([ORV-125](../ORV-125/spec.md)) names each difference and why.

What is real and what is simulated, so nobody mistakes one for the other:

- **Real:** the hue audit, the rules, their evaluation, the trace, and the contrast proof. All are deterministic TypeScript with tests.
- **Rule-based, not AI:** no model is called anywhere in this story. The output says `method: "rule-based"`. Nothing in code, tests or docs may call it AI interpretation.
- **Curated, not generated:** hex values come from a small curated swatch table (ADR 0007, "Not chosen: generating token values"). The rules choose which curated set applies; they do not invent colors.
- **Hypothesis-grade knowledge:** the thresholds and the preference order are our reading of the method, recorded as knowledge entries with basis `hypothesis` (confidence at most 0.4) unless a stronger basis is shown.
- **Stand-in lineup:** the ORIVILO lineup fixture uses hex values chosen to stand for the method's audit conclusion (§5.1: violet 250 to 265, black, cream with clay). They are not sampled from the named brands' own assets (decision 3).

## Story

As the Intent Engine's color node, given a category lineup (each competitor's dominant brand color) and a brand's personality vector, I want to audit the lineup's hues, apply closed color rules that rest on knowledge entries, and return a role palette for light and dark mode in which each value carries the decisions, rule ids and knowledge ids behind it, so that a person can see why every color was chosen, a missing input becomes a question instead of a guess, a tie between rules is shown instead of picked, and every palette the node can produce is proven readable by the existing contrast check.

## Rules and bounds

### Input

- `lineup`: `null` (not given) or 1 to 20 entries `{ name, hex }`. `name` is 1 to 60 characters, trimmed, unique ignoring case; it is a label for the trace only and is never read as an instruction (AGENTS.md, untrusted input). `hex` is `#RRGGBB`, either case, stored uppercase.
- Brief facts: the existing `BriefFacts` (personality, industry, audiences, avoid). Industry and audiences are carried but no color rule reads them.
- `crowded` is a fact only `auditLineup` sets. It is not added to `briefFactsSchema` or `interpretationSchema`, so the brief interpreter, rule-based or model-backed, can never supply it (row 16).

### Category audit (`auditLineup`)

Hue is the HSL hue in degrees of the sRGB value, the same measure the brand documents use (the method's 250 to 265 violet; the spec's violet at 272). Chroma is `(max − min) / 255`, lightness `(max + min) / 510`.

| Family  | Hue from (inclusive) | to (exclusive) |
| ------- | -------------------- | -------------- |
| red     | 345                  | 10             |
| orange  | 10                   | 45             |
| yellow  | 45                   | 65             |
| lime    | 65                   | 95             |
| green   | 95                   | 150            |
| teal    | 150                  | 185            |
| cyan    | 185                  | 205            |
| blue    | 205                  | 240            |
| violet  | 240                  | 290            |
| magenta | 290                  | 345            |

Chroma under 0.12 is achromatic: `ink` when lightness is under 0.5, `paper` otherwise. A family is **crowded** when two or more lineup entries fall in it (decision 4). `gaps` are the chromatic families that are not crowded. The audit reports per entry `{ name, hex, family }`, then `crowded` and `gaps`, all sorted.

### Grammar additions (ADR 0017, written in slice A)

ADR 0006 allows adding a fact and a condition form as additive changes that keep `schemaVersion` "1.0". This story adds:

1. A condition form `{ crowded: <chromatic family> }`. True when the family is in `facts.crowded`, false when it is not, unknown with missing `lineup` when `facts.crowded` is absent.
2. Node-scoped decisions. ADR 0006 decision 3 ties every action to `DECISION_VOCABULARY`, the list profiles declare. Color decisions are not profile decisions, so adding them there would force every curated profile, the resolver and the Direction Studio to carry them. Instead color decisions come from `COLOR_DECISIONS`, a separate closed vocabulary whose keys share none with `DECISION_VOCABULARY`; `DECISION_VOCABULARY` and the profile drift test stay as they are. **Scope follows the keys a rule sets** (ADR 0017 decision 1): a rule whose actions set color keys is a color-scope rule, a rule whose actions set profile keys is a profile-scope rule, and a rule that sets keys from both fails to parse at `then` (row 26). Topic adds one check on top: a rule that sets a color key must have topic `color`. A rule with topic `color` may still set profile keys, so the starter rule `emphasis.expressive-signature` in `directions.ts` and the `rules.test.ts` fixtures `emphasis.expressive-signature` and `emphasis.finance-restrained` (all topic `color`, setting `emphasis` or `typeVoice`) stay valid with no edit (row 16). This refines ADR 0006 decision 3, so it is a new ADR, 0017, that supersedes that one decision and nothing else.
3. The `crowded` condition is allowed only in color-scope rules. A profile-scope rule that uses it, at any depth, fails to parse (row 27), so the profile path never asks a brief for a lineup it never audits.
4. A scope check. `checkRuleSet(rules, knowledgeIds, scope?)` takes an optional third argument `"profile"` or `"color"` and reports a new problem, `wrong-scope`, for a rule whose keys belong to the other scope; without the argument it behaves exactly as today. `decideColor` passes `"color"`; `resolveProfile` passes `"profile"`, a one-argument change in `resolver.ts`. Either way a rule of the other scope makes the result `invalid` instead of firing and setting nothing (row 28). No existing resolver fixture carries a color-scope rule, so their output, fingerprint included, is unchanged.

`schemaVersion` stays "1.0": every rule that parsed before still parses, as ADR 0006's change rules allow for an added decision, value or condition form.

### Status and output

`decideColor` (slice A) and `buildColorPalette` (slice B, ORV-125) use ADR 0007's status words in its order: `invalid` (rule set fails `checkRuleSet`), `conflicted`, `needs-input` (a decision open), `resolved`. Output carries `version: "color-1"`, `method: "rule-based"`, the audit, the evaluation (decisions, conflicts, overridden, fired, undecided), `open`, `questions` (sorted fact names, `lineup` included when the lineup is missing), and `fingerprint`. `buildColorPalette` adds `roles` and `contractRoles`.

### Purity

The color modules are pure TypeScript in `packages/intent-engine`: no `Date`, no `Math.random`, no network, no framework or design-system import. The contrast proof lives in `packages/design-system`, which already depends on the engine for tests, so the engine never imports the design system (ADR 0007 decision 1).

The method's §3 reads ORIVILO's warm 70 as "warm-leaning neutrals kept close to neutral". The brand spec calls its canvas cool-neutral. The node's `near` band (26 to 74) takes ORIVILO to the brand spec's values (row 8, and the worked example in ORV-125); the band edges are a hypothesis (`color.warm-leans-hue`) that a second real brand should test.

## Out of scope

- Any UI: the canvas color node, its ports, an inspector or a palette view (E4). No locale strings are added.
- Wiring the palette into curated profiles, the resolver, the Direction Studio or the token build. The contrast proof builds runtime profiles in a test only.
- Locks and expert adjustments on color decisions (ADR 0007 applies them to profile decisions only); a person who disagrees with the result has no override in this story.
- A second hue for playful brands (method §3), the 60/30/10 proportion, the distinctive-asset plan, OKLCH, CMYK or Pantone output, and print.
- Sampling real competitor colors, reference collection (E1-7), and persistence (E2-12).
- Feedback and focus values: the contract owns them.
- Any model call, and any claim of AI interpretation.

## Decisions

G1 passed on the [ORV-20 G1 comment](https://tpetkaew.atlassian.net/browse/ORV-20) by Claude under the owner's POC delegation (ADR 0012 decision 4). Every open question of v1 took its default; the options weighed are kept for the record.

1. **Lane: L.** The backlog drafted M with no risk flag; the grammar additions are resolver logic, an L flag. Claude passes G1 and G2 under the owner's POC delegation; G3 and G4 with evidence.
2. **How color decisions enter the grammar: (a)** node-scoped `COLOR_DECISIONS` and ADR 0017. Not chosen: (b) add color keys to `DECISION_VOCABULARY`, which forces every curated profile, the resolver schema and the Direction Studio to carry them and fills the eight-key cap in `profiles.test.ts` (five plus three); (c) a separate algorithm outside the grammar, which breaks the traceability this story exists for.
3. **The ORIVILO lineup values: stand-ins,** hexes standing for the method's audit (fixture above), labelled as such. Not chosen: values sampled from the six named brands, which needs sources with licenses (E1-7) and dates. A sampled fixture can replace the stand-ins later with a spec version bump.
4. **Crowd threshold: two entries** in a family; a lineup of one cannot crowd anything. Not chosen: a share of the lineup (for example a quarter).
5. **Hue measure: HSL hue,** which matches the degrees the brand documents use. Not chosen for this story: OKLCH hue (perceptually even); it can replace the band table later as a versioned change of `color.hue-families`.
6. **Premium and canvas: a soft off-white canvas under white cards,** what the brand spec chose for premium 65. Not chosen: reading the method's "restrained, deep" for high premium as a dark canvas.
7. **Signature candidates: four** for the POC (lime, cyan, magenta, teal). Adding a value is additive; more come with a second real brand.
8. **Thresholds as written** (expressive 55, warm 50, neutral bands at 25 and 75, premium 60), recorded as hypotheses at confidence 0.4. The owner can raise an entry's basis by verifying it.
9. **Knowledge entry status: `draft`** with `verifiedAt` null until the owner checks them; `freshness` reports them as unverified.
10. **Two PRs: slice A then slice B,** as in the delivery table. Slice B became its own Jira issue, [ORV-125](https://tpetkaew.atlassian.net/browse/ORV-125), with its own spec (L-0016).
