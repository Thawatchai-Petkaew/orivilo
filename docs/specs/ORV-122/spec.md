# ORV-122: shared rate limits for sign-in and Better Auth's routes (ORV-112 slice B)

## Why

ORV-112 slice A put the AI reading, writes and import behind counts every Vercel instance shares. Sign-in is still open: Better Auth 1.7.12 counts `/api/auth/*` in process memory (one map per instance), and `signInWithGoogle` calls `auth().api.signInSocial` from a server action, which Better Auth's router limiter never sees. Each try writes a `verification` row, so an unbounded loop grows that table. ADR 0015 decision 4 and `.claude/rules/security.md` rule 6 require sign-in to be limited in a shared store. The full reasoning is in [ORV-112's Why](../ORV-112/spec.md#why); this story is that spec's slice B, split out so each slice has its own acceptance and its own gates.

Sign-in has two doors to the same `signInSocial` and the same `verification` row: the `signInWithGoogle` action and `POST /api/auth/sign-in/*` through the route. The sign-in limit (10 per 10 minutes per trusted IP) counts both in one bucket, so a script that skips the form meets the same cap as a person who presses the button (security review S1 on 33f8f93: counted only under Better Auth's `/sign-in*` rule, the route admitted 3 per 10 s, 180 per 10 minutes, 18 times the sign-in limit).

**Frame.** A server-side control, not a hook that judges text: counters live in our Postgres and only server code writes them through `orivilo_app` (ADR 0002). Per IP limits rest on one thing outside our code, Vercel's edge overwriting `x-forwarded-for` (K-0015), which row 21's staging probe checks before this story passes G4. A bound against one network, not against a distributed attack.

**What is real.** Real server checks with tests, plus one staging probe run by hand (row 21), not part of `pnpm test`.

## Story

As the workspace owner, I want each network's sign-in attempts and Better Auth requests counted in the store every server instance shares, so that a script cannot loop sign-in or flood `/api/auth/*` by either door, and the person who hits the cap is told in Thai or English how long to wait.

## What this story uses from ORV-112 (linked, not copied)

- **Limits and numbers**: the `sign-in` and `auth-http` rows, windows, `Retry-After` and the burst bound, [ORV-112 spec "Limits and numbers"](../ORV-112/spec.md#limits-and-numbers). The `sign-in` entry already sits in the `LIMITS` map from slice A. This spec widens where `sign-in` applies: the action and `POST /api/auth/sign-in/*` (row 24); its number is unchanged.
- **The store and the helper**: table, keys (`auth-http:ip:<subject>:<window>x<max>`), IP subject, trusted header, pruning and store failure, [ORV-112 spec "The store and the helper"](../ORV-112/spec.md#the-store-and-the-helper). Store failure applies here as written there: a call answered unavailable does not commit a count later, except a `COMMIT` already on the wire when the timer fired, which over-counts by at most one and still fails closed (ORV-112 comment 10187).
- **The outcome and the UI**: the `authRoute` 429 and 503 bodies, the sign-in notice under the button on `/account` with the `account.problem` badge, the wait format, [ORV-112 spec "The outcome and the UI"](../ORV-112/spec.md#the-outcome-and-the-ui). The strings `account.rateLimited`, `account.problem` and `wait.*` already sit in `apps/web/i18n/messages.ts` from slice A.
- **Decisions** 1 to 9 on ORV-112, in particular 4 (`useActionState` form), 5 (`x-forwarded-for` and its probe), 7 (503 `SERVICE_UNAVAILABLE`) and 8 (buckets per rule), [ORV-112 spec "Decisions"](../ORV-112/spec.md#decisions).
- **Tech notes** `docs/specs/ORV-112/tech.md` (Better Auth `customStorage`, `authRoute`, the probe steps) and **G2 design** `docs/specs/ORV-112/design.md` (the account notice, D2 for its page test). G1 and G2 for this work were passed on ORV-112.

## Scope (slice B)

- The `sign-in` limit, one bucket per trusted IP (`sign-in:ip:<subject>`), consumed by two doors: `signInWithGoogle` before `signInSocial`, with the notice on `/account` through a small client form with `useActionState`; and `authRoute` for `POST` requests whose path starts with `/api/auth/sign-in/` and whose media type is JSON (see "What the route counts"), before the Better Auth handler runs. Both doors call one shared server function in `apps/web` for the count.
- Better Auth's `rateLimit.customStorage` on the shared helper and table, always set, and `advanced.ipAddress.ipAddressHeaders: ["x-forwarded-for"]`; Better Auth's `no-trusted-ip` maps to `unknown`.
- `authRoute` in `packages/auth`, wrapping `GET` and `POST` in the route file: 429 with `Retry-After` and the `RATE_LIMITED` body, 503 with the `SERVICE_UNAVAILABLE` body on a store failure, any other error rethrown; `x-request-id` on every 429 and 503 it answers, equal to the body's `requestId`; one JSON log line by name only on a store failure.
- The staging header probe (row 21), a G4 condition.

## Rules and bounds

ORV-112's "Rules and bounds" apply unchanged. In short: one helper, no counter in process memory, only `x-forwarded-for` as a single value on Vercel, no raw IP or email in a key or log line, Thai and English together, no middot, no em dash. Added in v1.1:

- **Order on the route.** For `POST /api/auth/sign-in/*`, `authRoute` consumes `sign-in` first. Refused there, the handler is not called, so Better Auth's `/sign-in*` rule does not count that request. Allowed there, the handler runs and Better Auth's `/sign-in*` rule (3 per 10 s) still applies; a request it then refuses has already counted once toward `sign-in`. That is accepted: it only makes sign-in stricter, never looser.
- **One IP for both doors.** The route's subject for `sign-in` comes from the same trusted-IP function the action uses (`clientIp`, which calls Better Auth's `getIPFromHeader`), never from Better Auth's limiter key, so both doors land on one row.
- **Store failure on the sign-in check** in `authRoute` answers 503 as in row 20, and logs the same one line. Added in v1.2: this covers a count that throws synchronously, before it returns a promise, exactly like one that rejects; `authRoute` calls the count so that both forms reach the same 503 path, and only an error from the Better Auth handler that is not `RateLimitUnavailable` is rethrown (security F1 on b4184b5).
- **The log line** is the only line `authRoute` writes, one per store failure, as JSON with exactly `level`, `requestId`, `route`, `outcome`. A 429 is not logged by `authRoute` in this story.
- **Request id.** `authRoute` makes one random id per answer it writes itself and uses it in the body, the `x-request-id` header and the log line. Answers the Better Auth handler writes are unchanged (request ids across the app are ORV-113).

Added in v1.2:

- **What the route counts.** `authRoute` counts a sign-in only for a request that could start one: `POST`, a path that starts with `/api/auth/sign-in/`, and a `content-type` whose media type is JSON, read the way Better Auth reads it (lower-cased, the part before `;`, trimmed, containing `application/json`), so every request Better Auth would parse as a sign-in body is counted. Any other request goes to the Better Auth handler uncounted and Better Auth refuses it (415 for a wrong media type; email sign-in is disabled). A browser can send a cross-site `POST` without a preflight only as `text/plain`, `application/x-www-form-urlencoded` or `multipart/form-data`, so a page a visitor opens cannot fill that visitor's network's bucket (security F2 on b4184b5, row 25). Better Auth's own `/sign-in*` rule (3 per 10 s) still counts those requests in its `auth-http` bucket; that bucket clears in 10 s, which bounds the lockout such a page can cause.
- **Origin is not part of the count rule.** Better Auth 1.7.12 checks `Origin` against the trusted origins only when the request carries a cookie (`validateOrigin` in its origin-check middleware), so a script with no cookie and any `Origin` still starts a sign-in. Skipping the count for a foreign `Origin` would let that script past the sign-in limit and reopen security S1 on 33f8f93. A JSON request with a foreign `Origin` is counted; a browser cannot send one cross-site without a preflight, which our route does not answer with CORS headers, so this costs no lockout.
- **One wiring for both doors.** The app builds the sign-in count once, in a shared server function (`LIMITS["sign-in"]`, subject from `subjectFromHeaders`) that `signInWithGoogle` and the route both call, and a unit test pins its limit and subject (row 24, reviewer S2 on b4184b5).

## Out of scope

Everything in ORV-112's "Out of scope", and everything ORV-112 slice A delivered (the table, migrations, the helper, the client IP subject, the `ai-read`, `write`, `import` and `signed-out` limits, the directions UI). ## Impact list

- **`packages/auth`**: new `auth-route.ts` (sign-in check for a JSON `POST /api/auth/sign-in/*`, a synchronous throw from the count treated as unavailable, `x-request-id`, the store failure log line); `config.ts` gains `rateLimit.customStorage`, `advanced.ipAddress.ipAddressHeaders: ["x-forwarded-for"]` and test options for the limiter; `index.ts` exports `authRoute`.
- **Route**: `apps/web/app/api/auth/[...all]/route.ts` wraps the handler in `authRoute` for `GET` and `POST`, passing what `authRoute` needs to consume `sign-in` (the shared limiter).
- **Shared sign-in count** (v1.2): one server-only function in `apps/web` that consumes `LIMITS["sign-in"]` for the subject `subjectFromHeaders` gives, imported by `route.ts` and `actions.ts` instead of each building its own call, with its unit test (row 24).
- **Actions**: `apps/web/app/account/actions.ts`, `signInWithGoogle()` with no parameters, consuming `sign-in` per trusted IP. It takes no parameters because it reads nothing from the form: the provider is fixed and the IP comes from the request headers. `useActionState` passes the previous state and the form data, which the action ignores, and the signature type-checks against the form's `action` prop (reviewer S1 on 33f8f93; v1 said `signInWithGoogle(prev, formData)`).
- **UI**: `apps/web/app/account/page.tsx` and `SignInForm.tsx` show the sign-in notice in a polite live region with the `account.problem` badge; `apps/web/vitest.config.ts` may widen its `include` and JSX setting so row 11's rendered test runs.
- **Existing tests at risk**: `auth.integration.test.ts` now writes counter rows on every handler call, and every `POST /api/auth/sign-in/*` also counts toward `sign-in`; a test sending more than 3 `/sign-in*` requests per 10 s, or more than 10 sign-ins per 10 minutes for one IP, through the handler must pin its clock or use separate IPs.
- **Specs to review**: ORV-38 (sign-in limited by Better Auth's limiter, which held per instance only), ORV-113 (`SERVICE_UNAVAILABLE` joins its closed list of error codes; `x-request-id` on `authRoute`'s answers), ORV-112 spec "Limits and numbers" (`sign-in` "Applies to" now names the route too).
