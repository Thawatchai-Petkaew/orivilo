## Why

ADR 0003: shadcn provides behavior, our recipes provide every visual value, Storybook is the catalog. After E2-3 the tokens, two profiles, the neutral shell and the boundary exist, but no shared component does, so nothing yet proves that one component set changes its look under a profile while its states, names and keyboard paths stay intact. This story lands the first ten base components and the recipe layer they consume, so that every later screen (E2-5 overlays, E2-6 table, E2-8 reference screen, E4 canvas panels) composes from components that already pass the design gate.

## Story

As an agent or a person composing a Studio screen or a customer preview, I want Button, Input, Textarea, Select, Checkbox, Field, Tooltip, Badge, Popover and Tabs from `@orivilo/design-system`, each with every state in DESIGN.md §7 as a story and proven under three recipes and both modes, so that I compose from the catalog instead of styling anything myself.

## Rules and bounds

- **Recipe**: a recipe is the set of classes in `src/recipes/recipes.css` (`ds-button`, `ds-control`, `ds-menu`, …) whose every value is a `--cmp-*` or `--ds-*` custom property. A profile changes the recipe's values by overriding the semantic tokens the component tokens reference; it never changes a class. The neutral profile's resolution is the **airy** recipe of DESIGN.md §2. A catalog entry's `recipes` lists the profiles the component has been proven under (`neutral`, `professional`, `friendly`); the gate needs two. Decision-dependent rules beyond what tokens express (none today) land in the same file keyed by a data attribute, never in a component.
- **Component tokens** added in `component.json`, each referencing a semantic token only: `button.*` sizes, press and disabled slots, `input.height.{sm,md,lg}` (replaces the single `input.height`), `input.padding-y`, `select.*`, `menu.*`, `popover.*`, `tabs.*`, `badge.brand.*` and sizes, `checkbox.*` size and states, `field.*`. Disabled text uses `text.secondary` on the disabled surface, because DESIGN.md §7 requires ≥ 3.0 on disabled controls and `text.disabled` reaches 2.3 on the canvas; `text.disabled` stays for labels beside a disabled control, not on it.
- **Behavior** comes from the `radix-ui` package (the primitives shadcn generates from): Slot (Button `asChild`), Checkbox, Select, Tooltip, Popover, Tabs. Input, Textarea, Badge and Field are native elements. No shadcn visual class, variable or theme file is kept (ADR 0003).
- **Public API** (the risk flag): `ButtonProps`, `InputProps`, `TextareaProps`, `SelectProps` (`options` array, so empty and disabled options are part of the contract), `CheckboxProps`, `FieldProps`, `TooltipProps`, `BadgeProps`, `PopoverProps` with `PopoverTrigger`, `PopoverContent`, `PopoverClose`, `TabsProps` with `TabsList`, `TabsTrigger`, `TabsContent`. `ControlSize` is `sm | md | lg`. Hover, focus and pressed are interaction states, not props (handoff §14). Button adds the `intent` variant to the catalog's four because `button.intent.*` tokens exist and the Studio needs the one Intent Engine button per screen; inside a profile boundary it renders as the profile's primary action (E2-3 remap).
- **Portal scope**: `DesignProfileBoundary` publishes its mode and profile through context; `PortalScope` re-opens the same boundary inside a Radix portal. Select, Tooltip and Popover use it. This is the half of E2-5 that these three components need; E2-5 keeps Dialog and Card and the test on an overlay that traps focus.
- **Loading** blocks the click and announces status; it never removes the label or focus. **Disabled** uses `disabled` on native controls and `aria-disabled` on loading buttons.
- **Copy**: Thai labels in stories; sentence case; no middot, no em dash; errors say what went wrong and how to fix it.
- **Stories** sit next to the component (`src/components/<name>/<Name>.stories.tsx`), title `Base/<Name>` so the id matches the catalog `story` field; the Storybook project of `pnpm test` runs every story with the a11y addon; play functions prove the behaviors in AC 4, 6, 7, 8, 9 and 10.
- **Catalog status**: the ten entries are set to `stable` in this PR, because the PR's merge is the design gate (DESIGN.md §11) and the owner's pass is the approval; the §11 walk with evidence is in the PR body. If the owner requests changes, the status is reworked with the rest.
- `apps/web/app/page.tsx` moves the component line from "not yet" to "real"; the page uses no component yet (that is the E2-8 reference screen).

## Out of scope

Dialog, Card and the focus-trap portal test (E2-5), Table (E2-6), page examples (E2-7), RadioGroup, Switch, Combobox and the rest of `coverage.md`, a Storybook docs page per component, visual regression baselines, icon library (four inline SVGs ship with the components; an icon set is chosen when E4 needs it), deployment of Storybook (E0-3).

## Changelog

- v1 (2026-10-21): written and delivered in the same PR at the owner's request. Decisions taken while building: recipes are CSS classes keyed by data attributes rather than class-variance objects, so a profile restyles them with no JavaScript and the raw-value check is one regex over one file; `surface.raised` dark moves to gray.800 (and the profiles' to their .800) because `border.control` on a .700 menu reached 2.2 under Professional and Friendly; Friendly's light press moves to coral.300 because ink on coral.600 reached 3.3; `menu.border` and `tabs.border` are left out of the pairs as decorative dividers. Defects proven to fail: a planted hex, raw radius, unknown `--cmp-*` and `--op-*` reference in `recipes.css` fail three tests; removing `PortalScope` from Select fails the InsideProfile story ("professional" expected, "undefined" received); the pair list failed 19 times before the value changes above.
- v1.1 (2026-10-21): owner review of the Storybook build. `textarea.radius` moves to `shape.media.radius` and `tabs.radius` to `shape.check.radius`, applied to all four corners of the hover tint: the pill radius on a multi-line box read as a capsule, and on a tab's top edge as a dome. The selected tab stays a 2 px edge, so the shape carries no state.
- v1.2 (2026-10-21): the owner pointed back to the brand case study (boards 06, 08, 09): the primary action is Orbit violet, not ink. `action.primary`, `-hover`, `-press` return to violet.600/700/900 (dark violet.400/300/500) in DESIGN.md v1.6; `text.on-action` stays white and gray.900. Impact: Button `primary` and the checked Checkbox change colour through the semantic layer; the 420 contrast pairs re-run; profiles are unaffected because each overrides `action.primary`.
