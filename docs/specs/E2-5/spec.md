## Why

E2-4 proved the recipe layer on ten base components and re-opened the profile boundary inside the Radix portals of Select, Tooltip and Popover. None of those traps focus or blocks the page, so the handoff's overlay test (§19: "at least one overlay proves theme scope through a portal") is still open, and no container exists for the airy bento that DESIGN.md §2 describes. This story lands Dialog, the first overlay that traps focus, and Card, the bento's unit, so that E2-8's reference screen and E4's canvas panels compose confirmation, secondary tasks and comparable units from the catalog.

## Story

As an agent or a person composing a Studio screen, I want Dialog and Card from `@orivilo/design-system`, each with every DESIGN.md §7 state as a story and proven under three recipes and both modes, so that a confirmation or a short task opens over the page with the right profile and focus discipline, and comparable units sit on the canvas without a card kit.

## Rules and bounds

- **Dialog** is Radix Dialog (`radix-ui`): modal by default (focus trapped, page inert, scrim), `modal={false}` only for previews and the recipe matrix, where several may be open at once. A non-modal dialog still dismisses on focus or pointer outside, so a preview that keeps several open prevents `onInteractOutside`; the matrix story does and asserts six dialogs stay open. The content re-opens the trigger's boundary through `PortalScope`; `container` mounts the portal elsewhere (a preview frame) and the scope still travels with it, which answers the handoff's open question (§16: portal container or theme context) with both.
- **Public API** (the risk flag): `DialogProps` (`open`, `defaultOpen`, `onOpenChange`, `modal`), `DialogTrigger` and `DialogClose` (`asChild` by default), `DialogContentProps` (`title` required and visible, `description`, `variant` default or destructive, `size` sm or md, `pending`, `error`, `footer`, `container`, `closeLabel`). `CardProps` is a union: a static card (`as` div, article, section or li; `selected`), a button card (`interactive`, `selected` as `aria-pressed`) or a link card (`interactive` with `href`, `selected` as `aria-current`). `CardTitle` (`as`, defaults to `h3`, or `span` inside an interactive card), `CardValue` (numeral tile), `CardFooter`.
- **Component tokens** added in `component.json`, each referencing a semantic token only: `dialog.*` (scrim and its opacity, bg, fg, description, border, radius `shape.overlay.radius`, shadow, padding `space.inset.lg`, gap, title and body type, destructive and error `feedback.danger.fg`, layer) and `card.*` (bg `surface.card`, fg, border `border.card`, border-hover `border.control-hover`, bg-selected `surface.selected`, border-selected `selection.fg`, radius `shape.container.radius`, shadow `elevation.shell`, padding `space.inset.lg`, gap, title type, value type `type.numeral.md`, value fg). Widths are layout: sm `max-w-sm`, md `max-w-lg`.
- **Pairs** not floored: `dialog.border` and `card.border`, which are `border.subtle` and `border.card` (transparent in light); a dialog is identified by its scrim and shadow, a card by its ground against the canvas and, in dark, by `border.card`; neither edge carries information (WCAG 1.4.11 does not apply).
- **Focus order**: the close control sits last in the DOM so the first focusable is the task's first control or the safe action, and is placed top-right by the recipe.
- **Pending** blocks Escape, outside click and the close control; it never removes the label or focus. **Error** says what went wrong and how to fix it.
- **Card**: an interactive card contains no other control (catalog rule: whole-card click and inner actions never compete). `CardValue` takes digits only; Thai text never takes the numeral tracking (DESIGN.md §3.3, §9 item 9).
- **Copy**: Thai in stories; sentence case; no middot, no em dash; the primary action is named after the outcome, never "OK".
- **Stories** titled `Application/<Name>` so the id matches the catalog `story` field; play functions prove AC 2, 3, 4, 5 and 8.
- **Catalog status**: both entries are set to `stable` in this PR because the PR's merge is the design gate (DESIGN.md §11) and the owner's pass is the approval.
