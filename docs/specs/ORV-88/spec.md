## Why

The owner decided on 2026-10-23, in the question form for ORV-87 open question 7: "ห้าม resume ส่งงานใหม่ทุกครั้ง" (no resume; dispatch new work every time). Copy: `docs/specs/ORV-88/jira-issue.md`.

Two reasons, in order of weight:

1. **A hole in the guard.** A resume goes through the `SendMessage` tool with the subagent's id in `to`. `envelope-guard` matches the `Agent` tool only, so a resumed subagent runs with no envelope: nobody checked its brief, its facts, its `write_set` or its `done_when`. ADR 0013 decision 2 says only `Explore` runs without an envelope; a resume breaks that rule today. The `SendMessage` result even carries `revivedAgentId` next to `resumedAgentId` (`docs/specs/ORV-87/samples.md`), so a subagent that already stopped and was recorded can be brought back.
2. **The cost.** A resumed agent re-sends its whole earlier context on every later call. The Jira issue cites "about 200k tokens for fewer than 10 tool uses" (`docs/specs/ORV-87/baseline.md`); that figure is the completion notice, the size of the last call's context. The work done is larger: resumed reviewer passes summed about 1.6M to 2.8M tokens each (`docs/specs/ORV-87/samples.md`, the finding on `subagent_tokens`). A fresh dispatch is not cheaper by itself either: reviewer resumed runs median 589,723 against fresh 576,547.5 (`docs/lessons/L-0008-recheck-costs-like-a-first-review.md`). The saving comes from a narrow fresh envelope (L-0008), not from the block. This story closes the hole; it does not claim a token saving.

## Decisions this spec relies on

- The owner's answer to ORV-87 open question 7 (above): no resume. It replaces that question's default ("measure only").
- ADR 0013 decision 2 (only `Explore` runs without an envelope) and decision 5 (hooks block with exit 2 and never fail open; `ovl-doctor` probes every registered guard).
- ADR 0012 decision 4: during the POC, Claude passes G1 and G2 under the owner's delegation. The scope is the owner's decision above; G3 needs the full gate, two reviewer passes and CI.
- ORV-81 spec v1.3: Hooks (fail-closed rules, heartbeat, `ovl-doctor`), Records (the main checkout's `.orivilo/`, `agent.json` holds the bound subagent's `agent_id`), Honest limits.
- ORV-89 and ORV-90: records live in the main checkout's `.orivilo/`, found through `git rev-parse --git-common-dir`; a guard writes its heartbeat only into this project's records, and its verdict never depends on a checkout (`worktree-guard` is the model).
- L-0008 (promoted 2026-10-24): the Re-check envelope rule in `.claude/skills/ovl/SKILL.md` step 2.

### Decided in this spec

**The guard blocks every `SendMessage` call, whatever `to` names, from the main session and from any subagent.** It does not allow-list anything.

Why the stricter rule and not "only ids found in records" or "only agents this session started":

- Records miss agents. An `Explore` subagent is never recorded. A subagent that started with no single open envelope runs unbound and has no `agent.json` (ORV-81 Honest limits). A subagent from before slice A3, from another session, or recorded in a stray worktree folder before `migrate`, is not in the main checkout's records either. A records-only rule lets each of these be resumed with no envelope.
- "Agents this session started" needs session state that no hook input carries. The hook would have to read the transcript, whose shape changes between versions (ORV-87 samples), and a parse failure would have to fail closed anyway.
- `to` can be a name. The Agent tool accepts a `name` (ORV-85 recorded that the field is dropped from hook input in 2.1.282), and a name is never in the records. So a name cannot be told apart from an agent it may address. Blocking by id shape alone would let a name through.
- Nothing in this repo needs `SendMessage`. The `/ovl` loop speaks to a subagent only through an envelope, and to the owner through chat and question forms. No story uses agent teams or messages between sessions. The issue's "messages to other sessions or to `main` stay allowed if the spec needs them" is therefore answered: the spec does not need them.

What happens when `to` is a name (for example `reviewer`, `main` or `prober`): the call is blocked exactly like an id. The stderr says `to` names no recorded agent and that `SendMessage` is blocked whatever `to` names. When `to` equals an `agent_id` in a task folder's `agent.json`, the stderr also names that task's issue and `task_id`, so the main session knows which record to point the fresh envelope at. That lookup is a hint only: it never changes the verdict, and an error in it still blocks.

**`rework_of` stays a builder field.** The issue text says a re-check's `rework_of` names the earlier task. `envelope-guard` reads `rework_of` only on builder envelopes (it counts rework rounds), so on a reviewer it would carry no check and could be misread as a round. A reviewer re-check keeps the L-0008 form: `context_pointers` hold the absolute path of the previous review's `result.json` and the rework task's `result.json`. A builder rework keeps `rework_of`, as today. `envelope-guard` and `envelope.v1` do not change.

## Story

As the owner, I want every piece of work a subagent does to start from a checked envelope, so that no resumed agent runs with a brief nobody checked and a context nobody paid for on purpose.

## Rules and bounds

- **Always on.** Once registered, `resume-guard` runs in every Claude Code session in this repo, inside `/ovl` or not, as the other guards do (ORV-81 Rules and bounds).
- **Deterministic text rule.** The guard reads the tool name and that `to` is a string. It does not interpret the message, and no model is called. Nothing in this story is AI.
- **Verdict first.** The guard decides "block" before it touches a checkout or a record, as `worktree-guard` does. The record lookup (row 1's task hint) and the heartbeat come after, and neither can turn the verdict into an allow.
- **Records stay read-only.** The guard writes the heartbeat line and nothing under `.orivilo/runs/`. A blocked resume is not a round, does not close an envelope and does not change `metrics` output beyond the heartbeat.
- **Untrusted text.** `message`, `summary` and `to` are untrusted input. They are never echoed to stderr, written to the heartbeat, or used in a path (row 8). The lookup compares `to` with the `agent_id` values read from records; it never builds a path from `to`.
- **Fail closed.** Every non-zero exit is 2. The registration ends in `|| exit 2`, so a missing file or a missing `node` blocks (ORV-81 AC 47, 48).
- **One PR.** The whole story is one PR of about 400 changed lines (impact list below). If it runs over, the `metrics.mjs` note (row 16) splits into its own small PR that merges after this one, not before.

## Honest limits

- **The hook input is not recorded yet.** The `{to, summary, message}` shape comes from session transcripts (the `tool_use` input), not from hook stdin. Build step 1 records it. If the installed version gives the tool another `tool_name` in hook input, the `SendMessage` matcher never fires; the doctor probe (rows 11, 12) is what turns that silence into a stopped run.
- **The doctor needs the tool.** `SendMessage` may be a deferred tool that the main session must load before it can call it, and a session may not offer it at all. In the second case nothing can be resumed, but the doctor cannot tell that from a silent guard and stops the run (open question 2).
- **Other resume paths are not seen.** The guard covers the `SendMessage` tool only. If a Claude Code version adds a resume field to the Agent tool, `envelope-guard` passes unknown `tool_input` fields today, so a resume with a valid envelope would run (open question 3).
- **A session without these hooks** (hooks disabled, other settings, another client) escapes the guard, as it escapes every other guard.
- **The worktree's own copy runs.** Like every guard except `merge-guard`, `resume-guard` runs from the worktree's checkout, so a builder whose `write_set` lists a guard file can weaken it for that worktree until the merge (ORV-81 Honest limits).
- **No mid-task talk.** A running subagent can no longer be told anything, and a subagent cannot ask the main session through `SendMessage`. A subagent that needs a decision reports `blocked` with `needs_decision`, and the answer goes out in a fresh envelope. That is the cost of the owner's decision, and it is intended.
- **The hint can be stale.** Row 1's task hint reads the main checkout's records only. A subagent recorded in a stray worktree folder gets the row 2 message until `doctor.mjs migrate` runs. The verdict is the same.

## Out of scope

- Any allow-list for `SendMessage` (agent teams, messages between sessions).
- Changes to `envelope-guard`, `envelope.v1` or the rework round rules.
- A record of blocked attempts beyond the heartbeat line.
- Removing the fresh and resumed split from `metrics.mjs`: past sessions hold resumed runs, and the collector must still read them.
- `write-guard`, `merge-guard` and the other ORV-81 slices.

## Open questions (option, impact, default)

1. **Allow any `SendMessage` target?** Options: none; allow `main`; allow ids not in records. Impact: each allowance reopens a path to run an agent without an envelope (Decided in this spec). Default: none. A later story that needs agent teams adds an allow-list by an ADR.
2. **The doctor in a session with no `SendMessage` tool.** Options: the probe is required, so a missing tool stops the run; or `plan` marks the probe optional. Impact: optional means a renamed tool goes unnoticed, which is the failure the doctor exists to catch. Default: required. Build step 1 confirms the tool exists in the owner's 2.1.308 session; if it does not, the story stops for a decision.
3. **A resume field on the Agent tool.** Options: block any `tool_input` field `envelope-guard` does not know; block a named `resume` field; do nothing here. Impact: the first is a contract change to `envelope-guard` and would block fields Claude Code adds for other reasons. Default: do nothing in this PR. Build step 1 lists the Agent tool's input fields in the installed version in `samples.md`; if one resumes an agent, a follow-up issue is raised before the G3 packet.
4. **An ADR for the no-resume rule.** Options: amend ADR 0013 by a new ADR; or none. Impact: ADR 0013 decision 2 already says only `Explore` runs without an envelope, and this guard enforces that. Default: no ADR; this spec and the owner's ORV-87 answer are the record.
5. **Who updates the ORV-81 and ORV-87 specs.** Options: in this PR, by a `product` envelope with its own `write_set`; or a follow-up docs PR. Default: in this PR, so the specs never describe a guard set that does not exist.
