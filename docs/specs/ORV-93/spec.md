## Why

ORV-81 splits the AI team loop into slices, and slice B is next (`docs/specs/ORV-81/spec.md`, Rules and bounds, delivery slice 4; `docs/plans/master-plan.md`). Copy of the issue: `docs/specs/ORV-93/jira-issue.md`.

Two gaps stay open until it ships:

1. **Nothing stops the main session from doing the work or forging the proof.** No hook blocks a write to a deliverable (`packages/`, `apps/`), a guard file (`.claude/hooks/`, `scripts/ovl/`, `.claude/settings.json`) or a record (`.orivilo/runs/`, `.quality-gate/`). A session can still build alone and write its own `qa.json`, which is exactly what L-0006 records (`docs/lessons/L-0006-main-session-worked-solo.md`). The `ovl` skill's Honest limits name two concrete holes: any session can run `close-envelope.mjs --owner`, or append an `allow` line to `.orivilo/heartbeat.jsonl`, and so close a bound envelope as `abandoned` while its subagent may still run.
2. **There is no `qa` agent.** `envelope-guard` already knows the `qa` role, its required skills and `qa.v1`, and `result-recorder` already applies the `qa.v1` rules, but `.claude/agents/qa.md` does not exist. G3 has only the reviewer, who walks the AC in prose. There is also a defect in the existing wiring: `result-recorder` looks for a `qa.v1` screenshot in the qa's own checkout, while ORV-89 moved every record into the main checkout, and `doctor.mjs plan` stops a run while a worktree's own `.orivilo/runs/` holds a file.

Nothing in this story is AI. `write-guard` is a deterministic path and text rule; the `qa` agent is a model that runs checks, and its report counts only through the recorder rules that already exist.

### Decided in this spec

**The main session's one write under `.orivilo/` is `.orivilo/handoff.md`.** The owner's session hygiene keeps the live handoff in the main checkout's `.orivilo/handoff.md` (gitignored, injected by the owner's local SessionStart hook). No hook or script reads it, and it is never evidence, so it is not a record. The main session may write that exact file by Write or Edit, from any checkout of the project. Every other path under `.orivilo/` stays a record. A Bash write to the handoff and a subagent write to it are blocked.

**`docs/` is outside every protected set.** The main session keeps writing `docs/context/handoff.md`, `docs/plans/*.md` and the Jira copies `docs/specs/<KEY>/jira-issue.md` by Write or Edit. That is what ORV-81 Hooks already says (three sets, none of them `docs/`). Who should write a spec or an ADR is a process rule, not a guard rule (Honest limits, open question 3).

**Plain script runs stay allowed by their command, never by their target.** `metrics.mjs`, `doctor.mjs` and `close-envelope.mjs` write under `.orivilo/` from inside a node process, which no tool call shows. The main session may run `node scripts/ovl/<name>.mjs` and the quality gate as whole commands. A redirect, a chain, a pipe or a `--owner` makes the run a normal command, judged by the path rules. The one write the main session makes today by hand, the session metrics note `.orivilo/metrics/session-*.md`, moves into the script: `metrics.mjs session <id> --out <name>`, the same form `report --out` already has.

**Screenshots live in the main checkout.** `write-guard` and `result-recorder` resolve a screenshot path `.orivilo/runs/<ISSUE>/<task_id>/screenshots/<file>.png` against the records root (the main checkout), never against the checkout the qa or designer works in. That matches ORV-81 Records and keeps `doctor.mjs plan` from stopping on a worktree's `.orivilo/runs/`.

**Paths are judged after they are resolved.** A target path is made absolute against `cwd`, its nearest existing folder is resolved through `realpath` (so a link in `docs/` that leads into `packages/` is judged as `packages/`), and it is matched against the main checkout and each worktree under `.claude/worktrees/`, in lowercase, because the owner's disk is case-insensitive. A path outside every checkout of the project is in no protected set.

**Two write forms join the ORV-81 list.** A subagent Bash write form is a redirect (`>` or `>>` to a file; `2>&1`, `>&2` and `>/dev/null` are not writes), `tee`, `sed -i`, `cp`, `mv`, `rm`, `git apply`, any `git checkout` or `git restore` form (v1.2: with or without `--`, with a tree-ish such as `HEAD`, with `--source`), any `git switch`, `git stash` or `git reset` form (v1.3), and, new here, `ln` and `touch`. `ln` is the one that matters: a hard link to a guard file defeats `realpath`. A git form counts only when its text names a guard or record path (Naming, for Bash), so `git checkout -b feature/x` and `git checkout feature/ORV-1-x` stay allowed.

**What a redirect is (v1.3).** Before a command is checked for a redirect, the text inside quotes and every backslash escape is blanked, so a quoted `>` (as in `grep -n "=>" x`) is not a redirect. Blanking stops at the first `$(` or backtick that the shell would run: from there on the text is read as it is, so a `>` inside a command substitution, quoted or not, is still a redirect. Then the redirects that write no file are dropped: fd copies (`2>&1`, `>&2`, `>&-`) and the null device (`>/dev/null`, `2>/dev/null`, `>>/dev/null`, `&>/dev/null`). Any `>` left is a write. The same rule holds for a subagent's write forms and for the main session's plain reads (form (a)), so `ls .orivilo 2>/dev/null` is a plain read.

**A builder changes a guard file only with Write or Edit.** The exact-path exception in ORV-81 covers tool writes. A builder's Bash write form on a guard file is blocked, so the exception is one rule that a test can read, not a parse of every shell form.

**The builder grant holds only in the envelope's own worktree (v1.2).** The exception also requires the checkout that holds the target to equal the open envelope's `worktree`, both resolved. The same listed path in the main checkout or in another worktree is blocked. The PR 2 builder added this rule (reviewer finding F9); the spec records it so contract and code agree.

**`metrics.mjs session --root` is bounded (v1.2, corrected v1.3).** With `--out`, `session` accepts `--root <dir>` (the PR 2 builder added it for tests, reviewer finding F8) only when `<dir>` is the root of a main checkout: the records root that `git rev-parse --git-common-dir` gives for `<dir>` equals `<dir>` resolved through `realpath`. The note is then written to `<dir>/.orivilo/metrics/<name>.md`. A subfolder of a checkout (`packages/`, `scripts/ovl/`), a folder in no git checkout, and a worktree root exit 2; stderr starts `metrics: --root is not the root of a checkout` followed by the usage lines, and nothing is written. Without `--root`, the note goes under the records root of `cwd`, as before. Without the bound, an allowed run could write a `.md` file under `packages/` or `scripts/ovl/`. (v1.3 correction: v1.2 said a worktree root is accepted and quoted `--root is not a checkout of this project`; the code refuses a worktree root and prints the text above. It also does not check that the main checkout is this project's, Honest limits.)

## Story

As the owner, I want the main session unable to build, unable to weaken the guards and unable to write its own proof, and I want a separate `qa` agent to walk every acceptance criterion with evidence, so that G3 rests on work a role did and checks a role ran.

"Recorded sample" means hook stdin recorded from the installed Claude Code (row 33); a test never feeds an invented shape. ## Rules and bounds

- **Always on.** Once registered, `write-guard` runs in every Claude Code session in this repo, inside `/ovl` or not (ORV-81 Rules and bounds).
- **Deterministic.** The guard reads the tool name, the path field, the command text and the records. No model is called.
- **Three protected sets, as ORV-81 Hooks names them.** Deliverables `packages/`, `apps/` (main session blocked, subagents may write). Guard files `.claude/hooks/`, `.claude/settings*.json`, `scripts/ovl/`, `scripts/quality-gate.mjs`, `.github/workflows/`, the root `.gitignore` (every session blocked, except a bound builder's tool write to a path its open envelope lists exactly, inside the envelope's own `worktree`). Records `.orivilo/`, `.quality-gate/` in any checkout of the project (every session blocked, except the PNG rule and `.orivilo/handoff.md` for the main session).
- **Verdict order.** A tool write outside every protected set, and a Bash command that names no protected path, is allowed before any record is read. Records are read only to grant a subagent's exception, and an error there blocks. A Bash command that names nothing protected is never blocked for its `cwd`, as in `worktree-guard`.
- **Naming, for Bash.** Quotes and backslashes are removed and the text is lowercased. Then (v1.2) the paths are normalized before naming: repeated slashes collapse to one, and every `./` segment is dropped. The text names a protected path when it holds one of the set prefixes above, or a protected folder (`packages`, `apps`, `scripts/ovl`, `.claude/hooks`, `.github/workflows`, `.orivilo`, `.quality-gate`) followed by whitespace, a shell operator character or the end of the text, so `rm -rf scripts/ovl` names it. That is a text rule, not a parser, and it blocks toward safety: a harmless command that names a protected path in a message is blocked too.
- **Main-session Bash.** A command that names a protected path is blocked unless it is (a) a plain read: one or more of `cat`, `ls`, `head`, `tail`, `wc`, `jq`, `grep`, `sed -n`, `git diff`, `git log`, `git show`, `git status` (each `git` form may carry `-C <path>`), joined only by pipes into one another, with no write redirect, no `--output`, no `;`, `&&`, `||`, `$(`, backtick or newline; or (b) an allowed run: `node <prefix>scripts/ovl/<name>.mjs` with `<name>` in lowercase letters and hyphens, `node <prefix>scripts/quality-gate.mjs`, `pnpm quality-gate` or `pnpm run quality-gate`, followed only by plain arguments, on one line (v1.2: no newline and no carriage return anywhere in the command), where `<prefix>` is empty or the absolute path of a checkout of this project, and `--owner` never appears; or (c) one whole git write (v1.1): exactly one of `git add <paths>`, `git commit` with `-m "<message>"` or `-F <file>`, or `git push`, each `git` form may carry `-C <path>`, followed only by plain arguments, alone, with no `;`, `&&`, `||`, pipe, `$(`, backtick or write redirect. `<file>` after `-F` is in no protected set. A newline is allowed only inside the quoted `-m` message; the chain and expansion tokens block even there. `git add -A`, `git add .` and `git commit -a` stay allowed: they are plain arguments, and none of them holds a chain token. These forms change the index, the history and the remote, never a protected file in the working tree, so the main session can still stage, commit and push the changes a builder made under `Do not commit or push`.
- **Plain-read details (v1.2).** The command is split into its reads only on pipes outside quotes, before quotes are removed; a pipe or a backslash inside a quoted argument belongs to that argument. (v1.3) `sed` counts as a read only in one shape: `-n` as its first argument, then a script that is a line address or range (a number or `$`, optionally `,` and a second number or `$`) or one `/pattern/` (no `/` inside), followed directly by `p`, then only arguments that do not start with `-` (the files). So `sed -n 1,5p f`, `sed -n '3,$p' f` and `sed -n /verdict/p f` are reads; any other sed script, `w`, `W` and `e` included, any `-i`, `--in-place` or `-e`, and `sed` without `-n` first are not. A pipe may join that sed to the other reads. `tail` and `wc` are reads with any arguments that pass the other form (a) checks.
- **No process substitution (v1.2).** No form (a), (b) or (c) allows `<(` or `>(`, the same as `$(`: the shell runs the inner command, which may write.
- **Subagent Bash.** A command is blocked when it holds a write form (Decided in this spec) and names a guard file or a record path. The PNG exception: a single `cp`, `mv` or redirect whose target ends `.png`, with every protected path it names inside the writer's own `screenshots/` folder in the main checkout, from a `qa` or `designer` bound to an open envelope.
- **Untrusted text.** File content, `old_string`, `new_string` and the command are untrusted. stderr names only the set and the repo-relative path of a protected target, never content and never the whole command. The heartbeat holds the six `beat()` fields only (row 26).
- **Fail closed.** Every non-zero exit is 2, and the registration ends in `|| exit 2` (ORV-81 AC 47, 48).
- **Records stay read-only.** The guard writes its heartbeat line and nothing else.
- **Two PRs, qa first.** The work splits vertically into two PRs on ORV-93, each about 400 changed lines (open question 5). PR 1, `feature/ORV-93-qa-agent`: rows 31, 32, 34 and the step 2 line of row 35. PR 2, `feature/ORV-93-write-guard`: rows 1 to 30, 33 and the rest of row 35. PR 1 merges first, so a fresh `qa` agent walks PR 2 at its G3.

## Honest limits

- **Not a sandbox.** A process a session runs writes files itself, and the guard sees only the tool call and the command text. The main session can write a script to a scratchpad and run `node /tmp/x.mjs`, which names no protected path, and that script can write a record. The guard closes the direct forms, the ones L-0006 and the `ovl` skill name, not every form.
- **A text rule misses what the shell builds.** A path split across `cd` (`cd scripts && rm ovl/a.mjs`), built by expansion or a glob, or decoded from an encoded string is not seen, as in `worktree-guard`.
- **The text rule also blocks harmless commands.** A subagent's `node --test scripts/ovl/a.test.mjs > /tmp/out` is blocked (a redirect and a guard path); it drops the redirect. A main session's `git commit -m "fix packages/ x && y"` is blocked, since the chain token blocks even inside the message; the session rewords it. A whole `git commit -m "fix packages/ x"` is allowed (form (c)).
- **A whole git write still moves protected content.** Form (c) lets the main session stage and commit any working-tree change, a guard file included, and push it. The guard keeps the main session from writing that change; it does not judge what gets committed. That check is the reviewer's, the qa's and, from slice C1, `merge-guard`'s `write_set` union. A git hook that writes files would run inside the git process unseen; this repo has none today.
- **The main session can still edit a spec, an ADR, an agent or a skill.** `docs/` and `.claude/agents/`, `.claude/skills/` and `.claude/rules/` are outside every protected set. The `qa` recorder reads the AC table from the qa's own checkout, so a weakened table would show in the PR diff, and from slice C1 on outside the `write_set` union (open question 3).
- **`metrics.mjs session --root` checks the shape, not the project (v1.3).** It accepts the root of any git main checkout, not only this project's, so an allowed run can write `<other repo>/.orivilo/metrics/<name>.md`. That file is outside every checkout of this project and in no protected set; a subfolder such as `packages/` or `scripts/ovl/` is still refused.
- **Quotes are blanked only up to the first command substitution (v1.3).** After a `$(` or a backtick, a quoted `>` counts as a real redirect, so a subagent's harmless `echo "$(date)" "a>b" scripts/ovl/x` is judged a write form. That blocks toward safety.
- **The worktree's own copy runs.** A builder whose `write_set` lists `scripts/ovl/write-guard.mjs` can weaken the guard for that worktree until the merge (ORV-81 Honest limits).
- **PR 1 has no qa walk.** The PR that adds the `qa` agent cannot be walked by it, so its G3 rests on the gate, the reviewer and CI. (v1.2 correction) No session restart was needed: the `qa` agent was offered right after its file was written (ORV-93 comment 10088).
- **The handoff is context, not evidence.** The owner's local SessionStart hook injects `.orivilo/handoff.md` into each new session. The main session writes it, so a later session reads the earlier session's words; no hook treats it as a record.
- **Version gap.** Samples come from the `claude` on PATH; the owner's IDE session may run a newer build. A missing path field fails closed (row 22), and the doctor probe turns a silent guard into a stopped run (rows 29, 30).
- **A session without these hooks** escapes the guard, as it escapes every other guard.
