Until C1 ships, nothing blocks a merge:

1. **A PR merges on the session's own say-so.** `gh pr merge` runs whether or not a `qa.json` approve, a `reviewer.v1` approve, a passing gate and green checks exist for the head being merged. The records exist (slice A3 and ORV-93 write them), but nothing reads them at the moment that matters.
2. **Direct pushes and API merges are open.** `git push origin HEAD:develop`, `gh api -X PUT .../pulls/<n>/merge` and a GraphQL `mergePullRequest` move `develop` or `main` with no check at all.

Nothing in this story is AI. `merge-guard` is a deterministic text rule, and `merge-check` is a deterministic read of the run records, the PR as GitHub reports it, and its checks.

### Decided in this spec

**Three stages, each with one source of code.** `merge-guard` judges a Bash call in three stages:

1. The **text stage**, `scripts/ovl/merge-guard.mjs`, from the session's own checkout. It reads only the command text and, for a `git push`, the current branch. It makes no network call and reads no record. It decides every call except one whole `gh pr merge` (below): it blocks the always-blocked forms and allows the rest.
2. The **export stage**, `scripts/ovl/develop-export.mjs`, from the session's own checkout. It runs only for a whole `gh pr merge`. It builds the develop export (below) and fails closed when it cannot.
3. The **records stage**, `scripts/ovl/merge-check.mjs`, run from the develop export, never from the branch. It reads the PR, its checks and the records, and says yes or no.

So AC 59 and 74 hold for the checks that read records: the branch under review never runs its own `merge-check.mjs`. The text rules run from the branch, like the launcher itself, whose risk the owner accepted (ORV-81 open question 13); weakening either is a change to a guard file, which needs an exact `write_set` entry to write and the owner's approval record to merge (open question 1).

**The launcher is `.claude/hooks/merge-guard.mjs`.** ORV-81 Hooks names `.claude/hooks/merge-guard.sh`. A node launcher like `write-guard.mjs` and `worktree-guard.mjs` uses the shared `runHook` runner, its heartbeat and its fail-closed path, so it is one line and testable with `hook-test-kit.mjs`. It is registered in the existing PreToolUse `Bash` entry.

**Only one whole `gh pr merge` reaches the records stage.** After quotes and backslashes are removed, runs of whitespace collapse and the text is lowercased, a command that holds `gh pr merge` must be exactly `gh pr merge <n>` followed only by these flags: one of `--squash`, `--merge`, `--rebase` (or `-s`, `-m`, `-r`), optionally `--delete-branch` (or `-d`), and `--match-head-commit <sha>` with a 40-hex SHA. `<n>` is a whole number of 1 or more. No `;`, `&&`, `||`, pipe, `$(`, backtick, `<(`, `>(`, redirect or newline outside quotes. Any other `gh pr merge` form is blocked in the text stage: no number (the current branch's PR), `--auto`, `--admin`, `--repo` or `-R`, `--subject`, `--body`, `--body-file`, an unknown flag, or a chain. `gh pr merge 0`, the doctor probe, is blocked there too, with no network call.

**`--match-head-commit` is required.** The records stage judges the head GitHub reports, and GitHub refuses the merge when the head is no longer that SHA. Without it, a push between the check and the merge would merge a head nobody checked. The records stage also blocks when the flag's SHA differs from `headRefOid`.

**The develop export lives in the records.** The export stage resolves develop's SHA with `git ls-remote origin refs/heads/develop` (never the local `origin/develop` ref), runs `git fetch origin <sha>`, and extracts `git archive <sha> scripts/ovl` into `<main>/.orivilo/exports/<sha>/`, where `<main>` is the records root. It extracts into an aside folder first and renames it into place, so a half-written export is never used, and it reuses `<main>/.orivilo/exports/<sha>/` when that folder exists. Under the main checkout, node finds `<main>/node_modules` by walking up, so the export runs with the repo's dependencies (ORV-81 Hooks). The folder is gitignored (`.orivilo/`) and a record path for `write-guard`, so no tool call writes it. When the export has no `scripts/ovl/merge-check.mjs`, the stage blocks: that is the C1 bootstrap, and the owner merges the C1 PR in the GitHub web UI (ORV-81 open question 11).

**The records stage runs as a process.** The export stage runs `node <main>/.orivilo/exports/<sha>/scripts/ovl/merge-check.mjs <n> --head <sha>` with the hook input's `cwd`. Exit 0 allows the merge; any other exit blocks, and its stderr lines become the block reasons. The main session may run the same script from its own checkout as a pre-check, `node scripts/ovl/merge-check.mjs <n> --head <sha>`, which `write-guard` form (b) already allows; only the hook's run from the export counts.

**What the records stage reads.** The PR from `gh pr view <n> --json number,title,baseRefName,headRefName,headRefOid,files,changedFiles`, its checks from `gh pr checks <n> --json name,state,bucket,description,link,workflow` (stdout is read whatever the exit code, since `gh pr checks` exits non-zero when a check fails or waits; empty or unparsable stdout blocks), and the records under the main checkout's `.orivilo/`, the owner approval and waiver files included. It reads no PR comment and no repo owner login: since v1.1 nothing it decides rests on them. For story titles it fetches the PR head with `git fetch origin refs/pull/<n>/head` and reads files with `git show <headRefOid>:<file>`. The file list is the PR's own, never `git diff origin/develop...`, so the local `origin/develop` ref plays no part. When `changedFiles` is larger than the length of `files`, GitHub cut the list, and the stage blocks.

**The issue is the head branch key.** The issue is `ORV-<n>` from `headRefName` in the form `<type>/ORV-<n>-<slug>`, as `envelope-guard` reads it. The PR title must start with the same `ORV-<n>:` (AGENTS.md iron rule 2). A head branch with no key, or a title with another key, blocks.

**The gate evidence is the gate record, not the report file.** ORV-81 Hooks says the merge reads "the gate report in the qa task's worktree". That file is rewritten by every later gate run in that checkout, so at merge time it may describe another commit. The records stage reads the gate records instead: the latest `.orivilo/runs/<ISSUE>/gates/*.json` (by `recorded_at`) whose `sha` equals `headRefOid` must have `ok: true`, `dirty: false` and `steps_source: "gate"`. Those records are written once, exclusively, by `result-recorder` from the main session's own gate run (Rework loop step 2). The qa's own gate run is already checked when `qa.json` is recorded (`approveProblems` in `result-recorder.mjs`), so a merge rests on two gate runs, the main session's and the qa's.

**Which approve counts.** Records are ordered by their `recorded_at`.

- `qa`: the latest `qa.json` of the issue must have `report.verdict` `approve`, `report.head_sha` equal to `headRefOid` and `report.pr` equal to `<n>`. An older approve on the same head does not count once a later `qa.json` exists.
- `reviewer`: among the issue's `result.json` records with `contract` `reviewer.v1`, from an envelope with role `reviewer`, the latest whose `report.head_sha` equals `headRefOid` must have `report.verdict` `approve`. A designer's `reviewer.v1` does not count.

**Every check passes, with one waiver.** Every entry of `gh pr checks` must have `bucket` `pass`. A `pending`, `fail`, `cancel` or `skipping` entry blocks, and so does a list with no checks at all. The one exception is the owner's rule: an entry whose `name` starts with `Vercel` and whose `bucket` is `fail` is waived when its `description` starts with `Deployment rate limited` and the owner's waiver file for the PR names that check on `headRefOid` (below). The recorded sample confirms the check name and the description text (row 43); a different text is a deviation for the builder to report, not a guess.

**How the waiver is recorded.** `.orivilo/owner-waivers/<n>.json` in the main checkout, `{ "by": "owner", "pr": <n>, "head_sha": "<sha>", "checks": ["<check name>"], "at": "<ISO time>" }` (open question 6, answered). It counts when `by` is `owner`, `pr` equals `<n>`, `head_sha` equals `headRefOid`, `checks` is a non-empty list of strings and `at` is a valid time. A check is waived only when its `name` is in `checks` exactly, starts with `Vercel`, has `bucket` `fail` and a `description` that starts with `Deployment rate limited`. A name in `checks` that is not such a check waives nothing: that check is judged like any other. A waiver covers that head SHA only; after a new push the owner writes a new file, which the same command writes over the old one. It never covers a failed build, a failed Actions check or a check that waits. A PR comment, whoever wrote it, is not a waiver, so the records stage reads no comments. The owner writes the file with this one line, from a terminal outside Claude Code, in the main checkout, with `<n>`, `<sha>` and `<checks>` filled in; `<checks>` is the JSON list of the rate-limited check names that the pre-check prints, for example `["Vercel"]`:

```bash
mkdir -p .orivilo/owner-waivers && printf '{"by":"owner","pr":%s,"head_sha":"%s","checks":%s,"at":"%s"}\n' <n> <sha> '<checks>' "$(date -u +%Y-%m-%dT%H:%M:%SZ)" > .orivilo/owner-waivers/<n>.json
```

`write-guard` already blocks every session's write under `.orivilo/` (its record set: a Write, an Edit, or a Bash redirect or `tee` to a record path), so, like the approval record, the waiver file can only come from the owner's terminal (row 7). No new rule is added to `write-guard` or to the text stage for it.

**The owner approval record and its command.** `.orivilo/owner-approvals/<n>.json` in the main checkout, `{ "by": "owner", "pr": <n>, "head_sha": "<sha>", "at": "<ISO time>" }` (ORV-81 Records). It counts when `by` is `owner`, `pr` equals `<n>`, `head_sha` equals `headRefOid` and `at` is a valid time. The G3 packet prints this one line for the owner to run from a terminal outside Claude Code, in the main checkout, with `<n>` and `<sha>` filled in:

```bash
mkdir -p .orivilo/owner-approvals && printf '{"by":"owner","pr":%s,"head_sha":"%s","at":"%s"}\n' <n> <sha> "$(date -u +%Y-%m-%dT%H:%M:%SZ)" > .orivilo/owner-approvals/<n>.json
```

`write-guard` blocks that command in every Claude Code session (a redirect to a record path), so only the owner's terminal runs it. A new push needs a new approval, which the same command writes over the old file.

**Docs-only PRs need no qa run.** A PR is docs-only when every changed file ends in `.md` and is in no protected set (`write-guard`'s deliverable, guard-file and record sets). Improvement runs (`.claude/skills/ovl/SKILL.md`, step 5), handoff and plan updates, and spec revisions are of this kind; they have no stories and no AC walk of their own, and a qa walk would walk the issue's whole AC table for a markdown change. For a docs-only PR into `develop` the records stage needs, instead of `qa.json`, the gate record and the screenshots: a `reviewer.v1` approve on `headRefOid` (the reviewer rule above) or an owner approval record for `headRefOid`, plus every other check that applies to every PR (checks, issue key, file list, `write_set` union). A PR with one file outside that definition, a `.md` under `packages/` included, needs the full set of records.

**The `write_set` union.** The union is every `write_set` entry of every envelope of the issue that was bound (has `agent.json`), whatever its role and however it closed. A denied envelope never ran, so its entries do not count. An entry is an exact path or a glob, matched with `path.posix.matchesGlob` (Node 22; `*` does not cross `/`). Three main-session paths count as listed for every PR of the issue, because the main session writes them by Write or Edit (ORV-93, Decided: `docs/` is outside every set): `docs/context/handoff.md`, `docs/plans/*.md` and `docs/specs/<ISSUE>/jira-issue.md` for the PR's own issue. Every other changed file must match the union (open question 5).

**A merge into `main`.** Base `main` is allowed only when `headRefName` is `develop` (the release PR), every check passes under the rule above, and an owner approval record exists for `headRefOid`. The approval record is the owner's yes for the release, which ORV-81 called a process rule the hook cannot see; the release PR has no `qa.json`, no reviewer and no `write_set` union of its own. Any base other than `develop` or `main` blocks.

**The guard-file list is shared.** `scripts/ovl/write-guard.mjs` exports its `GUARD_PATH` pattern, and `scripts/ovl/result-recorder.mjs` exports `storyTitle` and `storyPrefix`. `merge-check.mjs` imports them from the same export, so the merge judges guard files and story titles exactly as the develop copy of `write-guard` and `result-recorder` do. Neither export changes the behaviour of its module.

## Story

As the owner, I want a merge into `develop` or `main` to happen only when the records prove the head was built, checked by a qa, approved by a reviewer and green in CI, and only with my own approval when it changes a guard file or releases to `main`, so that I stop checking every PR's files and records by hand.

## Rules and bounds

- **Always on.** Once registered, `merge-guard` runs on every Bash call in every Claude Code session in this repo, inside `/ovl` or not (ORV-81 Rules and bounds).
- **Deterministic.** The guard reads the command text, the current branch, the PR and its checks as `gh` reports them, and the records. No model is called.
- **Cheap for every other call.** The text stage decides every Bash call except a whole `gh pr merge`, with no network call and no record read (row 3). A command that holds none of `git push`, `git update-ref`, `git remote`, `git config` and the word `gh` is allowed before any parse.
- **Naming, for the text stage.** Quotes and backslashes are removed, runs of whitespace collapse to one space, and the text is lowercased, as in `worktree-guard` and `write-guard`. It is a text rule, not a parser, and it blocks toward safety: `sh -c 'git push origin HEAD:develop'` is caught (row 1), and so is a harmless command that holds a blocked form in a message.
- **Push targets.** The words after each `git ... push` (each segment between `;`, `&&`, `||`, `|` and newlines) are read as options, a remote and refspecs. A refspec `src:dst` targets `dst`; a refspec with no `:` targets itself; a leading `+` and `refs/heads/` are dropped; `HEAD` and `@` are the current branch of the checkout the command names (`-C <path>`, else `cwd`); a push with no refspec targets the current branch; `--delete` or `-d` targets each name after it; `--all` and `--mirror` always block. A target `develop` or `main` blocks. `--tags` alone moves no branch. A push whose target needs the current branch, in a checkout that cannot be read, fails closed.
- **API forms.** The text holds `gh api` and a path with `/merge` (which covers `/merges`) or `/git/refs`; or `gh api graphql` and one of `mergepullrequest`, `enablepullrequestautomerge`, `mergebranch`, `updateref`, `createref`, `deleteref` (the lowercased mutation names), or a query read from a file or stdin (`=@`, `--input`). A GET on such a path is blocked too.
- **Remote forms.** `git update-ref` with `refs/remotes/origin/` in its text, `git remote add`, `git remote set-url`, and any `git config` whose text holds `remote.`, reads included.
- **No waiver forms in the text stage.** A comment is not a waiver, so `merge-guard` has no rule for `gh pr comment`, `gh issue comment`, `gh pr review` or `gh api .../comments`. The waiver file is a record path, which `write-guard` already guards (row 7).
- **Always blocked, whoever asks.** The forms in rows 1, 2 and 4 to 6, and a session's write of a waiver or approval file (row 7, by `write-guard`), from the main session and from every subagent. The release agent pushes its feature branch and merges with `gh pr merge`; it never pushes `develop` or `main`.
- **Records stay read-only.** The guard writes its heartbeat line and the export folder; `merge-check.mjs` writes nothing. Neither writes, edits or closes a record.
- **Untrusted text.** The command, the PR title, check names, check descriptions and file contents are untrusted. They are read as data, never run and never echoed in full (rows 35, 38). stderr names the rule, the issue key, the SHAs, file paths and check names only.
- **Fail closed.** Every non-zero exit is 2, and the registration ends in `|| exit 2` (ORV-81 AC 47, 48). A step that cannot run (no network, no `gh`, a record that cannot be read) blocks the merge. It never blocks a call the text stage allows.
- **No fallback.** When develop's export has no `merge-check.mjs`, a `gh pr merge` is blocked, never judged by the branch's copy (ORV-81 open question 11, answered).
- **One PR.** The slice ships as one PR into `develop`, `ORV-95: merge-guard ...`, built by the builder tasks in Build order, one deliverable each (open question 2). The owner merges it by hand in the GitHub web UI after reading its G3 packet. Its qa walks every row above.

### What still merges, and how

- A code PR into `develop`: the main session or the `release` agent runs `gh pr merge <n> --squash --delete-branch --match-head-commit <sha>` after the qa and the reviewer approve the pushed head, the main session's gate run passes on it, and CI is green. A guard-file PR also needs the owner's approval record for that head.
- A docs-only PR into `develop`: the same command, after a reviewer approve or the owner's approval record for the head, with CI green.
- A PR with a rate-limited Vercel check: the same, after the owner runs the waiver command for that head and those checks from the owner's own terminal. A PR comment does not waive a check.
- The release PR into `main`: `gh pr merge <n> --merge --match-head-commit <sha>` after the owner writes the approval record for the release PR's head (ADR 0011; G5 stays the owner's).
- The C1 PR itself: the owner, in the GitHub web UI. The first PR into `develop` after it is the first guarded merge.
- A pre-check before any of these: `node scripts/ovl/merge-check.mjs <n> --head <sha>` from the main session (`write-guard` form (b)); it prints every missing record at once.

## Honest limits

- **The hooks are the only merge barrier.** GitHub branch protection and rulesets are not available on this repo's plan (HTTP 403), so a merge in the GitHub web UI or from another client is not guarded. The owner's own hand merge of the C1 PR is one.
- **The text rules and the launcher run from the session's checkout.** A builder whose `write_set` lists `scripts/ovl/merge-guard.mjs`, `scripts/ovl/develop-export.mjs`, `.claude/hooks/merge-guard.mjs` or `.claude/settings.json` can weaken them for its own worktree until the merge, and so stop the develop checks from running for that worktree's sessions. The merge of such a change needs the owner's approval record, but only when the merging session's guard is intact. The owner accepted this risk (ORV-81 open question 13).
- **A text rule misses what the shell builds.** A target built by expansion (`git push origin HEAD:$B`), a `cd` before the push (`cd ../other && git push`), an alias, or an encoded command piped to a shell is not seen, as in `worktree-guard`. A GraphQL mutation the list does not name, or one whose name is built outside the command text, is not caught.
- **The approval record and the waiver are files.** `write-guard` blocks every tool write to `.orivilo/owner-approvals/` and `.orivilo/owner-waivers/`, but a script a session runs can write the same files, as ORV-81 Honest limits says for every record. The waiver's damage is bounded: it covers only a check named `Vercel...` that GitHub reports as `Deployment rate limited` on that head, never a failed build or a failed Actions check. Since v1.1 a comment a session posts with the owner's `gh` login waives nothing.
- **The export trusts its folder once written.** A process can change `<main>/.orivilo/exports/<sha>/` after it is extracted; no tool call can. The export also runs with the checkout's own `node_modules`, which is not a guard file.
- **The launcher trusts `origin`.** The text stage blocks the `git remote` and `git config` forms that change it; a direct edit of `.git/config` by a process is not caught.
- **Docs-only PRs skip the qa and the gate record.** CI is their only check that runs, and a change to `.claude/agents/`, `.claude/skills/` or `.claude/rules/` (all markdown, in no protected set) merges on a reviewer's or the owner's approve. A PR that adds a non-markdown file is not docs-only.
- **A merge needs the network.** The records stage calls `gh` and `git ls-remote`; offline, every `gh pr merge` is blocked. Other Bash calls are not affected.
- **The file list stops at what GitHub returns.** A PR whose `files` list is cut (`changedFiles` larger) is blocked, not judged; such a PR is split.
- **`looked_at` and the screenshot `note` stay the qa's own statement.** The records stage checks that the screenshots exist in `qa.json` for each title, not what they show; the recorder checked the PNG files when `qa.json` was written.
- **Moves to G3, Staging and Done are not guarded here.** `g3-check` is slice C2.
- **A session without these hooks** escapes the guard, as it escapes every other guard.
