## Why

ADR 0004 has a person talk to the engine where they are working: press "/" at a point on the board, or open a chat in the sidebar, and get the answer back as a node on the board, linked to the node it is about. ORV-45 part 1 shipped the base parts (Toast, Progress, Tag) and part 2 the TaskBar. Part 3 is the chat surface itself, so that asking about the board stays on the board and every answer stays traceable to the node it came from (the Intent Engine's promise: every artifact traceable to its source reasons).

This is a design-system component only. No chat model is connected (ADR 0009 puts `chat` on its own pinned model in a later story). The component takes its replies from a host callback, and every reply carries a basis, `rules` or `mock`, that the UI shows on the reply and on the node it becomes (AGENTS.md rule 4). **What the MVP simulates:** in stories the host is a fixture that streams canned or rule-based text with a delay; nothing interprets language. No copy, label or story says AI answered.

Not a guard spec; the guard frame (L-0012) does not apply.

## Story

As a Studio user working on the board, I want to ask the engine a question at the spot I am looking at or in a side panel, point at nodes with @, watch the reply arrive, and find the reply on the board as a node linked to what I asked about, so that answers never get lost in a chat log and I can always see where each one came from and that it was worked out by rules or is mock data.

## Public API sketch (new contract, impact below)

```ts
/** Where a reply comes from today. A later story adds a real source with its adapter (ADR 0009). */
export type ChatBasis = "rules" | "mock";

export interface ChatRequest {
  /** What the person typed, trimmed, without the @ queries. */
  text: string;
  /** Mentioned node ids still on the board, in the order picked (slice C). */
  mentions: readonly string[];
  /** The node the chat is about: the one selected alone when the message is sent, if any. */
  contextNodeId?: string | undefined;
  /** Flow position the at-cursor form opened at (slice D). */
  position?: { x: number; y: number } | undefined;
}

/** One snapshot of the reply: the whole text so far. The last snapshot is the reply. */
export interface ChatReply {
  text: string;
  basis: ChatBasis;
}

interface CanvasChatBase {
  /** What answers today; shown as a notice before the first message. */
  basis: ChatBasis;
  /**
   * The host's answer. Yields snapshots while it streams; ends to finish; throws to fail.
   * The signal aborts when the person presses Stop or the chat unmounts.
   */
  onAsk: (request: ChatRequest, signal: AbortSignal) => AsyncIterable<ChatReply>;
  /** A finished reply. The host places it (`placeReply`) and returns the new node id (slice B). */
  onReply?: ((reply: ChatReply, request: ChatRequest) => string | undefined) | undefined;
  /** Controlled mentions (slice C): the shell adds one on `node.mention`. */
  mentions?: readonly string[] | undefined;
  defaultMentions?: readonly string[] | undefined;
  onMentionsChange?: ((ids: readonly string[]) => void) | undefined;
  className?: string | undefined;
}

export type CanvasChatProps =
  | (CanvasChatBase & { variant: "sidebar"; onClose?: (() => void) | undefined })
  | (CanvasChatBase & {
      variant: "at-cursor";
      /** Flow coordinates from `board.open-chat-here`. */
      position: { x: number; y: number };
      /** Escape and the close button call it; the shell unmounts the form. */
      onClose: () => void;
    });

/** Pure helper beside `placeBlock` (slice B): the graph with the reply as a node linked to its sources. */
export function placeReply(
  graph: Graph,
  reply: {
    id: string;
    title: string;
    text: string;
    basis: ChatBasis;
    sources: readonly string[];
    position?: { x: number; y: number };
  },
): Graph;
```

`NodeContent` gains `basis?: ChatBasis` (slice B): a node that carries it shows the basis tag in its header. The component stores only the session's transcript, the draft text, the pending request and local mentions; the board graph is the shell's. An at-cursor chat without `position` or `onClose`, or a reply without `basis`, does not type-check. Exact names may change in G2 design; a change after G2 bumps this spec.

## Rules and bounds

- Replies come only from `onAsk`. The component never makes text up, never calls a network, a model or a server action, and keeps no transcript after unmount.
- Every reply shows its basis, from the reply's own `basis`, never from the chat's `basis` prop. A mismatch between the two is shown as it is, not corrected.
- One request at a time per chat. Loading blocks repeat submission (DESIGN.md §7).
- A stopped or failed reply is never placed as a node; only a reply whose iterable ended is passed to `onReply`.
- Graph changes go through the shell: the component calls `onReply` and the shell applies `placeReply`, like `placeBlock` (CanvasBoard is controlled). `placeReply` is pure, deterministic for the same input and puts no time or random value in the graph; the caller gives the id.
- A reply node is a `note` kind with the reply as its `summary` and `basis` set; it is never marked done, approved or trusted, and no rating or confidence appears (DESIGN.md §9 item 11).
- Colour roles (DESIGN.md §8): Send is the ask action, `action.intent`; the failure uses `feedback.danger`; mention chips are neutral tags, never selection colour; the streaming mark uses `status.running`. No new semantic token; needing one is a contract change that bumps this spec.
- Thai IME: Enter during composition never sends; "/" and "@" are read from the typed character, not the key position.
- Text length: the textarea uses Textarea's soft `maxLength` of 2,000 graphemes with its counter; over the limit Send is `aria-disabled` and the counter says by how much.
- Untrusted text: question and reply text render as plain text, never as HTML or markdown (AGENTS.md: model output is data).
- No middot and no em dash in any copy, story, fixture or reply fixture.

## Out of scope

- A real chat adapter, a pinned model, a server action, streaming over the network, prompts and any "by AI" label (ADR 0009 chat story).
- Saving the transcript, chat history across sessions, several threads, editing or deleting a sent message.
- Rendering markdown, code, images or links inside replies; attachments; voice.
- Replies that change existing nodes or run commands (the agent controlling the board).
- Wiring the chat into the Studio page in `apps/web` and a shell button or shortcut to open the sidebar.
- Rich inline mention tokens inside the textarea (mentions are chips above it).
- `node.generate`, `node.generate-variation`, `node.stop`, `panel.toggle-task-bar` and `panel.jump-to-node`, which are also tagged E4-5 but belong to the generation and task-bar wiring stories.
