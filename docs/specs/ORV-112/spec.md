# ORV-112: rate limits that hold across Vercel instances

## Why

ADR 0015 decision 4 and `.claude/rules/security.md` rule 6 require sign-in and every AI job to be rate limited, with counters in a store every server instance shares. Today nothing holds:

- **Better Auth's limiter counts in process memory.** `packages/auth/src/config.ts` sets `rateLimit: { enabled: true }` and no storage, so Better Auth 1.7.12 picks `storage: "memory"` (`better-auth/dist/context/create-context.mjs`, line 175). On Vercel each function instance has its own map, so a caller spread over instances is never stopped.
- **`signInWithGoogle` skips that limiter anyway.** It calls `auth().api.signInSocial` directly from a server action (`apps/web/app/account/actions.ts`). Better Auth's limiter runs in its HTTP router (`onRequestRateLimit`), so a server-side `auth.api` call is never counted.
- **No limit on AI reading.** `readBriefWithAi` (`apps/web/app/directions/actions.ts`) calls the paid `interpret` model on every click by a signed-in person. A reading costs about 1.5 US cents (ADR 0009, Consequences), and the only cap is the key's monthly credit limit, shared by everyone (ADR 0009 point 7). One stuck client or one person can spend it for the whole environment.
- **No limit on writes or import.** `saveDirection`, `approveDirection` and `importDirection` run a database transaction (import also replays the resolver) per call with no bound.
- **No client IP is confirmed as one the caller cannot choose.** Better Auth reads `x-forwarded-for` by default and falls back to one shared bucket when it finds no single IP, and nothing has checked on a deployment that the value is set by Vercel and not by the client. Our own actions read no IP at all.

**Frame.** This is a server-side control, not a hook that judges text. The counters live in our Postgres and are written only by server code through the restricted `orivilo_app` role (ADR 0002); the browser holds no counter and no credential to the store. A signed-in person cannot reset their own count. Per IP limits rest on one thing outside our code: Vercel's edge overwrites `x-forwarded-for` with the caller's public IP to prevent spoofing (K-0015), which row 21's staging probe checks before slice B passes G4. It is a bound against abuse by a single person or a single network, not against a distributed attack from many IPs and many accounts; that needs an edge firewall rule (Vercel firewall), which is out of scope.

**What is real.** The limits are real server checks with tests. The AI reading the person keeps when limited is the existing rule-based reading (ADR 0009 point 3), labelled as rules, as today. Nothing here claims conformance to the OWASP LLM Top 10 (ADR 0015 decision 13); it adds the rate limit half of the LLM06:2026 row, with the tests named below.

## Story

As the workspace owner paying for AI and hosting, I want each person's AI readings, saves and imports, and each network's sign-in attempts, capped by counts that every server instance shares, so that one person, one stuck tab or one script cannot burn the AI budget or flood the database, and the person who hits a cap is told in Thai or English how long to wait.

Windows are fixed and aligned: a 10 s, 60 s or 10 minute window starts at a multiple of its length in Unix seconds, an hour at the top of the hour, a day at 00:00 Asia/Bangkok (UTC+7, Thailand has no daylight saving, so 17:00 UTC). `Retry-After` is the whole seconds until the window that refused the call ends, rounded up, at least 1. When more than one window of a limit refuses, the later end wins. The windows of one limit nest (a longer window's length and offset are whole multiples of the shorter one's), which the helper checks when it is built.

Reads (`listDirections`, `openVersion`, `exportVersion`) and the locale action (`apps/web/i18n/actions.ts`) are not limited in this story.

## The store and the helper

- **One table** in our Postgres, `rate_limit_counter`: `key text` (at most 200 characters), `window_start bigint` (Unix seconds), `window_end bigint` (Unix seconds, exclusive), `count integer` (at least 1), primary key (`key`, `window_start`, `window_end`), and an index on `window_end`. The primary key holds `window_end` because `ai-read`'s hour and day windows share one key and both start at 17:00 UTC once a day; without it they would land on one row and count every call twice in that hour (finding F1).
- **Two migrations**, as the repo pairs a generated table file with a hand-written access file (finding F11): `0004_rate_limits.sql`, generated by `drizzle-kit generate` and not hand-edited, and `0005_rate_limits_access.sql`, a custom migration. 0005 grants `SELECT, INSERT, UPDATE, DELETE` to `orivilo_app`, enables row security with one policy for `orivilo_app` with `USING (true) WITH CHECK (true)` as on the auth tables (the rows are not workspace data), and revokes everything from `PUBLIC` and from `anon`, `authenticated` and `service_role` where those roles exist, so no other role holds a grant whatever default privileges the host applies (finding F7).
- **Keys** are `<limit name>:u:<user id>` for a person, `<limit name>:ip:<subject>` for an IP, and `auth-http:ip:<subject>:<window>x<max>` for Better Auth (for example `auth-http:ip:<subject>:10x3`). The user id is Better Auth's own id from the server session, never a value from the client.
- **The IP subject** is one of: the hex HMAC-SHA-256 of the normalised IP under a key derived from `BETTER_AUTH_SECRET` for the label `orivilo/rate-limit/ip/v1` (finding F3, since the secret already keys `sealReading`); `local` off Vercel; `unknown` on Vercel with no usable header. No raw IP is stored, and no new environment variable is added. Rotating the secret resets every IP bucket, which is accepted. A hashed IP is still pseudonymous personal data; rows live at most 24 hours past their window's end.
- **One helper**, `createRateLimiter({ db, now, pruneEveryMs, timeoutMs })` in `packages/auth` (it already holds the access helper and talks to the database), whose `consume(limit, subject)` every limited server action uses. The clock and database are injected for tests. `consume` never throws: it returns allowed, limited with `retryAfter`, or unavailable. One call consumes from every window of its limit or from none: a refused call does not count. One window is one statement, `INSERT ... ON CONFLICT (key, window_start, window_end) DO UPDATE SET count = count + 1 WHERE count < max`, so two instances racing never let more than `max` through. More than one window (`ai-read`) is one transaction, longest window first, rolled back at the first refusal.
- **Better Auth** gets `rateLimit.customStorage` backed by the same helper and table, always set, so its routes count in the shared store and never in memory, and `advanced.ipAddress.ipAddressHeaders: ["x-forwarded-for"]` (Decision 5). Better Auth's `no-trusted-ip` key part maps to the subject `unknown`.
- **Trusted client IP.** On Vercel, meaning `VERCEL_ENV` is `production` or `preview` (finding F4: a pulled `.env.local` may set Vercel variables locally, with `VERCEL_ENV` as `development`), the IP is the value of `x-forwarded-for`, which Vercel's edge overwrites with the caller's public IP (K-0015, Decision 5). Only a single value counts (finding F5): a comma list, an empty value or a value that is not an IP gives the subject `unknown`, as Better Auth gives no IP for a list. The value is normalised the way Better Auth does it, with the same code (`normalizeIP` and `getIPFromHeader` from `@better-auth/core/utils/ip`, Decision 9): an IPv4-mapped IPv6 address becomes IPv4, and IPv6 is masked to its /64, so a caller cannot dodge a limit by rotating addresses inside one /64. `x-vercel-forwarded-for`, `x-real-ip` and every other header are never read. Off Vercel (local dev, CI) the subject is `local`. A request on Vercel with no usable header is counted under `unknown`, one shared bucket, and logs one warning line per process with no header values.
- **Pruning.** After a call, the helper deletes rows whose `window_end` is more than 24 hours in the past, at most once per minute per instance. A failed prune never changes the call's result. Tests run with pruning on every call.
- **Store failure.** If the limiter's query fails or takes longer than 2 seconds, the call is refused as a failure, never let through: the AI path keeps the rules' reading with the existing `ai-failed` text and makes no model call; a write or import returns `failed`; `signInWithGoogle` returns `failed` and shows the existing failure notice without calling `signInSocial`; `/api/auth/*` answers 503 with `SERVICE_UNAVAILABLE` (Decision 7, finding F8: without it a store error escapes Better Auth's router as a bare 500). The database being down breaks these actions anyway, so failing closed loses nothing. The error is logged at the action or route boundary by its name only, never its message, query or key.
- **Why Postgres holds the load.** Limited calls are human-paced clicks: at MVP scale a few per second at most across the whole app. Each costs one upsert on a small table by primary key (a four round trip transaction for `ai-read`, ahead of a model call of seconds). Postgres on Supabase handles thousands of such statements a second. The cost is latency, one round trip per limited call; the PR records the helper's added time measured on staging (n, p50 and p95 for the single-window path, with the Vercel function region and the Supabase region), and if its 95th percentile is above 50 ms the shared cache question goes to an ADR addition (ADR 0015 Consequences). No new service is added.

## The outcome and the UI

- Server actions return an outcome, not an HTTP status (ADR 0015 decision 7). A refused call returns `{ ok: false, error: "rate-limited" | "ai-rate-limited", code: "RATE_LIMITED", retryAfter: <seconds>, retryable: true }`.
- `/api/auth/*` goes through one wrapper, `authRoute` in `packages/auth`, used by the route file, so row 12's integration test covers the header and the body (finding F6). A refused call answers status 429 with a `Retry-After` header in seconds (Better Auth sends only `X-Retry-After`; the wrapper copies it and keeps the original) and the body `{"error": {"code": "RATE_LIMITED", "message": "Too many requests. Try again later.", "requestId": "<random id>", "retryable": true}}`. A store failure answers status 503 with the body `{"error": {"code": "SERVICE_UNAVAILABLE", "message": "Service unavailable. Try again later.", "requestId": "<random id>", "retryable": true}}`. Any other error is rethrown, as today. The bodies are read by code, not shown to people, so their messages are English only.
- Nothing retries automatically in this story. The person reads the wait and acts again (the client retry matrix is ORV-113).
- The wait shows as seconds under 60, else whole minutes rounded up under 3600, else whole hours rounded up.
- **Where each notice shows** (G2, `docs/specs/ORV-112/design.md` §4, deltas X1 to X4). A refused save, approve or import, signed in or signed out, shows in the existing notice region of the "Saved directions" card, word `saved.problem` ("Not done" / "ทำไม่สำเร็จ") above the line. A refused AI reading (`ai-rate-limited`, or `rate-limited` when the session has ended) shows in `DirectionStudio`'s reading section, in a note row under the "Read with AI" button, word `direction.aiNotice` ("Check this" / "โปรดตรวจดู") above the line, and not also in the card region: one message, one place. A refused sign-in shows under the button on `/account`, word `account.problem` ("Not done" / "ทำไม่สำเร็จ") above the line. Each notice sits in a polite live region and never takes focus.
- **The AI notice reaches the studio through `readWithAi`** (X1). `DirectionStudio`'s public prop widens from `(brief: string) => Promise<Interpretation | null>` to `(brief: string) => Promise<Interpretation | null | { notice: string }>`. `null` keeps today's failed line; `{ notice }` shows the caller's line, already in the person's language with `{wait}` filled. `SavedStudio` returns `{ notice }` for `ai-rate-limited` and `rate-limited`; every other error keeps today's path. Editing the brief clears the note, as it clears the failed line today.
- **The `ai-failed` line moves into the same note row** (X2). The existing "AI could not read the brief" line (row 15) no longer sits beside the button; it shows in the note row, muted and without a badge, so both "AI did not read" states share one place.
- If `retryAfter` is not a positive finite number, the line falls back to the existing `errors.failed` text rather than printing an empty wait.

New catalog strings (Thai and English together; `apps/web/i18n/messages.ts`, except a key marked "design-system", which lives in `packages/design-system/src/i18n`). `account.problem` and `direction.aiNotice` are the words on the notice badges (G2, X3); they repeat `saved.problem` and `saved.attention` so a refusal reads the same on every screen:

## Rules and bounds

- Every limited server action calls the one helper before any other work except the session read; no action keeps its own counter, and no counter lives in process memory.
- A limit is per person when a session exists, per trusted IP when it does not. A workspace id from the client never picks a bucket.
- The numbers live in one exported map beside the helper, so a change is one line and its test. `.claude/rules/security.md` rule 6 names them, and ADR 0015 decision 4 records them as an addition (architect).
- Fixed windows allow up to twice a limit across a window boundary, for our limits and for Better Auth's rules alike. Accepted at these numbers.
- Only `x-forwarded-for` picks an IP bucket on Vercel, and only as a single value. If a proxy is ever placed in front of Vercel, the header choice is reopened first (K-0015 warns such a proxy can overwrite it).
- No raw IP and no user email in a key or a log line. A log line for a call holds the limit name, the outcome and its duration only.
- Thai and English copy together, no middot, no em dash.

## Out of scope

- **The AI spend cap per workspace** (ADR 0015 decision 4, code `AI_SPEND_CAP`), moved to its own story, [ORV-121](https://tpetkaew.atlassian.net/browse/ORV-121). It needs OpenRouter's reported usage stored per call and a monthly sum. ADR 0015 decision 4's confirmation stays half open until ORV-121 lands (Decision 2).
- Limits on reads, exports and the locale action.
- Distributed abuse from many IPs or accounts (Vercel firewall or an edge rule).
- The client retry matrix and the request id helper (ORV-113); this story makes a random request id only for the 429 and 503 bodies.
- Storage upload limits; no upload path exists yet.

## Decisions

Decisions 1 to 6 were decided at G1, recorded in the G1 decision comment on [ORV-112](https://tpetkaew.atlassian.net/browse/ORV-112). Decision 5 was revised and decisions 7 to 9 added after the architect review (`docs/specs/ORV-112/tech.md`, findings F1 to F12), recorded on the issue.

1. **The numbers.** `ai-read` is 10 per hour and 50 per day per person (v1 proposed 20 and 60). `sign-in`, `auth-http`, `write`, `import` and `signed-out` stay as v1 proposed. Rows 5 and 6 and the "Limits and numbers" table carry the decided numbers.
2. **Spend cap.** Not in this story. It moves to [ORV-121](https://tpetkaew.atlassian.net/browse/ORV-121), listed under Out of scope. ADR 0015 decision 4's confirmation stays half open until ORV-121 is done.
3. **Day window start.** 00:00 Asia/Bangkok (UTC+7, no daylight saving). Not 00:00 UTC, which resets at 07:00 in Thailand, and not a rolling 24 h, which needs a log of calls.
4. **How the sign-in notice reaches the page.** `useActionState` in a small client form on `/account`. No redirect with a `?wait=` parameter, since anyone could craft that URL to show the notice.
5. **The trusted IP header on Vercel (revised).** `x-forwarded-for`. K-0015 (`docs/knowledge/platform/K-0015-vercel-client-ip-headers.md`) found that Vercel's docs say only of `x-forwarded-for` that the edge overwrites it with the client's public IP to prevent spoofing, with a custom value passing only through an Enterprise trusted proxy; they call `x-vercel-forwarded-for` and `x-real-ip` identical to it but never say a client-sent value of either is replaced. G1 chose `x-vercel-forwarded-for` pending that research; the research does not back it against client forgery, so the header is the one the docs do back. The docs' caveat, a proxy in front of Vercel overwriting `x-forwarded-for`, does not apply: no proxy sits in front of Vercel. The step from "documented" to "a client cannot forge it" is checked on staging by row 21 before slice B passes G4; if the probe fails, this spec changes first with a version bump.
6. **Store failure.** Fail closed, as in "The store and the helper". A store outage never disables a limit.
7. **Store failure on `/api/auth/*`.** 503 with the error envelope, code `SERVICE_UNAVAILABLE`, `retryable: true` (finding F8), row 20. The code joins ORV-113's closed list.
8. **`auth-http` buckets.** Counted per trusted IP and rule (`<window>x<max>`), not per path, with Better Auth's numbers unchanged (finding F2), row 23.
9. **IP normalisation.** `@better-auth/core` 1.7.12 becomes a direct dependency of `packages/auth`, pinned to the `better-auth` version, so our actions and Better Auth's routes parse and normalise the IP with the same code. The `node:net` alternative in tech.md is not taken.
