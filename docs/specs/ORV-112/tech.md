# ORV-112 tech notes: a shared rate limit store in Postgres

This turns the spec's "The store and the helper" into a design you can build. It was checked against ADR 0002 (server-only access, restricted role), ADR 0009 (rules' reading as the fallback, cost), ADR 0015 decisions 4 and 7, `.claude/rules/security.md`, K-0015 (Vercel client IP headers), and the installed Better Auth 1.7.12 source:

- `better-auth/dist/api/rate-limiter/index.mjs`
- `better-auth/dist/api/index.mjs` (router `onRequest`)
- `@better-auth/core/dist/utils/ip.mjs`
- `@better-auth/core/dist/types/init-options.d.mts`
- `better-call@1.4.4/dist/router.mjs`

Findings that change the spec are in "Findings for the spec" at the end. They are listed there and not edited into the spec.

## 1. What Better Auth 1.7.12 actually asks for

These facts were read from the installed source. They shape the design.

- **`customStorage` has a single method.** It is `consume(key, rule: { window, max }) => Promise<{ allowed, retryAfter: number | null }>` (`BetterAuthRateLimitStorage`, `init-options.d.mts`). The old `get` and `set` pair is gone. When `customStorage` is set, `getRateLimitStorage` returns it first, so neither the memory map nor the `rateLimit` model is used.
- **The rule comes with each request.** `onRequestRateLimit` resolves `window` and `max` from the path: 3 per 10 s on `/sign-in*`, `/sign-up*`, `/change-password*` and `/change-email*`; 3 per 60 s on the password reset and verification paths; plugin rules; then the default 100 per 10 s. So the storage has to accept any window and max, not only names from our map.
- **The key is `${ip}|${path}`** (`createRateLimitKey`). If no IP resolves, it is `no-trusted-ip|${path}`, plus one warning per process.
- **The limiter runs before the route is looked up** (`router.handler`: `onRequest`, then `processRequest`, then `findRoute`). Any path under `/api/auth/` reaches `consume`, including paths that do not exist. If we keyed by path, a caller could create one counter row per made-up path.
- **An error thrown in `consume` is not caught.** better-call's `try/catch` wraps `processRequest` only. Its `onRequest` call sits outside it, so a throw leaves `auth.handler()` and becomes Next's bare 500 unless our route catches it.
- **How the IP is resolved.** `getIP` walks `advanced.ipAddress.ipAddressHeaders` in order (default `["x-forwarded-for"]`). If `trustedProxies` is not set, a header counts only when it holds a single valid IP. A comma list gives `null`. The IP is then normalised: IPv4-mapped IPv6 becomes IPv4, and IPv6 is masked to /64 (`ipv6Subnet`, default 64). In test and development with no header, it returns `127.0.0.1`.
- **The library describes `consume` as a rolling window.** Its interface comment says "rolling `window`". We use fixed, aligned windows (spec, "Limits and numbers"). The contract only needs `allowed` to mean "counted" and `retryAfter` to mean "seconds until it frees up", and fixed windows meet both. The burst is a different shape: up to 2x max across a window boundary, which the spec accepts.

## 2. The table and the migration

Two files, following the repo's pattern of one generated file plus one hand-written file (`0002_directions` + `0003_directions_access`, `0000_init` + `0001_access`):

- `packages/db/migrations/0005_rate_limits_access.sql`, made by `drizzle-kit generate --custom --name rate_limits_access`, holding the grant, row security, policy and revoke.

Each comes with its `meta/*_snapshot.json` and a `_journal.json` entry.

### Schema file `packages/db/src/schema/rate-limit.ts`, exported from `schema/index.ts`

```ts
import { sql } from "drizzle-orm";
import { bigint, check, index, integer, pgTable, primaryKey, text } from "drizzle-orm/pg-core";

/**
 * Shared rate limit counters (ORV-112, ADR 0015 decision 4). One row per key and window.
 * Not workspace data: no workspace_id. Written only through `createRateLimiter` in @orivilo/auth.
 */
export const rateLimitCounter = pgTable(
  "rate_limit_counter",
  {
    key: text("key").notNull(),
    windowStart: bigint("window_start", { mode: "number" }).notNull(), // Unix seconds
    windowEnd: bigint("window_end", { mode: "number" }).notNull(), // Unix seconds, exclusive
    count: integer("count").notNull(),
  },
  (t) => [
    primaryKey({ columns: [t.key, t.windowStart, t.windowEnd] }),
    index("rate_limit_counter_window_end_idx").on(t.windowEnd),
    check("rate_limit_counter_count_check", sql`${t.count} >= 1`),
    check("rate_limit_counter_window_check", sql`${t.windowEnd} > ${t.windowStart}`),
    check("rate_limit_counter_key_check", sql`char_length(${t.key}) <= 200`),
  ],
);
```

**The primary key is (`key`, `window_start`, `window_end`). The spec has (`key`, `window_start`), and that is a bug** (finding F1). `ai-read` keeps its hour and day windows under one key, `ai-read:u:<id>`. The Bangkok day starts at 17:00 UTC, which is also the top of an hour. So once a day the hour window and the day window have the same `window_start`, and they would fall on the same row. The two-window transaction would then raise one row twice and count every call double in that hour. Adding `window_end`, which is start plus length, keeps the windows apart with no new column.

`count >= 1` holds because a row only exists once a call has been counted, and a refusal never writes.

The revoke loop is why the spec's "nothing to any other role" holds whether or not Supabase grants new tables to `anon` and `authenticated` by default. ## 3. Keys, subjects and the trusted IP

### Key format

| Limit                     | Key                                     |
| ------------------------- | --------------------------------------- |
| per person                | `<limit>:u:<user id>`                   |
| per IP                    | `<limit>:ip:<subject>`                  |
| Better Auth (`auth-http`) | `auth-http:ip:<subject>:<window>x<max>` |

`<subject>` is one of:

- the 64-char hex HMAC of the normalised IP;
- `local` (off Vercel);
- `unknown` (on Vercel, but no usable header).

The user id is Better Auth's own random id, taken from the session on the server. It never comes from the client.

**Better Auth keys are by rule, not by path** (finding F2). The storage reads the IP part of Better Auth's key up to the first `|` and drops the path. It keys the counter by the rule (`10x3`, `10x100`, `60x3`) instead. This gives each IP at most a few rows, whatever paths a caller makes up. The numbers do not change. One effect: the 100 per 10 s "elsewhere" rule now covers all of a caller's ordinary auth paths together, not each path alone, which is stricter. Every path under one rule shares a bucket, so `/sign-in/social` and any other `/sign-in*` path share 3 per 10 s. If Better Auth's IP part is `no-trusted-ip`, the subject is `unknown`.

### The HMAC and its key (`packages/auth/src/client-ip.ts`)

- `ipKey = HMAC-SHA-256(key = BETTER_AUTH_SECRET, message = "orivilo/rate-limit/ip/v1")`. This is derived once, when the limiter is built. Subject: `HMAC-SHA-256(key = ipKey, message = normalisedIp)`, as hex.
- **Why derive a key instead of using the secret directly** (finding F3). `sealReading` already uses `BETTER_AUTH_SECRET` as an HMAC key, and keeping the two uses apart costs one line. No new environment variable is added. The secret stays where ADR 0002 and the security rules keep it: the Vercel environment and `.env.local`. It never goes to the database, a log or the client. `ipKey` only lives in memory.
- If `BETTER_AUTH_SECRET` is rotated, every IP bucket is reset. That is acceptable, since buckets last minutes or hours at most.
- Without the key, the hashes cannot be turned back into IPs, even though IPv4 is only 2^32 addresses. A hashed IP is still pseudonymous personal data. Rows live at most 24 hours past their window's end, so 48 hours at most for a day window (§5). When `classification.ts` lands (ORV-113), tag `key` as `personal` and the other three columns as `internal`. This is a record of retention, not a PDPA claim.

Note, 2026-10-30 (ORV-158): `classification.ts` landed, and `rateLimitCounter.key` is tagged `personal` and the other three columns `internal`, as the line above asked. The test `packages/db/src/schema/classification.test.ts` pins `rateLimitCounter.key` in the `personal` set.

### Reading the IP: `clientIp(headers, env, secret): string` returns a subject

1. **Is this Vercel?** Yes if `env.VERCEL_ENV` is `"production"` or `"preview"`. Otherwise it is "off Vercel" and the subject is `local`. The spec's test is "`VERCEL` is set" (finding F4). K-0015 notes that a pulled `.env.local` may set Vercel variables locally. `VERCEL_ENV` is `development` in that file, and `settingsFromEnv` already relies on `VERCEL_ENV` on deployments.
2. **On Vercel:** read only `x-forwarded-for`, through `getIPFromHeader`. If it holds exactly one valid IP, normalise it with the same rules as Better Auth: IPv4 as it is, IPv4-mapped IPv6 to IPv4, IPv6 masked to its /64. Then HMAC it. If it is missing, empty, a comma list or not an IP, the subject is `unknown`, with one `client-ip` step line per process through `logStep`: `level: "warn"`, `step: "client-ip"`, `outcome: "no-trusted-ip"`, `durationMs`, and the request's `requestId` and `route`, with no header values (ORV-141 tech notes section 6, built in ORV-142 task B4). Before ORV-142 it was one `console.warn` of `{"level":"warn","route":"rate-limit","outcome":"no-trusted-ip"}`, with no request id.
3. **`x-vercel-forwarded-for`, `x-real-ip` and every other header are never read.**

**Normalising.** Import `normalizeIP` and `getIPFromHeader` from `@better-auth/core/utils/ip`. That package is exported as `./utils/*`, and Better Auth already installs it. Add `"@better-auth/core": "1.7.12"` to `packages/auth/package.json`, pinned to the same version as `better-auth`, because pnpm will not resolve a transitive dependency. Then our sign-in bucket and Better Auth's route bucket parse the header with the same code, and IPv6 callers cannot dodge the limit by rotating addresses inside their /64. This is decided (ORV-112, after review): `@better-auth/core` 1.7.12 is a direct dependency of `packages/auth`, and there is no hand-written `node:net` version. When `better-auth` is upgraded, `@better-auth/core` moves with it in the same change.

**The spec says "first value"; this design takes the single value only** (finding F5). Better Auth gives `null` for a list when `trustedProxies` is not set, so taking the first item would bucket the action and the route differently. A list from Vercel would be unexpected (K-0015: the docs describe one "public IP address"), so here `unknown` is the safer answer.

**The trusted header is `x-forwarded-for`** (decided on ORV-112 after review, replacing the spec's `x-vercel-forwarded-for` default from G1 decision 5; the spec records it in its next version). K-0015: it is the only header Vercel's docs say is overwritten with the client's public IP to prevent spoofing, and a custom value passes only through an Enterprise trusted proxy. The docs call `x-vercel-forwarded-for` and `x-real-ip` identical to it, but never say a client-sent value of either is replaced. The cost K-0015 names is that a proxy placed in front of Vercel could overwrite `x-forwarded-for`. ORIVILO has no such proxy; adding one reopens this choice. It is also Better Auth's default header, so `clientIp` and Better Auth's `getIP` read the same header with the same code. "Documented as overwritten" is still an inference about a client's reach, so the staging probe (§9.4) is the G4 check for slice B.

## 4. The helper (`packages/auth/src/rate-limit.ts`)

### Public surface (exported from `packages/auth/src/index.ts`)

```ts
import type { Db } from "@orivilo/db/client";

/** One fixed window. It starts at floor((t + offsetSeconds) / seconds) * seconds - offsetSeconds. */
export interface Window {
  seconds: number;
  max: number; // integer >= 1
  /** Shifts the alignment. The Bangkok day is +25_200 (UTC+7, no daylight saving). */
  offsetSeconds?: number;
}
export interface Limit {
  name: string;
  /** Longest first. Each window nests in the one before it (checked by `assertNested`). */
  windows: readonly Window[];
}

export const BANGKOK_OFFSET_SECONDS = 7 * 3600;

/** The decided numbers (spec v1.1, G1 decision 1). One line per limit; `limits.test.ts` pins them. */
export const LIMITS = {
  "sign-in": { name: "sign-in", windows: [{ seconds: 600, max: 10 }] },
  "ai-read": {
    name: "ai-read",
    windows: [
      { seconds: 86_400, max: 50, offsetSeconds: BANGKOK_OFFSET_SECONDS },
      { seconds: 3_600, max: 10 },
    ],
  },
  write: { name: "write", windows: [{ seconds: 600, max: 60 }] },
  import: { name: "import", windows: [{ seconds: 3_600, max: 10 }] },
  "signed-out": { name: "signed-out", windows: [{ seconds: 600, max: 30 }] },
} as const satisfies Record<string, Limit>;
export type LimitName = keyof typeof LIMITS;

export type Subject = { user: string } | { ip: string; scope?: string }; // ip from `clientIp`; scope only for auth-http (`10x3`), appended as `:<scope>`

export type Consumed =
  | { ok: true }
  | { ok: false; reason: "limited"; retryAfter: number } // whole seconds, >= 1
  | { ok: false; reason: "unavailable" }; // the store failed or timed out: fail closed

export interface RateLimitDeps {
  db: Db; // the orivilo_app pool
  now?: () => number; // ms since epoch; default Date.now
  pruneEveryMs?: number; // default 60_000; tests pass 0
  timeoutMs?: number; // default 2_000; past this the call is "unavailable"
  /** One line per call for the latency measurement; never receives the key. */
  onResult?: (r: {
    limit: string;
    outcome: "allowed" | "limited" | "unavailable";
    durationMs: number;
  }) => void;
}

export interface RateLimiter {
  consume(limit: Limit, subject: Subject): Promise<Consumed>;
  /** `rateLimit.customStorage` for Better Auth, backed by `consume` (limit `auth-http`). */
  betterAuthStorage(secret: string): BetterAuthRateLimitStorage;
}

export function createRateLimiter(deps: RateLimitDeps): RateLimiter;
export class RateLimitUnavailable extends Error {} // thrown only by betterAuthStorage, see §6
```

The spec asks for `consume(limit, subject)` "with an injected clock and database". Here that is the limiter's `consume` method, with the clock and database passed to `createRateLimiter`. Each limiter object keeps its own pruning timestamp, so two limiters on two pools behave like two Vercel instances. Tests give their own `Limit` values, for example `{ name: "t", windows: [{ seconds: 60, max: 2 }] }`, so no test map is needed.

`consume` never throws. A refusal and a store failure are both returned values, and the union type makes every caller deal with them.

### Window maths (pure, unit tested)

For `nowMs`, let `t = Math.floor(nowMs / 1000)`. For each window:

```
start = Math.floor((t + off) / s) * s - off
end   = start + s
```

where `off = offsetSeconds ?? 0`.

- A 10 s or 10 minute window starts at a multiple of its length. An hour starts at the top of the UTC hour, which is also the top of the Bangkok hour, because UTC+7 is a whole-hour offset.
- The day window, with `off = 25_200`, starts at 17:00:00 UTC, which is 00:00 Asia/Bangkok. Example: `2026-10-26T16:59:59Z` is in the day that ends at `2026-10-26T17:00:00Z`, so `retryAfter` is 1. `2026-10-26T17:00:00Z` starts a new day.
- `retryAfter = Math.max(1, Math.ceil((end * 1000 - nowMs) / 1000))`.

**`assertNested(limit)`** checks, for each pair of windows in order (longer `L`, then shorter `S`), that `L.seconds % S.seconds === 0` and `(offL - offS) % S.seconds === 0`. It runs in `createRateLimiter` for every entry of `LIMITS` and in `limits.test.ts`. If the windows nest, a longer window always ends at or after a shorter one. That lets the transaction below stop at the first refusal and still report "the later end wins" (spec, "Limits and numbers"). `ai-read` passes: 86 400 % 3 600 = 0, and 25 200 % 3 600 = 0.

### The upsert (one window)

```sql
INSERT INTO rate_limit_counter AS c (key, window_start, window_end, count)
VALUES ($key, $start, $end, 1)
ON CONFLICT (key, window_start, window_end)
DO UPDATE SET count = c.count + 1
WHERE c.count < $max
RETURNING c.count;
```

- **One row back:** the call was counted. **No rows back:** the row already held `max`, so the call is refused and nothing was written.
- **Why racing instances never pass more than `max`.** Under READ COMMITTED, `INSERT ... ON CONFLICT DO UPDATE` either inserts or locks the existing row and updates it, with no third outcome. A racer that loses the insert waits for the winner's row and then evaluates `WHERE c.count < $max` against the row's latest committed version. Each successful increment holds the row lock until its transaction ends, so at most `max` calls reach `count = max`.
- Build it with drizzle's `sql` template and `db.execute`, with values bound as parameters (never interpolated). Drizzle's query builder `onConflictDoUpdate({ target, set, setWhere })` gives the same statement. Either is fine, as long as the test in §9 passes.

### Every window or none

- **Every limit runs in one transaction**, so `SET LOCAL` can bound it (see the timeout below). The first statement sets the timeouts; then the windows run in `Limit.windows` order (longest first). A one-window limit costs BEGIN, the timeouts, one upsert and COMMIT.
- Sketch:

```ts
await db.transaction(async (tx) => {
  await tx.execute(
    sql`SELECT set_config('statement_timeout', ${ms}, true), set_config('lock_timeout', ${ms}, true)`,
  );
  for (const w of windows) {
    const rows = await tx.execute(upsert(key, w));
    if (rows.length === 0) throw new Refused(w.end); // rolls back the windows already raised
  }
});
```

- **`Refused`** is a private error. It is caught right outside the transaction and turned into `{ ok: false, reason: "limited", retryAfter }`. The rollback undoes any window already raised in this call, so a refused call raises no count (AC 3, AC 4).
- **No deadlock.** Every transaction for a key locks its rows in the same order (longest first), so two transactions cannot wait on each other.
- **Round trips:** BEGIN, the timeouts, one upsert per window, COMMIT. The extra trips are accepted: they buy a database-side bound on every call.
- **Not chosen:** a single statement with a compensating decrement. It would cost one round trip, but other callers could briefly see a count that was over-raised, and a crash between the two statements would leave it raised. The spec's "every window or none" is meant as a real guarantee, so the transaction stays.

### Fail closed and the timeout

- Any error from the database (connection, timeout, constraint) gives `{ ok: false, reason: "unavailable" }`, and nothing is let through.
- The statement races a `timeoutMs` timer, 2 s by default. If the timer wins, the result is also `unavailable`. The same `timeoutMs` is set in the transaction as `statement_timeout` and `lock_timeout` (`SET LOCAL`, through `set_config(..., true)`), so the database cancels a statement at the bound and a lock wait does not outlast it. The timer also sets a `timedOut` flag that the transaction checks before its first statement, before each upsert and after the last one; if it is set, the transaction throws and rolls back, whether the call waited in the pool queue or across `ai-read`'s two windows. The last check runs before COMMIT, not during it: a call answered `unavailable` can still commit its count only when COMMIT is already on the wire as the timer fires. That over-counts by at most one per call and still fails closed, since the caller was told `unavailable` and nothing was let through. Integration tests hold `ACCESS EXCLUSIVE` on the table, lock each `ai-read` window in turn, and fill the pool with five busy connections to prove the rollback; the COMMIT window is not tested. Slice B (the `sign-in` limit and Better Auth's storage) moved to ORV-122.
- The error is logged once, at the action or route boundary, with its `name` only (security rules 8 and 15), never its message, query or key.

### Pruning

After a call, if `now - lastPrune >= pruneEveryMs`, set `lastPrune = now` and run:

```sql
DELETE FROM rate_limit_counter WHERE window_end < $t - 86400;
```

- It is never awaited: `consume` returns without waiting for it, so a hung or slow store cannot hold the result or break the 2 s bound. It runs in a transaction with the same `statement_timeout` and `lock_timeout`, and a rejection is caught and dropped (`onResult` is not affected, the call's result stands). A test with a store that never settles proves `consume` returns `unavailable` within the timeout with pruning on.
- At the default it runs at most once a minute per instance, one extra round trip.
- `window_end` is indexed, so the delete is a range scan.
- Rows never need a `count` reset: a new window is a new row.

### The clock

The app's clock decides the window, not `now()` in the database, so tests can inject one. Two Vercel instances whose clocks differ by a few milliseconds may count a call that lands right on a boundary in different windows. That can only add one call per boundary, and it is accepted with the 2x burst already in the spec.

## 5. Wiring

### Better Auth (`packages/auth/src/config.ts`)

`AuthSettings` gains `rateLimit?: Omit<RateLimitDeps, "db">` (clock, prune and timeout options for tests). The database and the secret already arrive in the settings.

```ts
const limiter = createRateLimiter({ db, ...settings.rateLimit });
// ipKey is derived inside the storage from settings.secret (client-ip.ts)
return betterAuth({
  // ...
  rateLimit: { enabled: true, customStorage: limiter.betterAuthStorage(settings.secret) },
  advanced: { ipAddress: { ipAddressHeaders: ["x-forwarded-for"] } }, // Better Auth's default, set explicitly
});
```

- **`customStorage` is always set.** There is no code path that falls back to the memory store.
- **`ipAddressHeaders` is set in every environment.** Off Vercel the header is missing, and Better Auth returns `127.0.0.1` in development and test, or `null` (shared bucket) under `next start`. Both are harmless locally.
- **`betterAuthStorage(secret).consume(key, rule)`:** split `key` at the first `|`. Turn the IP part into a subject: `no-trusted-ip` becomes `unknown`, and anything else becomes the HMAC of that string, which Better Auth has already normalised. Then call `consume({ name: "auth-http", windows: [{ seconds: rule.window, max: rule.max }] }, { ip: subject, scope: `${rule.window}x${rule.max}` })`.
- **Mapping the result:**
  - `ok` gives `{ allowed: true, retryAfter: null }`;
  - `limited` gives `{ allowed: false, retryAfter }`;
  - `unavailable` throws `RateLimitUnavailable` (§6).

### The auth route (`packages/auth/src/auth-route.ts`, used by `apps/web/app/api/auth/[...all]/route.ts`)

`authRoute(handler: (r: Request) => Promise<Response>): (r: Request) => Promise<Response>` wraps `auth().handler`. It sits in `packages/auth`, not in the route file, so that AC 12's integration test covers the header and the body (finding F6).

- **On a 429 from the handler:** answer 429 with `Retry-After: <X-Retry-After>` (the original `X-Retry-After` is kept too), `Content-Type: application/json`, and the body `{"error":{"code":"RATE_LIMITED","message":"Too many requests. Try again later.","requestId":"<the request's id>","retryable":true}}`. Since ORV-141 the body's `requestId` is the request's id (the proxy's `x-request-id`, or a fresh one from `requestIdOf`), the same value as the `x-request-id` header and the boundary line (ORV-141 tech notes section 5); before ORV-141 it was a fresh `randomUUID()`. Only the limiter makes 429s in this Better Auth setup.
- **On `RateLimitUnavailable`:** answer 503 with `{"error":{"code":"SERVICE_UNAVAILABLE","message":"Service unavailable. Try again later.","requestId":"<the request's id>","retryable":true}}`, the same id as the 429 and the `x-request-id` header since ORV-141; before ORV-141 it was a fresh random id, as on the 429. The spec says nothing about this case (finding F8). Since ORV-144 any other error answers 500 with the `INTERNAL_ERROR` body and the request's id (ORV-144 `orv144-route-answers`); before ORV-144 it was rethrown.
- The route file becomes `export const GET = authRoute((r) => auth().handler(r))`, and the same for `POST`.

### The app (`apps/web/server/rate-limit.ts`, `import "server-only"`)

```ts
let shared: RateLimiter | undefined;
export function limiter() {
  shared ??= createRateLimiter({ db: appDb(), onResult: logRateLimit });
  return shared;
}
export const subjectFromHeaders = (h: Headers) =>
  clientIp(h, process.env, requireEnv("BETTER_AUTH_SECRET"));
```

`logRateLimit` writes one `rate-limit` step line through `logStep`: `level: "info"`, `step: "rate-limit"`, `limit`, `outcome`, `durationMs`, and the request's `requestId` and the entry's `route` (ORV-141 tech notes section 6, built in ORV-142 task B4). It writes no key, no user id and no IP. Before ORV-142 the line was `{"level":"info","route":"rate-limit","limit","outcome","durationMs"}`, with no request id.

Every limited action uses the same database pool as Better Auth, `appDb()` with `max: 5`.

**`apps/web/app/directions/actions.ts`:** `run(fn, limit?: LimitName)`. The order inside `run`:

1. `headers()`, then `getSession`.
2. If `limit` is set:
   - signed in: `consume(LIMITS[limit], { user: session.user.id })`;
   - signed out: `consume(LIMITS["signed-out"], { ip: subjectFromHeaders(h) })`.
3. Map the result:
   - `limited` gives `{ ok: false, error: limit === "ai-read" ? "ai-rate-limited" : "rate-limited", code: "RATE_LIMITED", retryAfter, retryable: true }`;
   - `unavailable` gives `ai-failed` for `ai-read` and `failed` otherwise (AC 15).
4. Only then:
   - signed out: return `signed-out`;
   - signed in: build the service and run `fn`.

Which action uses which limit:

| Action                                           | Limit     |
| ------------------------------------------------ | --------- |
| `readBriefWithAi`                                | `ai-read` |
| `saveDirection`, `approveDirection`              | `write`   |
| `importDirection`                                | `import`  |
| `listDirections`, `openVersion`, `exportVersion` | none      |

**`apps/web/app/account/actions.ts`:** `signInWithGoogle(prev, formData)` for `useActionState`:

1. `consume(LIMITS["sign-in"], { ip: subjectFromHeaders(await headers()) })`.
2. If `limited`: return `{ error: "rate-limited", retryAfter }`. If `unavailable`: return `{ error: "failed" }`. In both cases, return before `signInSocial`.
3. Otherwise run today's code (`signInSocial`, then `redirect(url)`).

Server-side `auth.api` calls skip Better Auth's own limiter (spec, "Why"), so `sign-in` is the only limit on this path.

## 6. Fail closed, path by path

| Path                  | Store fails or times out        | Result the person or caller sees                                         |
| --------------------- | ------------------------------- | ------------------------------------------------------------------------ |
| `readBriefWithAi`     | `unavailable`, then `ai-failed` | rules' reading with the existing "AI could not read" text; no model call |
| save, approve, import | `unavailable`, then `failed`    | existing "failed" text; no transaction runs                              |
| `signInWithGoogle`    | `unavailable`, then `failed`    | account page failure notice; `signInSocial` not called                   |
| `/api/auth/*`         | `RateLimitUnavailable` thrown   | 503 with the error envelope, `retryable: true`                           |

## 7. Latency measurement (spec, "Why Postgres holds the load")

- **Where it comes from.** `durationMs` in `onResult` is measured with `performance.now()` around the counting statement or transaction, excluding pruning. The app writes it in the `rate-limit` log line.
- **How to measure on staging, after slice B is deployed:**
  - Send 200 `GET /api/auth/get-session` requests, which go through `auth-http` at 100 per 10 s, paced at 5 a second (well under the limit). Use a small script run by the QA role or the implementer, which is not part of `pnpm test`.
  - Take the `rate-limit` lines from the Vercel runtime logs for that period.
  - Report n, p50 and p95 for the single-window path.
- **The two-window path** (`ai-read`, 4 round trips) is reported from the readings made during QA, with its n stated. Its p95 is not compared to the budget, because a model call of seconds follows it.
- **Also record** the Vercel function region and the Supabase region in the PR, since the round trip between them is most of the cost.
- **If the single-window p95 is above 50 ms**, raise an addition to ADR 0015 on the shared cache question (spec), and do not merge a cache in this story.
- Slice A can be measured the same way, using the QA role's saves (the `write` limit). Use at least 50 samples, or say in the PR that it has fewer.

## 8. Is an ADR needed?

**No new ADR. One addition to ADR 0015 decision 4, written by a later `architect` task when slice A merges** (it is outside this task's write set).

Why:

- **The choices here carry out decision 4; they do not change it.** It already chose "a Postgres table through the restricted app role", requires a shared store, and asks ORV-112 to "record [the numbers] here as an addition". An addition the ADR itself asks for does not rewrite it.
- **No other ADR is superseded.** ADR 0002 holds (server code only, `orivilo_app`, row security on). ADR 0009 holds (the rules' reading on a refusal, no model call).
- **The addition records** the numbers (§4 `LIMITS`), the `customStorage` choice, the fixed aligned windows with the Bangkok day, the trusted header and its probe, the derived HMAC key, fail closed, and Better Auth keys by rule.

**A new ADR becomes necessary if:**

- the staging probe shows `x-forwarded-for` can be forged, or a proxy is placed in front of Vercel, and the header changes; or
- the measured p95 sends the store question to a cache, which is a new store and possibly a new service, excluded by "No new external service" and ADR 0015 "Not chosen"; or
- a later story wants per-path Better Auth buckets back.

## Slice B as built (ORV-122)

- `createRateLimiter` returns `SharedRateLimiter` (`RateLimiter` plus `betterAuthStorage`), so the app's fake limiters in slice A tests keep the narrow `RateLimiter` type. `RateLimitUnavailable` and `authRoute` are exported from `@orivilo/auth`; `hashIp` in `client-ip.ts` is the one place the IP HMAC is made.
- `Subject` gains `scope` for `auth-http` (`:<window>x<max>` after the subject). Better Auth's `no-trusted-ip` and an empty IP part map to `unknown`.
- The `/account` form is `SignInForm.tsx` (client, `useActionState`); its sentence is the pure `signInLine` in `sign-in-line.ts`, tested in both locales. `SignInForm.test.tsx` renders it with `react-dom/server` in both locales (`apps/web/vitest.config.ts` takes `.test.tsx` and sets the oxc automatic JSX runtime).
- `signInWithGoogle()` takes no parameters: it reads nothing from the form (the provider is fixed, the IP comes from the request headers), and a function with fewer parameters still type-checks against the form's `action` prop that `useActionState` calls with the previous state and the form data.
- `authRoute(handler, { consumeSignIn })` counts `POST /api/auth/sign-in/*` against `LIMITS["sign-in"]` before the handler, in the bucket `signInWithGoogle` uses. Since ORV-141, every answer it gives (the handler's, 429, 503) carries the request's `x-request-id` (the proxy's, or a fresh UUID v4 when none came), its 429 and 503 bodies use that same id, and it writes one boundary line per answer with `route: "api/auth"` (ORV-141 tech notes section 5). Under ORV-122 it set its own random id on its 429 and 503 only and logged one `{level, requestId, route, outcome}` line on a store failure only.
- Spec v1.2 changes: `authRoute` counts only `POST /api/auth/sign-in/*` whose `content-type` is JSON, read as better-call reads it (lower-cased, part before `;`, trimmed, includes `application/json`); Origin is not part of the rule, because Better Auth checks it only with a cookie. Other media types go to the handler uncounted (row 25; unit and integration tests: ten `text/plain` posts with a foreign Origin leave no row, a cookieless JSON post with a foreign Origin is counted). The count is called inside an async wrapper, so a `consumeSignIn` that throws synchronously answers 503 `SERVICE_UNAVAILABLE` with `x-request-id` and one log line (row 20, unit case).
- `apps/web/server/sign-in-limit.ts` exports `consumeSignIn(headers)`: `LIMITS["sign-in"]` with the `subjectFromHeaders` subject. `signInWithGoogle` and `api/auth/[...all]/route.ts` both import it; `sign-in-limit.test.ts` pins the limit and subject (row 24).
- `app/account/page.test.tsx` renders the signed-out page and asserts `main` has `justify-start` and `pt-24` and neither `min-h-dvh` nor `justify-center`; the notice line's `text-pretty` is asserted in `SignInForm.test.tsx` (design D2a).
- The row 21 probe is `scripts/probe/forged-ip-headers.mjs <staging url>` on machine 1 (aligned start, prints the window end) and `... --replay <window end>` on machine 2 (refuses to send after it). It prints one JSON line per request and exits 1 on a fail or a void run. Run it after the staging release, never in CI.
